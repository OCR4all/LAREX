# CI/CD

LAREX uses GitHub Actions workflows in `.github/workflows/`.

## Workflows

| Workflow | File | Purpose |
|----------|------|---------|
| CI | `.github/workflows/ci.yml` | Backend, frontend, docs, theme, Docker image, and Compose validation checks |
| Branch Container Images | `.github/workflows/branch-images.yml` | Deployable branch images for non-production environments |
| Release | `.github/workflows/release.yml` | Versioned release, image publishing, administrator bundle publishing, and version sync |

## CI Workflow (`ci.yml`)

### Triggers

- Push to `main`
- Pull requests targeting `main`
- Reusable workflow calls from release and branch-image workflows

### Jobs

1. `backend` (Backend Tests)
- Uses PostgreSQL `17-alpine` service
- Runs with JDK 25 (Temurin)
- Executes `./gradlew test`
- Builds JAR via `./gradlew build -x test`
- Uploads backend test reports as artifact

2. `frontend` (Frontend Checks)
- Uses Node 22 + pnpm 11.5.2
- Installs dependencies in `frontend/`
- Runs linting, type checking, tests, and a production build

3. `keycloak-theme` (Keycloak Theme Build)
- Uses Node 22 + pnpm 11.1.2
- Installs dependencies in `keycloak-theme/`
- Runs `pnpm run build-keycloak-theme`
- Uploads generated theme artifact (`dist_keycloak/`)

4. `docs` (Docs Build)
- Uses Node 22 + pnpm 11.6.0
- Installs dependencies in `docs/` with `--frozen-lockfile`
- Stages the canonical deployment assets and runs `pnpm build`

5. `compose-validation` (Compose Validation)
- Validates local dev, production-like, bundled Keycloak, external Keycloak, bundled Nginx, Actions, and self-hosted docs Compose configurations
- Builds the complete administrator deployment ZIP to catch missing canonical assets
- Checks for stale deployment references in `README.md`, `docs`, and `Taskfile.yml`

6. `docker-build` (PR-only build test)
- Runs only on pull requests
- Builds backend, frontend, and docs production Docker images with Buildx
- Does not push images

7. `dependency-review` (PR-only supply-chain check)
- Reviews dependency changes through GitHub's dependency graph
- Rejects newly introduced high or critical runtime vulnerabilities

## Branch Container Images Workflow (`branch-images.yml`)

### Triggers

- Push to `dev`, `staging`, or `next`
- Manual dispatch (`workflow_dispatch`) when run from `dev`, `staging`, or `next`

### Pipeline

1. `test`
- Reuses `ci.yml`
- Must pass before images are published

2. `build-and-push`
- Builds backend, frontend, and docs images
- Pushes mutable branch tags for deployable non-production environments
- For `next`, also pushes the snapshot version from `VERSION` (for example `1.0.0-SNAPSHOT`)
- Does not create GitHub releases

## Release Workflow (`release.yml`)

### Triggers

- Push to `main` when `VERSION` changes
- Manual dispatch (`workflow_dispatch`) with optional `skip_tests`

### Pipeline

1. `version`
- Reads and normalizes `VERSION`
- Exposes it as workflow output

2. `test`
- Reuses `ci.yml`
- Skipped when `skip_tests=true`

3. `build-and-push`
- Builds and pushes backend/frontend/docs production images to `ghcr.io`
- Runs after successful tests (or when tests are skipped manually)
- Adds Docker metadata tags
- Generates SPDX SBOM and maximum-mode provenance attestations
- Scans all three images and blocks fixable high or critical vulnerabilities
- Signs approved image digests keylessly with Sigstore and GitHub OIDC

4. `create-release`
- Creates GitHub release `v<version>`
- Uses generated release notes
- Attaches the deployment ZIP, its SHA-256 checksum, and an immutable manifest
  binding the source commit, archive checksum, and container-image digests
- Creates a GitHub build-provenance attestation for the ZIP and manifest

5. `sync-versions`
- Runs `scripts/version-sync.sh`
- Commits and pushes version-sync changes if needed

## Image Tags

Release images are tagged with Docker metadata rules, including:

- `<version>`
- `<version>-<sha>`
- `latest` (default branch only)
- `sha-<sha>`

Branch images are tagged with:

- `<branch>` such as `dev`, `staging`, or `next`
- `<branch>-<sha>`
- the `VERSION` snapshot tag when building `next`
- `sha-<sha>`

Set `LAREX_IMAGE_TAG` to the branch tag for non-production deployments, for example `LAREX_IMAGE_TAG=staging`.

## Verifying a Release

Verify the administrator bundle before extraction:

```bash
sha256sum --check larex-deployment-<version>.zip.sha256
```

After extraction, verify its complete internal file manifest:

```bash
cd larex-deployment-<version>
sha256sum --check SHA256SUMS
```

The `larex-release-<version>.json` release asset contains digest-qualified image
references. With the GitHub CLI and Cosign installed, verify the release-file
attestation and any recorded image:

```bash
gh attestation verify larex-deployment-<version>.zip --repo ocr4all/larex

IMAGE=$(jq -r '.images.backend' larex-release-<version>.json)
cosign verify "$IMAGE" \
  --certificate-identity \
  'https://github.com/ocr4all/larex/.github/workflows/release.yml@refs/heads/main' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com'
```

## Registry and Auth

- Registry: `ghcr.io`
- Backend image: `ghcr.io/ocr4all/larex/backend`
- Frontend image: `ghcr.io/ocr4all/larex/frontend`
- Docs image: `ghcr.io/ocr4all/larex/docs`
- Authentication: `GITHUB_TOKEN` via `docker/login-action`

## Local Validation

Useful local commands before pushing:

```bash
task test
task build
cd docs && pnpm build
```
