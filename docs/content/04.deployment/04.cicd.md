LAREX uses GitHub Actions workflows in `.github/workflows/`.

## Workflows

| Workflow | File | Purpose |
|----------|------|---------|
| CI | `.github/workflows/ci.yml` | Backend, frontend, docs, theme, Docker image, and Compose validation checks |
| Branch Container Images | `.github/workflows/branch-images.yml` | Deployable branch images for non-production environments |
| Semantic Release | `.github/workflows/semantic-release.yml` | Calculates the next version from commit messages, updates the changelog and version files, and pushes the release or release candidate tag |
| Release | `.github/workflows/release.yml` | Builds, signs, and publishes a release from its `v<version>` tag |

## CI Workflow (`ci.yml`)

### Triggers

- Push to `main`
- Pull requests targeting `main` or `dev`
- Reusable workflow calls from release and branch-image workflows

### Jobs

1. `backend` (Backend Tests)
- Uses PostgreSQL `18.7-alpine` service
- Runs with JDK 25 (Temurin)
- Executes `./gradlew test`
- Builds JAR via `./gradlew build -x test`
- Uploads backend test reports as artifact

2. `frontend` (Frontend Checks)
- Uses Node 22 + pnpm 11.5.2
- Installs dependencies in `frontend/`
- Runs linting, type checking, tests, and a production build

3. `keycloak-theme` (Keycloak Theme Build)
- Uses Node 22 + pnpm 11.1.2
- Installs dependencies in `keycloak-theme/`
- Runs `pnpm run build-keycloak-theme`
- Uploads generated theme artifact (`dist_keycloak/`)

4. `docs` (Docs Build)
- Uses Node 22 + pnpm 11.6.0
- Installs dependencies in `docs/` with `--frozen-lockfile`
- Stages the canonical deployment assets and runs `pnpm build`

5. `compose-validation` (Compose Validation)
- Validates local dev, production-like, bundled Keycloak, external Keycloak, bundled Nginx, Actions, and self-hosted docs Compose configurations
- Builds the complete administrator deployment ZIP to catch missing canonical assets
- Checks for stale deployment references in `README.md`, `docs`, and `Taskfile.yml`

6. `docker-build` (PR-only build test)
- Runs only on pull requests
- Builds backend, frontend, and docs production Docker images with Buildx
- Does not push images

7. `dependency-review` (PR-only supply-chain check)
- Reviews dependency changes through GitHub's dependency graph
- Rejects newly introduced high or critical runtime vulnerabilities

## Branch Container Images Workflow (`branch-images.yml`)

### Triggers

- Push to `dev`
- Manual dispatch (`workflow_dispatch`) when run from `dev`

### Pipeline

1. `test`
- Reuses `ci.yml`
- Must pass before images are published

2. `build-and-push`
- Builds backend, frontend, and docs images
- Pushes the mutable `dev` tag for environments that follow every push
- Reports `<branch>-<sha>` as the application version
- Does not create GitHub releases or push version tags

## Branches and Releases

Work happens on feature branches that open pull requests into `dev`. `dev` is
promoted to `main` for each stable release.

1. Start the Semantic Release workflow from `dev` to tag a release candidate
   `v<version>-rc.<n>`. The Release workflow publishes it as a GitHub prerelease
   with signed images, a deployment bundle, and a manifest.
2. Deploy the candidate to staging by pinning its version, for example
   `LAREX_IMAGE_TAG=1.1.0-rc.1`. Staging is an environment, not a branch.
3. Fix problems on `dev` and tag the next candidate until staging passes.
4. Merge `dev` into `main`. CI and Semantic Release tag the stable `v<version>`.
5. Merge `main` back into `dev` so the next candidate counts from the new release.

Release candidates do not add `CHANGELOG.md` sections. The stable release lists
every change from its candidates. The changelog templates in
`scripts/release/changelog-templates` implement this.

## Versioning

LAREX follows [Semantic Versioning](https://semver.org/) and derives each version
from [Conventional Commits](https://www.conventionalcommits.org/) on `main` with
[python-semantic-release](https://python-semantic-release.readthedocs.io/).
`releaserc.toml` holds its configuration.

| Commits since the last release | Next version |
|---|---|
| `BREAKING CHANGE:` footer or `!` after the type, such as `feat!:` | Major |
| `feat:` | Minor |
| `fix:` or `perf:` | Patch |
| Only other types, such as `docs:`, `chore:`, `refactor:`, `test:`, or `ci:` | No release |

Write commit subjects in this format, including the subjects of squash merges. A
release updates these files in a `chore(release): <version>` commit:

- `VERSION`
- `CHANGELOG.md`
- `backend/gradle.properties`
- `frontend/package.json`
- `keycloak-theme/package.json`
- the default image tag of the docs deployment wizard

Do not change these versions by hand. On `main`, `VERSION` holds the most recent
release. On `dev`, it can hold the most recent release candidate.

To check the next version locally, run:

```bash
uvx --from python-semantic-release==10.6.1 --with 'gitpython<3.1.60' semantic-release -c releaserc.toml --noop version --print
```

## Semantic Release Workflow (`semantic-release.yml`)

### Triggers

- Successful completion of the CI workflow for a push to `main`
- Manual dispatch from `main` or `dev` (`workflow_dispatch`) with an optional
  `patch`, `minor`, or `major` override. A dispatch from `dev` creates a release
  candidate.

### Pipeline

1. `version`
- Checks out the commit that passed CI
- Runs python-semantic-release, which exits without changes when no commit
  requires a release
- Otherwise commits the version files and changelog, tags the commit
  `v<version>` (or `v<version>-rc.<n>` on `dev`), and pushes both with the
  `RELEASE_TOKEN` secret

`RELEASE_TOKEN` must be a token that can push to `main` and `dev` and whose tag pushes
start workflows. Tags pushed with the default `GITHUB_TOKEN` do not start the
Release workflow. GitHub only runs `workflow_run` triggers from workflow files on
the default branch.

## Release Workflow (`release.yml`)

### Triggers

- Push of a `v<major>.<minor>.<patch>` or `v<major>.<minor>.<patch>-rc.<n>` tag
- Manual dispatch (`workflow_dispatch`) from a release tag, with optional `skip_tests`

### Pipeline

1. `version`
- Reads the version from the tag
- Fails unless the tag is a stable version or release candidate, matches
  `VERSION`, and points to a commit on `main` (stable) or `dev` (candidate)

2. `test`
- Reuses `ci.yml`
- Skipped when `skip_tests=true`

3. `build-and-push`
- Builds and pushes backend/frontend/docs production images to `ghcr.io`
- Runs after successful tests (or when tests are skipped manually)
- Adds Docker metadata tags
- Generates SPDX SBOM and maximum-mode provenance attestations
- Scans all three images and blocks fixable high or critical vulnerabilities
- Signs approved image digests keylessly with Sigstore and GitHub OIDC

4. `create-release`
- Creates GitHub release `v<version>`
- Uses the version's `CHANGELOG.md` section as release notes
- Publishes release candidates as prereleases that never become the latest
  release, with notes generated by GitHub
- Attaches the deployment ZIP, its SHA-256 checksum, and an immutable manifest
  binding the source commit, archive checksum, and container-image digests
- Creates a GitHub build-provenance attestation for the ZIP and manifest

## Image Tags

Release images are tagged with Docker metadata rules, including:

- `<version>`
- `<version>-<sha>`
- `latest`, for stable releases only
- `sha-<sha>`

Branch images are tagged with:

- `dev`
- `dev-<sha>`
- `sha-<sha>`

Pin staging to a release candidate, for example `LAREX_IMAGE_TAG=1.1.0-rc.1`.
Use `LAREX_IMAGE_TAG=dev` only for environments that follow every push to `dev`.

## Verifying a Release

Download `larex-deployment-<version>.zip`, its `.sha256` file, and
`larex-release-<version>.json` from the GitHub release into one directory. Run
every command below from that directory. Verify the administrator bundle
before extraction:

```bash
sha256sum --check larex-deployment-<version>.zip.sha256
```

After extraction, verify its complete internal file manifest. The subshell
keeps your working directory unchanged for the following steps:

```bash
(cd larex-deployment-<version> && sha256sum --check SHA256SUMS)
```

The `larex-release-<version>.json` release asset contains digest-qualified image
references. With the GitHub CLI and Cosign installed, verify the attestations of
the ZIP and the JSON manifest before you trust its image references, then verify
any recorded image:

```bash
gh attestation verify larex-release-<version>.json --repo ocr4all/larex

gh attestation verify larex-deployment-<version>.zip --repo ocr4all/larex

IMAGE=$(jq -r '.images.backend' larex-release-<version>.json)
cosign verify "$IMAGE" \
  --certificate-identity \
  'https://github.com/ocr4all/larex/.github/workflows/release.yml@refs/tags/v<version>' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com'
```

## Registry and Auth

- Registry: `ghcr.io`
- Backend image: `ghcr.io/ocr4all/larex/backend`
- Frontend image: `ghcr.io/ocr4all/larex/frontend`
- Docs image: `ghcr.io/ocr4all/larex/docs`
- Authentication: `GITHUB_TOKEN` via `docker/login-action`
