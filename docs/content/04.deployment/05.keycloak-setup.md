LAREX supports two auth modes:

- bundled Keycloak through `compose.prod.auth.bundled-keycloak.yaml`
- external Keycloak through `compose.prod.auth.external-keycloak.yaml`

Both modes rely on the same LAREX realm model.

## Bootstrap Realm Template

LAREX ships `config/keycloak/larex.bootstrap.realm.json` as the bootstrap template for fresh realms.

It creates:

- realm role `GLOBAL_ADMIN`
- realm role `LAREX_DELETE_ACCOUNT`, which grants the `account/delete-account` client role to every user
- backend service-account client `larex-backend-service` with the `kc-admin-api` client scope
- frontend client `larex-frontend`
- initial seeded admin user from `LAREX_INITIAL_ADMIN_*`
- enabled `delete_account` required action for self-service account deletion

## Bundled Keycloak

The bundled auth overlay runs Keycloak with `--import-realm` and mounts the bootstrap template automatically.

Relevant env values:

- `KEYCLOAK_REALM`
- `KEYCLOAK_ADMIN`
- `KEYCLOAK_ADMIN_PASSWORD`
- `KEYCLOAK_ADMIN_CLIENT_SECRET`
- `NUXT_OAUTH_KEYCLOAK_CLIENT_SECRET`
- `LAREX_INITIAL_ADMIN_*`

After first login:

- rotate `KEYCLOAK_ADMIN_PASSWORD`
- rotate `LAREX_INITIAL_ADMIN_TEMP_PASSWORD`
- change any placeholder client secrets

The bootstrap realm enables brute-force detection (temporary lockout after 10
failed logins, growing to at most 15 minutes) and requires passwords of at least
12 characters that differ from the username and email. Keycloak imports the
realm only when it does not exist yet, so realms created by earlier releases keep
their settings. Apply both under **Realm settings → Security defenses** and
**Authentication → Policies** for existing installations.

## Install and verify the LAREX theme

The official Keycloak image loads the theme from a read-only JAR mount. Both wizard
modes and the release deployment ZIP include the theme, SHA-256 checksum, source
metadata, and installation guide. Stable releases also publish a standalone
`larex-keycloak-theme-<version>.jar` with GitHub provenance attestation.

Before starting bundled Keycloak, verify from the extracted bundle root:

```bash
(cd config/keycloak && sha256sum --check theme.jar.sha256)
bash scripts/verify-keycloak-theme.sh
```

On macOS use `shasum -a 256 --check`. The verification script requires the GitHub
CLI and checks the official release workflow on `main`; it fails if provenance
cannot be verified. Local development builds have no release attestation.

For external Keycloak, verify the same JAR, mount it read-only at
`/opt/keycloak/providers/larex_theme.jar` in **your existing Keycloak container**,
recreate that container, then select `keycloakify-larex` for Login and Email under
**Realm settings → Themes**. Existing realms need that selection even with bundled
Keycloak. Optimized deployments must include the JAR before their Keycloak build
step. The theme is tested with the bundled Keycloak version, currently 26.7.4.

The complete guide is included as `deployment/KEYCLOAK-THEME.md` in every bundle
and is available in the [source repository](https://github.com/ocr4all/larex/blob/main/deployment/KEYCLOAK-THEME.md).
It covers standalone downloads, verification, external Compose mounts, and rollback.
Checksums establish integrity; GitHub attestations establish release origin. Themes
still contain executable templates and browser code and require trust in LAREX.

## External Keycloak

When using `compose.prod.auth.external-keycloak.yaml`, LAREX does not run Keycloak for you.

You must import the bootstrap template manually or reproduce its settings in your existing realm:

- realm name must match `KEYCLOAK_REALM`
- frontend client must allow the LAREX redirect URL
- frontend client must allow the LAREX web origin
- backend service client must use `KEYCLOAK_ADMIN_CLIENT_SECRET`
- initial admin user and `GLOBAL_ADMIN` role must exist if you want the seeded bootstrap path
- the `delete_account` required action must be enabled under **Authentication → Required Actions**
- users who may delete themselves need the `account/delete-account` client role; assign it through a default composite role if every user should have it

Realm imports only create realms that do not exist yet. For an existing bundled or external realm, apply the two account-deletion settings above manually once during the upgrade.

## Upgrading to Keycloak 26.8.2 or Later

Keycloak 26.8.2 accepts Admin REST API calls only from tokens that carry the built-in `kc-admin-api` client scope. The upgrade adds that scope to Keycloak's own clients but not to `larex-backend-service`, so the backend's calls start failing with HTTP 401. Profiles, user lists, invitations, and the admin dashboard then fail to load, and the backend logs `NotAuthorizedException: HTTP 401 Unauthorized` from `UserService`.

Realms created from the current import templates already include the scope. For an existing realm, add it once:

1. Open the Keycloak admin console and select the LAREX realm.
2. Go to **Clients → larex-backend-service → Client scopes**.
3. Choose **Add client scope**, select `kc-admin-api`, and add it as **Default**.

Then restart the backend so it requests a new service-account token. The service account's `realm-management` roles do not change.

## Frontend Session Refresh

The frontend validates sessions before rendering protected pages. Expired sessions return to login; temporary authentication failures return 503 without deleting the session cookie. Successful refreshes update the browser's encrypted cookie, including during server rendering.

The supplied realms configure **Remember me** for seven days of inactivity and a 30-day maximum session lifetime. Automatic authentication recovery clears only the LAREX session, allowing Keycloak to restore it without another password prompt while the remembered session remains valid. The explicit **Log out** action ends the Keycloak session as well. Existing realms retain their own timeout settings; changing the import files does not update them.

Refresh requests have a 10-second timeout and are not automatically retried. Within one frontend process, concurrent requests share a token exchange; successful results remain available for five seconds for requests already carrying the previous cookie.

This coordination is process-local. Strict single-use refresh tokens across multiple frontend replicas require shared server-side session storage and refresh coordination, which this cookie-based implementation does not provide. Keycloak's [Revoke Refresh Token setting](https://www.keycloak.org/docs/latest/server_admin/#_timeouts) enables token rotation; check existing realm settings before changing this deployment topology. A lost refresh response can also require login when strict token rotation is enabled.

To test the auth flow locally, run `pnpm build` and then `node test/auth-flow.mjs` from `frontend`. The check starts an isolated application server with a local OAuth stub and exercises SSR cookies, expiration, concurrency, outages, and callback recovery.

## Externally Managed Users

Set `LAREX_USER_PROVISIONING_MODE=EXTERNALLY_MANAGED` when LDAP, Active Directory, or a single sign-on provider is authoritative for user lifecycle. Earlier releases called this mode `LDAP_MANAGED`; that value is still accepted.

In that mode:

- LAREX still lists users and audit history
- user creation is disabled
- setup-email flows are disabled
- enable/disable actions are blocked from LAREX

This keeps the backend service account least-privileged and avoids broad Keycloak admin roles.

## Institutional Directories (LDAP)

Configure LDAP or Active Directory under **User Federation** in the LAREX realm, map user attributes, and set the provisioning mode above if the directory owns user lifecycle. LAREX shows these users with the identity source **LDAP**.

See [LDAP Federation](https://www.keycloak.org/docs/latest/server_admin/#_ldap) in the Keycloak documentation.

## Single Sign-On Through an Identity Provider

LAREX does not talk to institutional identity providers directly. Keycloak acts as a broker: users sign in at their own provider, Keycloak links that sign-in to a Keycloak account, and LAREX only ever sees Keycloak tokens. No LAREX configuration change is needed beyond the optional provisioning mode.

Each provider gets an **alias** in Keycloak. The alias is part of the redirect URL the provider must allow, so choose it before registering LAREX at the provider:

```text
https://<KEYCLOAK_PUBLIC_HOST>/realms/<realm>/broker/<alias>/endpoint
```

### OpenID Connect Providers

This covers providers such as Microsoft Entra ID, Google Workspace, Okta, authentik, or another Keycloak.

1. Register a web application at the provider with the redirect URL above, and create a client secret.
2. In Keycloak, open the LAREX realm and go to **Identity Providers → OpenID Connect v1.0**.
3. Enter the alias, then paste the provider's discovery URL so Keycloak fills in the endpoints. For Entra ID this is `https://login.microsoftonline.com/<tenant-id>/v2.0/.well-known/openid-configuration`.
4. Enter the client ID and secret, set **Client authentication** to *Client secret sent as post*, and request the scopes `openid profile email`.
5. Turn on **Trust Email** only if the provider verifies email addresses.

### SAML Providers

This covers Shibboleth and other institutional SAML identity providers.

1. In Keycloak, go to **Identity Providers → SAML v2.0**, enter the alias, and import the provider's metadata URL.
2. Give the provider Keycloak's service-provider metadata from `https://<KEYCLOAK_PUBLIC_HOST>/realms/<realm>/broker/<alias>/endpoint/descriptor`.
3. Under the provider's **Mappers**, add *Attribute Importer* mappers for email (`urn:oid:0.9.2342.19200300.100.1.3`), first name (`urn:oid:2.5.4.42`), and last name (`urn:oid:2.5.4.4`). Use a persistent identifier such as `eduPersonPrincipalName` (`urn:oid:1.3.6.1.4.1.5923.1.1.1.6`) or a persistent NameID as the principal.

Keycloak configures one identity provider per entry. Federations with many member institutions need one entry per institution or a federation proxy in front of Keycloak.

### How LAREX Treats Single Sign-On Users

- The first sign-in creates a Keycloak account linked to the provider. If an account with the same email already exists, Keycloak asks the user to confirm the link.
- The admin user list shows these accounts with the identity source **SSO**.
- Administrators can enable or disable them. Disabling the Keycloak account blocks sign-in even though the provider still accepts the user.
- Setup emails are not offered, and the password option in **Settings → Security** is replaced by a note, because the password belongs to the provider.
- `GLOBAL_ADMIN` and `GLOBAL_CURATOR` remain Keycloak realm roles. Assign them in Keycloak or derive them from provider claims with identity provider mappers.
- Account deletion removes the Keycloak account, not the account at the provider. The next sign-in through the provider creates a new Keycloak account with a new LAREX user ID.

### Sign-On Only Deployments

To send users straight to the provider instead of the LAREX login page, open **Authentication → browser** flow, configure the **Identity Provider Redirector** step, and set its default provider to the alias. Also set `LAREX_USER_PROVISIONING_MODE=EXTERNALLY_MANAGED` so administrators cannot create local password accounts by accident.

See [Identity Brokering](https://www.keycloak.org/docs/latest/server_admin/#_identity_broker) in the Keycloak documentation for provider-specific options.
