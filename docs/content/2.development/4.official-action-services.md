# Official Action Services

Official processors run as isolated services and are not part of the default
development stack. The reusable `compose.actions.yaml` fragment adds them when
requested. Its `actions` profile starts every official processor; processor-specific
profiles start only selected services.

Currently shipped:

| Profile | Service | Processor |
| --- | --- | --- |
| `action-kraken` | `action-kraken-segmentation` | Kraken baseline segmentation |

## Start All Official Processors

```bash
task docker:actions:up
```

The first run creates `.env.actions` from
`deployment/env/.env.actions.example` and generates the shared HMAC secret. The
development backend automatically registers the Kraken definition globally.
Kraken admits one run at a time by default. Set `KRAKEN_MAX_CONCURRENT_RUNS` in
`.env.actions` when deliberately testing parallel processor capacity.

Check status and follow logs:

```bash
task docker:actions:ps
task docker:actions:logs
```

Stop the combined stack without deleting volumes:

```bash
task docker:actions:down
```

## Start Selected Processors

Use the individual profile when the catalog grows and only Kraken is needed:

```bash
scripts/bootstrap-env-secrets.sh actions
docker compose --env-file .env.actions \
  -f compose.yaml \
  -f compose.actions.yaml \
  --profile action-kraken \
  up -d --build
```

## Verify Reactive Results

Run **Kraken Segmentation** on multiple PAGE images. While the overall run remains
active, each completed page should receive PAGE XML, lose its processing animation
and page lock, and update in open project/editor views.

The processor is private to the `backend` Compose network. Inspect its health
without publishing a host port:

```bash
docker compose --env-file .env.actions \
  -f compose.yaml \
  -f compose.actions.yaml \
  --profile action-kraken \
  exec action-kraken-segmentation \
  python -c "import urllib.request; print(urllib.request.urlopen('http://localhost:9000/health').read().decode())"
```

## Add Another Official Processor

To extend the fragment:

1. Add a service based on `x-action-processor-defaults`.
2. Give it both `actions` and a unique processor profile.
3. Keep it on the private `backend` network and do not publish its port.
4. Add its HMAC secret and pinned image tag to `.env.actions.example` and the secret bootstrap.
5. Ship its Action definition under `deployment/actions/`.
6. Add the service to Compose validation and this catalog.

See [Official Action Services Deployment](/deployment/official-action-services)
for production configuration and security requirements.
