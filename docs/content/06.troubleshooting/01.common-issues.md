# Common Issues

Start with the symptom below. Keep the error message, affected workspace/project,
time, and run or job ID before changing configuration. Logs and status usually
identify the failing service without resetting stored data.

## First checks

For the repository's development stack:

```bash
docker compose ps -a
docker compose logs --tail=100 app frontend keycloak postgres
curl -s http://larex.localhost/api/health/backend
```

For production, use the commands generated in your deployment bundle so all selected
Compose fragments and environment files are included. Repository users can run
`task docker:prod:ps` and `task docker:prod:logs` for the default bundled-Keycloak
topology. Add the matching Actions or docs overlay when inspecting optional services.

The frontend health route returns a JSON `status`; inspect that value as well as
the HTTP status. A direct unauthenticated request to `/actuator/health` may return
401 because the backend protects it. The frontend reports a reachable protected
Actuator endpoint as `UP`; this alone does not verify sign-in or every database operation.

| Symptom | Start here |
| --- | --- |
| Hostname does not load, or proxy returns 502 | [Routing and ports](#routing-and-port-conflicts) |
| Login loops, callback error, or 401 | [Authentication](#login-and-keycloak) |
| Startup fails on database or Flyway | [Database](#database-and-migrations) |
| Upload, import, or download fails | [Files and storage](#uploads-imports-and-downloads) |
| Page is locked or changes do not appear | [Editor and realtime](#editor-locks-and-realtime-updates) |
| Action cannot start or finishes with issues | [Actions](#action-failures) |
| Build or reload fails | [Development tooling](#development-builds-and-hot-reload) |

## Routing and port conflicts

The development stack uses Traefik on port `80`. The local production-like stack
uses Nginx on that same port. Stop one stack before starting the other.

| Development endpoint | Purpose |
| --- | --- |
| `http://larex.localhost` | Application and sign-in |
| `http://api.localhost` or `localhost:8080` | Backend; API paths start with `/api/v1` |
| `http://keycloak.localhost` | Keycloak; development does not publish port `8090` |
| `http://mail.localhost` or `localhost:8025` | Mailpit inbox |
| `localhost:5432` | Application PostgreSQL |
| `localhost:3000` | Direct frontend dev server |

Production defaults publish frontend on `127.0.0.1:3000` and bundled Keycloak on
`127.0.0.1:8090`. These are HTTP upstream ports for your TLS proxy, not the public
issuer URLs. External Keycloak has its own existing endpoint.

Identify the owner of a conflicting port, then stop that application normally:

```bash
# macOS/Linux
lsof -nP -iTCP:80 -sTCP:LISTEN
lsof -nP -iTCP:3000 -sTCP:LISTEN

# Windows
netstat -ano | findstr :3000
```

For 502 errors, inspect the upstream service's logs and verify its configured
container name and port. For native service development, follow the explicit
[host networking configuration](/development/local-setup#configure-host-networking).

## Login and Keycloak

1. Open the configured application hostname, normally `http://larex.localhost` in
   development. The realm's redirect URIs must include that exact origin and callback.
2. Check Keycloak discovery in development:

   ```bash
   curl -f http://keycloak.localhost/realms/larex-dev/.well-known/openid-configuration
   docker compose logs --tail=100 keycloak keycloak-postgres
   ```

3. Verify the issuer, realm, frontend client secret, backend service client secret,
   and public/internal Keycloak URLs agree with [Keycloak Setup](/deployment/keycloak-setup).
4. In production, inspect the container health status. Bundled Keycloak's readiness
   check uses its internal management port `9000`; `/health/ready` is not served
   from the published application port `8090`.
5. After editing production env values, recreate the affected services using the
   same Compose stack. A container restart alone does not apply new environment values.

Realm imports initialize a missing realm. Editing an import JSON file does not
update an existing realm. Apply client, role, theme, and account-deletion changes
in the Keycloak admin console for an existing installation.

Keycloak users and realms live in `keycloak_postgres_data`. Deleting a runtime
volume does not reset them. Preserve that database when recovering login problems.
For session expiry, refresh failures, and multiple frontend replicas, see
[session refresh](/deployment/keycloak-setup#frontend-session-refresh).

## Database and migrations

Check readiness and credentials before changing data:

```bash
docker compose ps postgres
docker compose logs --tail=100 postgres app
docker compose exec postgres pg_isready -U larex -d larex_backend
task db:shell
```

The development defaults are database `larex_backend`, user `larex`, and password
`larex_dev_pw`. Native backend processes need `localhost:5432`; Docker uses
`postgres:5432`. Production credentials come from the selected environment file.
Changing initialization passwords in Compose does not rewrite an existing database's users.

For Flyway errors, capture the migration name, checksum, and database version.
Use the application version that owns that schema and follow the release's
migration instructions. Take a verified backup before recovery. Do not remove
migration history or edit applied migrations to suppress a validation error.

Only when deliberately rebuilding a disposable development instance may you use
`task docker:down:clean`: it removes named development volumes, including both
application and Keycloak databases, Gradle cache, and portable backup volume.
It preserves the bind-mounted `backend/uploads` files, so this is not a complete
filesystem reset. Never use it as production recovery.

## Uploads, imports, and downloads

| Symptom | Check and recovery |
| --- | --- |
| HTTP 413 | Check the reverse proxy's request size, Spring multipart limits, and the relevant upload/archive limit. Action defaults are 100 MiB per file and 480 MiB per request. |
| Upload/import stops | Inspect job details, workspace free quota, backend disk space, and writable upload/temp directories. PDF rendering and archive extraction have separate limits. |
| IIIF source returns 429/503 | Inspect the remote response and `Retry-After`; LAREX applies pacing and cooldown. Admin IIIF settings can override deployment pacing. |
| Server import cannot see a folder | Mount it into the backend, configure its container path in `LAREX_IMPORT_ALLOWED_PATHS`, and verify read permission. Host paths alone are insufficient. |
| Export is queued or fails before generation | Check the per-user/global queue limits and free space in `LAREX_PROJECT_EXPORT_DIR`; generation requires 5 GiB free by default. |
| Finished export is unavailable | Temporary project export archives expire after 24 hours by default. Generate a new export. Durable Action outputs and releases have their own retention. |
| Large download truncates | Check proxy timeouts and the backend async response timeout; inspect the export job status before retrying. |
| Backend fails its storage startup check | Confirm persistent mounts, ownership, and SELinux labels. Keep shipped `:Z` labels on private bind mounts. |

See [Environment Variables](/deployment/environment-vars) for exact limits and
[backup recovery](/deployment/production-deploy#verify-and-restore) for restoring data.
Check disk use with `docker system df` and `docker stats`. Inspect volumes before
removing anything; unused volumes can still contain a database or your only backup.

## Editor locks and realtime updates

An Action page lock, project lock, workflow lock, and another user's active edit
lease have different causes. Inspect the displayed owner and message before acting.
For an Action lock, open the owning run and inspect its progress. Curators/admins
can force-unlock an Action page; this cancels the owning run and releases all of
that run's locks. It does not terminate the external processor process.

If saved or imported changes are slow to appear, confirm the proxy supports WebSocket
upgrades and inspect the browser's network errors. The backend notification bridge
and frontend must share the same bridge secret. Reload after reconnecting and
inspect the saved PAGE XML before repeating edits. Workspace search indexing can
lag behind a successful save or Action import.

## Action failures

Follow the run details from dispatch to input download, heartbeat, and result import:

| Symptom | Check and recovery |
| --- | --- |
| Action absent or disabled | Definition enabled, workspace availability, explicit workspace/project activation, execution role, target support, and required files. Global availability still requires workspace activation. |
| Endpoint test fails | Signed preflight checks identity, HMAC secret, protocol, and capabilities; a health-only test proves reachability. Check origin policy and both secret values. |
| Dispatch works but input cannot download | Callback base must include `/api/v1` and be reachable from the processor. Check processor callback-origin allowlist, DNS, TLS, and forwarding of the bearer header. |
| Dynamic model selector is empty | Check parameter discovery endpoint, model publication, and provider logs. Refresh the choices after fixing the service. |
| Run stops after a long computation | Check heartbeats, processor resource limits, and its subprocess timeout. Use cancellation-aware SDK work helpers for lengthy work. |
| Result rejected | Read the sanitized backend detail in processor logs: output declarations, page IDs, XML/image validity, target IDs, quota, and multipart limits. |
| Completed with issues | Open the page report; successful imports remain. Retry failed/unfinished pages after fixing the cause. Warnings alone do not create retryable pages. |
| Cancellation does not finish | Processor cancellation is cooperative; the default watchdog is five minutes. Force cancel revokes callbacks and releases locks immediately. |

See [Run Reports](/actions/run-reports), [Result Import](/actions/result-import),
and [Security and Deployment](/actions/security-deployment).

## Development builds and hot reload

Preserve committed lockfiles when reinstalling dependencies:

```bash
cd frontend
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm build
```

If generated Nuxt output is stale, remove only `.nuxt` and `.output` and run the
install/build again. For Docker, source mounts are already configured; rebuild
images after Dockerfile or dependency changes with `task docker:up:build`.

For backend failures, use Java 25 and inspect Gradle's original exception:

```bash
cd backend
./gradlew test --stacktrace
```

Integration tests use PostgreSQL Testcontainers and require Docker. Switching to
an in-memory database changes the environment under test. For IDE debugging, run
`./gradlew bootRun --debug-jvm` and attach on `5005`; the JVM waits for attachment.

## TLS certificates

The development Traefik configuration uses HTTP. Production bundled Nginx loads
operator-provided certificates and has no ACME issuer or renewal job. Check the
selected Nginx template, certificate filenames, permissions, expiry, and proxy
logs. Renew certificates with your certificate provider, then reload/recreate
the proxy as appropriate. Restarting Traefik does not renew these certificates.

## Reporting a problem

Include the LAREX version, deployment mode, browser, exact reproduction steps,
expected/actual behavior, relevant job/run ID, and sanitized recent logs. Include
which Compose overlays are active. Remove tokens, secrets, personal data, and
private document contents from reports.

```bash
task ver
docker compose ps -a
docker compose logs --tail=100 app frontend
```

Search the [issue tracker](https://github.com/OCR4all/larex/issues) for the same
error before opening a new report.
