# Processor SDK

The recommended way to build a processor is the Python package [`larex-action-sdk`](https://github.com/OCR4all/larex-action-sdk). SDK `0.13` provides custom durable files, authenticated processor preflight and parameter-value discovery, target-aware input requirements, and detailed result-callback errors. Custom files also require a LAREX server advertising `capabilities.customFileResults`. The SDK requires Python `>=3.11` and provides a `fastapi` extra.

## Install

For a FastAPI processor:

```bash
uv add "larex-action-sdk[fastapi]>=0.12.0,<0.13"
```

For framework-neutral usage:

```bash
uv add "larex-action-sdk>=0.12.0,<0.13"
```

## FastAPI Quickstart

```python
import os

from larex_actions import ActionContext
from larex_actions.fastapi import create_larex_action_app


async def process(ctx: ActionContext) -> None:
    action_input = await ctx.pull_input()
    for page in action_input.pages:
        async with ctx.step(f"Processing {page.name}", progress_percent=25):
            await ctx.check_cancelled()
            results = ctx.result_builder()
            if page.xml:
                xml_bytes = await ctx.download_bytes(page.xml[0])
                results.add_xml_bytes(
                    page_id=page.id,
                    content=xml_bytes,
                    file_name=f"{page.name}-processed.xml",
                )
            await ctx.submit_page_results(page.id, results, f"Imported {page.name}")

    await ctx.complete(message="Done")


app = create_larex_action_app(
    processor_id="my-processor",
    dispatch_secret=os.environ["LAREX_DISPATCH_HMAC_SECRET"],
    handler=process,
)
```

The FastAPI adapter exposes:

- `/dispatch`
- `/preflight`
- `/health`

`/preflight` accepts a signed LAREX request and returns the processor identity,
Action protocol version, and processor capabilities. Add it as
`endpoint.preflightUrl` so the admin endpoint test verifies authentication and
compatibility rather than only checking liveness.

Set `LAREX_ACTION_ROUTE_PREFIXES` when a reverse proxy preserves a path prefix:

```bash
LAREX_ACTION_ROUTE_PREFIXES=/kraken,/ocr
```

With that setting, the processor also exposes `/kraken/dispatch`,
`/kraken/preflight`, `/kraken/health`, and equivalent `/ocr/*` routes. Do not
strip the prefix before the request reaches the processor, because the signature
includes the path.

## What The SDK Handles

The SDK helps processors with:

- verifying `X-LAREX-Action-*` HMAC dispatch headers
- parsing typed dispatch payloads
- constructing clients from dispatch payloads
- pulling input metadata
- downloading image/XML files
- sending heartbeats and progress
- checking cooperative cancellation
- running cancellable subprocesses
- building result manifests
- uploading result files
- submitting and acknowledging individual page results
- avoiding secret leakage in model representations

## Input Pull

After dispatch, processors pull input from the callback URL in the dispatch payload:

```python
action_input = await ctx.pull_input()
```

The input contains:

- `protocolVersion`
- `runId`
- `processorKey`
- `projectId`
- resolved processor parameters
- pages in processor scope
- page image file descriptors
- page XML file descriptors
- target selection
- resolved input requirements
- image variant selection
- cancellation state
- negotiated capabilities, including `incrementalPageResults` and `customFileResults`

Files are not embedded in the input response. The processor downloads each file through its `downloadUrl`.

## Dynamic Parameter Values

Register processor-global synchronous or asynchronous providers with the FastAPI
adapter. Returned values are strict allowlists and may carry friendly labels:

```python
from larex_actions import ParameterChoice

app = create_larex_action_app(
    processor_id="my-processor",
    dispatch_secret=secret,
    handler=process,
    parameter_value_providers={
        "models": lambda: [
            ParameterChoice(value="model-a", label="Model A"),
            ParameterChoice(value="model-b", label="Model B"),
        ]
    },
)
```

The SDK exposes authenticated `/parameter-values` routes, including configured
route prefixes, and advertises `capabilities.parameterValueDiscovery`. Configure
the matching URL and provider name in the Action YAML.

## Target-Aware Runs

LAREX can dispatch `PAGE`, `REGION`, and `TEXT_LINE` targets.

```python
payload_target = ctx.payload.target
action_input = await ctx.pull_input()
input_target = action_input.target
```

For region and textline targets, processors receive full page images/XML according to the Action definition's effective input levels. The Python SDK exposes the resolved `NONE`, `OPTIONAL`, or `REQUIRED` levels as `input_requirements` (serialized as `inputRequirements`) for images and XML. Pages that do not satisfy required inputs are excluded before dispatch. The target metadata contains selected region or textline IDs. The processor is responsible for resolving geometry from PAGE XML when it wants to crop, mask, pad, deskew, or process a subset.

Return normal PAGE XML. LAREX imports only the selected region/textline scope when the run target is scoped.

## Heartbeats And Cancellation

Cancellation is cooperative. LAREX marks a run as cancellation requested, and the processor observes that state through heartbeat responses.

Use:

```python
await ctx.check_cancelled()
```

or:

```python
await ctx.heartbeat(progress_percent=50, status_message="Halfway", raise_on_cancel=True)
```

Guidelines:

- Check cancellation at safe interruption points.
- Do not call cancellation checks in a tight inner loop without pacing.
- Send progress updates that help users understand long-running work.
- On cancellation, stop work and acknowledge cancellation instead of uploading results.

For external commands, use the SDK subprocess helper when possible so cancellation can terminate the child process cleanly before escalating.

## Framework-Neutral Verification

Use `DispatchVerifier` when the processor is not a FastAPI app:

```python
from larex_actions import DispatchVerifier

payload = DispatchVerifier(
    processor_id="my-processor",
    dispatch_secret=secret,
).verify(
    method=request_method,
    path_and_query=request_path_and_query,
    headers=request_headers,
    body=request_body,
)
```

Then pass the verified payload into your queue or worker system and use `ActionClient.from_dispatch(payload)` in async workers.

This is useful when:

- dispatch should enqueue work and return quickly
- the actual processor runs in a worker pool
- the HTTP framework is not FastAPI
- GPU work is scheduled by another runtime

## Result Builder

Use the result builder for files LAREX should import:

```python
results = ctx.result_builder()
results.add_xml_bytes(
    page_id=page.id,
    content=xml_bytes,
    file_name=f"{page.name}-processed.xml",
)
results.add_image_bytes(
    page_id=page.id,
    content=image_bytes,
    variant="processed",
    file_name=f"{page.name}-processed.png",
)
await ctx.complete(results, "Processed pages")
```

That remains the backward-compatible bulk API. For reactive processors, create a fresh builder per page and submit it as soon as that page succeeds:

```python
for page in action_input.pages:
    await ctx.check_cancelled()
    results = ctx.result_builder()
    # Add this page's XML and/or images when the processor produced output.
    await ctx.submit_page_results(page.id, results, f"Imported {page.name}")

# Final acknowledgement contains no files.
await ctx.complete(message="Processed pages")
```

The SDK refuses `submit_page_results` if the dispatch did not advertise `capabilities.incrementalPageResults`. This prevents an incremental processor from silently running against an older LAREX server. Do not reuse one result builder across pages.

### Submit a Page Without a Result

Sometimes processing succeeds but intentionally produces no output—for example, when a page contains no eligible regions or no entities pass a confidence threshold. The page must still be acknowledged. Create an empty result builder and submit it for that page:

```python
results = ctx.result_builder()
await ctx.submit_page_results(
    page.id,
    results,
    message=f"Skipped {page.name}: no eligible content",
)
```

An empty page submission is a successful acknowledgement, not a failure. LAREX counts the page toward run progress and, for Actions using `locking.mode: PAGES`, releases that page's lock. It does not create or modify XML, images, or custom files.

Do not simply `continue` without calling `submit_page_results`. An incremental run can only be completed after every page in `action_input.pages` has been submitted, whether with files or with an empty builder. Once every page is acknowledged, finish the run normally:

```python
await ctx.complete(message="Processing complete")
```

The Action YAML must allow every uploaded output type. If the definition does not declare image output, image results are rejected. If it does not declare XML output, XML results are rejected.

For a postprocessing result, check `ctx.capabilities.custom_file_results` before starting work and use `add_file_bytes` or `add_file_path`. Pass a page ID for incremental submissions; omit it from a final/bulk builder for a project-level file. The client raises `CustomFileResultsUnsupported` before uploading to an older server.

When LAREX rejects a result callback, current SDK releases raise
`ResultSubmissionError`, an `httpx.HTTPStatusError` subtype whose message includes
a bounded and sanitized backend response detail. Let the FastAPI adapter log this
exception, or include it in your own worker logs, to surface the actual manifest,
quota, or import validation failure.

## Environment Variables

Common processor variables:

| Variable | Use |
| --- | --- |
| `LAREX_DISPATCH_HMAC_SECRET` | Shared HMAC secret copied from LAREX endpoint secret creation/rotation. |
| `LAREX_PROCESSOR_ID` | Processor ID expected in dispatch headers, when the processor supports env-based configuration. |
| `LAREX_ALLOWED_CALLBACK_ORIGINS` | Comma-separated callback origins accepted by the SDK. |
| `LAREX_ACTION_ROUTE_PREFIXES` | Additional route prefixes for `/dispatch`, `/preflight`, and health routes. |

Processor-specific implementations may add their own variables for model paths, devices, precision, timeouts, or output variants.
