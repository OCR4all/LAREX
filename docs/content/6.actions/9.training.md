# Dataset Model Training

Training Actions reuse the normal Action dispatch, authentication, queue,
heartbeat, cancellation, logging, and result callbacks. They differ from
processing Actions in two important ways: their resource is one dataset instead
of one project, and the Action publishes its model directly instead of uploading
an output artifact to LAREX.

```yaml
version: 1
id: example-training
name: Example Training
kind: TRAINING
category: LAYOUT
targets: [PAGE]
locking:
  mode: NONE
inputs:
  images:
    level: required
  xml:
    level: required
training:
  splits:
    TRAIN: required
    VAL: optional
    TEST: none
```

Training definitions cannot declare `outputs`. `TRAIN` is required in V1;
definitions may accept `VAL` or `TEST` as optional/required/none, although the
Kraken POC intentionally does not accept TEST.

## Snapshot lifecycle

When a user starts training, LAREX resolves the dataset's LINK or COPY material
and selected image variant, reserves workspace quota, and copies one image plus
one PAGE XML file per input into run-owned storage. Checksums and source metadata
remain in run history. The files themselves are removed after every terminal
path, including completion, processor failure, cancellation, dispatch failure,
and watchdog timeout.

The Action receives dataset item IDs as input page IDs, together with each
item's `sourcePageId` and split. Active training runs create no page/project
locks and no Action output draft. Retrying an exact snapshot is intentionally
unsupported; starting again creates a new snapshot.

## Model ownership

LAREX considers a training run complete only after the Action reports completion.
The Action is responsible for validating and atomically publishing its model to
operator-managed storage first. LAREX V1 does not register, download, delete,
or retain model files.
