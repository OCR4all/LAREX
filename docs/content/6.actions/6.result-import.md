# Result Import

Processors upload results to LAREX through the per-run result callback. LAREX validates the manifest and files before importing anything into project storage.

Protocol version `1` supports both the original one-shot upload and capability-negotiated incremental page uploads. Dispatch and input payloads advertise `capabilities.incrementalPageResults: true` and `capabilities.customFileResults: true` when supported.

## Result Manifest

The result upload contains a manifest and multipart file parts.

```json
{
  "protocolVersion": 1,
  "status": "completed",
  "message": "Processed 3 pages",
  "files": [
    {
      "fieldName": "page-1-xml",
      "pageId": "page-id",
      "type": "xml",
      "fileName": "page-1.xml"
    }
  ]
}
```

| Field | Meaning |
| --- | --- |
| `protocolVersion` | Optional for backward compatibility; when present it must be `1`. |
| `status` | Must be `running`, `completed`, or `failed`. |
| `pageId` | Required for a `running` incremental page result; omitted for bulk/final completion. |
| `message` | User/admin-visible progress or terminal message, limited by LAREX. |
| `files` | Files to import. |
| `patches` | No longer supported; return PAGE XML as XML files instead. |

Each file entry needs:

| Field | Meaning |
| --- | --- |
| `fieldName` | Multipart field containing the file. Must be unique and non-blank. |
| `pageId` | Required for XML/image and incremental files. A final/bulk `file` may omit it for a project-level result. |
| `type` | `xml`, `image`, or `file`. |
| `variant` | Optional output image variant. |
| `fileName` | Optional preferred stored file name. |

## Incremental Page Results

A reactive processor sends one `running` manifest per page. Every file in that upload must carry the same `pageId` as the manifest. A manifest with no files is a valid acknowledgement for a page that produced no output.

Each accepted page is imported in its own transaction. After commit, LAREX records the acknowledgement, updates the aggregate result summary and progress, releases a `PAGES` lock for that page, and publishes a targeted UI event. `PROJECT` locks remain effective until terminal completion. Duplicate submissions for the same run/page return the earlier success without importing or versioning files again.

### Pages Without Output

If processing succeeds but a page has nothing to import, submit an incremental result manifest with the page ID and an empty `files` array:

```json
{
  "protocolVersion": 1,
  "status": "running",
  "pageId": "page-id",
  "message": "Skipped: no eligible content",
  "files": []
}
```

Send this JSON as the multipart `manifest` part without any file parts. With the Python SDK, the equivalent is:

```python
results = ctx.result_builder()
await ctx.submit_page_results(page.id, results, "Skipped: no eligible content")
```

This acknowledges only the specified page. It does not modify project files, but it counts toward progress and releases a page-level lock. Processors must submit either output files or an empty acknowledgement for every page in the run; omitting a page prevents terminal completion.

After every run page has been acknowledged, send `completed` with no files and no `pageId`. LAREX then sets progress to 100%, expires the run secret, releases remaining/project locks, and makes the processor queue slot available. Incremental and bulk uploads cannot be mixed.

If a later page fails, send `failed`. Previously committed pages remain imported; the run fails and remaining locks are released.

## Limits

Default server limits:

| Limit | Default |
| --- | --- |
| Maximum result files | `500` |
| Maximum single file size | `536870912` bytes |
| Maximum total upload size | `2147483648` bytes |

These are configured under `larex.actions.results`.

## Output Type Validation

LAREX checks the Action definition before accepting output:

- XML files require `outputs.xml.enabled: true`.
- Image files require `outputs.images.enabled: true`.
- Custom files require `outputs.files.enabled: true`.
- Result `pageId` must be part of the run scope.
- Multipart field names must exist and be unique.
- Image files must have a valid content type and be decodable.
- XML files must be valid enough for the import path and target merge.

If validation fails, the run fails and LAREX records the error.

## Durable Custom Files

Custom `file` results accept any MIME type and fall back to `application/octet-stream`. They are stored separately from page XML/images and published as exactly one project output only after the run completes successfully. A failed or cancelled run removes its partial custom files; an empty successful run creates no output.

Completed outputs remain available independently of Action run-history pruning. Workspace members can download one file or the complete output as a ZIP. Curators, workspace owners, and global admins can share or delete outputs. The project retention setting is snapshotted when the run starts; `Never` is the default. Public shares always download the complete ZIP and cannot outlive automatic deletion.

Filenames are sanitized and ZIP collisions receive deterministic numeric suffixes. Version 1 stores a flat collection, so processors should return directory-shaped formats as an archive.

## PAGE-Targeted XML

For `PAGE` target runs, returned XML applies to the whole result page.

Use this for:

- OCR/HTR output for full pages
- full PAGE XML cleanup
- full-page layout segmentation

The Action output mode controls whether XML is upserted or appended.

## Region-Targeted XML

For `REGION` target runs, LAREX imports only the selected region scope from the returned PAGE XML.

The processor should return normal PAGE XML for the page. LAREX finds the selected region IDs and replaces that target scope in the existing page XML. Results outside the selected region scope are ignored for the scoped merge.

Use this when a processor can improve one or more selected regions without overwriting unrelated page work.

## Textline-Targeted XML

For `TEXT_LINE` target runs, LAREX imports only selected textlines from the returned PAGE XML.

Use this for targeted recognition or correction workflows where a user chooses specific lines in the editor.

## Image Results

Image results are stored as page images.

Variant behavior:

- If the result file declares `variant`, LAREX uses it after validation.
- If no result variant is declared, LAREX uses the fallback variant from import logic.
- Variant names must match `[a-zA-Z0-9][a-zA-Z0-9._-]{0,63}`.

The Action definition must declare image outputs and the intended default variant. Use descriptive variants such as `kraken-lines`, `deskewed`, or `action-copy`.

## Terminal Runs

After a run reaches `COMPLETED`, `FAILED`, or `CANCELLED`, later callbacks cannot change it and its run secret expires. An in-flight duplicate result request may receive the already-terminal run response; processors should otherwise treat callback failures after terminal state as final and stop retrying.

## Search And UI Refresh

After each page import, LAREX immediately refreshes the affected overview/editor page through its realtime bridge and schedules related index/search updates. Polling remains a fallback for reconnections and missed events. Recently imported XML may take a short time to appear in workspace search while indexing finishes.
