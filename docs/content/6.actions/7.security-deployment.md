# Security and Deployment

Actions deliberately separate LAREX from processor execution. Processors receive signed dispatch requests and per-run callback credentials, not database access or permanent storage credentials.

## Dispatch Authentication

External endpoints must use HMAC dispatch authentication.

```yaml
endpoint:
  url: https://processor.example.org/dispatch
  auth:
    type: hmac
    secretRef: processor-v1
```

LAREX signs dispatch requests with the secret behind `secretRef`. The processor verifies the request before doing work.

## HMAC Headers

Signed dispatch requests include:

| Header | Meaning |
| --- | --- |
| `X-LAREX-Action-Auth` | Authentication scheme, currently `hmac-sha256;v=1`. |
| `X-LAREX-Action-Processor` | Processor ID. |
| `X-LAREX-Action-Run-Id` | LAREX run ID. |
| `X-LAREX-Action-Timestamp` | Dispatch timestamp. |
| `X-LAREX-Action-Nonce` | Opaque nonce. |
| `X-LAREX-Action-Body-SHA256` | Base64url SHA-256 of the dispatch body. |
| `X-LAREX-Action-Signature` | `v1=` plus base64url HMAC SHA-256 signature. |

Canonical string:

```text
larex-action-dispatch-v1
POST
<path-and-query>
<run-id>
<processor-id>
<timestamp>
<nonce>
<body-sha256-base64url>
```

Use the SDK verifier instead of implementing this by hand when possible.

## Dispatch Payload Secrets

The dispatch payload includes a per-run `secret`. Processors use it as a bearer token for:

- pulling input
- downloading files
- sending heartbeats
- uploading results

This run secret is separate from the endpoint HMAC secret. The endpoint HMAC secret authenticates dispatch. The run secret authorizes callbacks for one run.

## Endpoint URL Policy

Endpoint URLs must:

- use HTTP or HTTPS
- include a host
- not include credentials
- not include fragments
- pass the configured HTTPS/local policy
- match `LAREX_ACTIONS_ENDPOINT_ALLOWED_ORIGINS` when an allowlist is configured

Defaults:

| Setting | Default |
| --- | --- |
| `LAREX_ACTIONS_ENDPOINT_REQUIRE_HTTPS` | `true` |
| `LAREX_ACTIONS_ENDPOINT_ALLOW_INSECURE_LOCAL` | `true` |
| `LAREX_ACTIONS_ENDPOINT_ALLOWED_ORIGINS` | empty |

Local/private endpoints include `localhost`, `.localhost`, `.local`, hosts without dots, loopback, private IPv4 ranges, and link-local IPv6.

## Public Callback Base URL

Processors call back into LAREX through URLs built from the public Action base URL.

Relevant settings:

| Setting | Purpose |
| --- | --- |
| `LAREX_ACTIONS_PUBLIC_BASE_URL` | Explicit public base URL for Action callbacks. |
| `LAREX_ACTIONS_PUBLIC_BASE_URL_ALLOWED_ORIGINS` | Allowed callback origins. Defaults from `cors.allowed-origin`. |
| `LAREX_ACTIONS_PUBLIC_BASE_URL_REQUIRE_HTTPS` | Require HTTPS for non-local callback URLs. Defaults to `true`. |
| `LAREX_ACTION_RESULT_MAX_FILE_BYTES` | Maximum individual result upload; defaults to 100 MiB. |
| `LAREX_ACTION_RESULT_MAX_TOTAL_BYTES` | Maximum multipart callback and aggregate result upload; defaults to 480 MiB. |

Set `LAREX_ACTIONS_PUBLIC_BASE_URL` when processors run outside the Docker network and cannot reach the internal backend URL.

## SDK Callback Origin Allowlist

Processors should restrict which LAREX origins they accept through:

```bash
LAREX_ALLOWED_CALLBACK_ORIGINS=https://larex.example.org
```

This protects processors from following callback URLs from unexpected origins.

## Reverse Proxy Path Prefixes

If a processor is published behind a path prefix, preserve the prefix all the way to the processor.

```bash
LAREX_ACTION_ROUTE_PREFIXES=/kraken
```

Action definition:

```yaml
endpoint:
  url: https://processors.example.org/kraken/dispatch
  healthUrl: https://processors.example.org/kraken/health
```

Do not strip `/kraken` before the request reaches the processor. The dispatch signature includes the path and query that the processor verifies.

## Secret Rotation

Recommended rotation flow:

1. Create or rotate the endpoint secret in LAREX.
2. Copy the one-time revealed value into the processor environment.
3. Restart or reload the processor.
4. Test the endpoint from Admin -> Actions.
5. Run a small test Action.

Use versioned secret refs such as `ocr-processor-v1` when you need blue/green rotation between processor deployments.

## Timeouts And Retention

Defaults:

| Setting | Default |
| --- | --- |
| Dispatch attempts | `3` |
| Dispatch retry backoff | `3000` ms |
| Dispatch timeout watchdog | `5` minutes |
| Heartbeat timeout watchdog | `30` minutes |
| Terminal run retention | `30` days |

Processors should heartbeat during long work and use clear status messages so users can distinguish slow processing from a stuck run.

## Production Checklist

- Use HTTPS for external processor endpoints.
- Use HMAC authentication for all external processors.
- Store endpoint secrets outside source control.
- Set callback origin allowlists on processors.
- Configure public callback base URL when processors run outside the app network.

For supported processors on the same host, use the hardened, internal-only
`compose.actions.yaml` fragment described in [Official Action Services](/deployment/official-action-services).
- Preserve reverse-proxy path prefixes used in endpoint URLs.
- Set result file limits appropriate for your data.
- Monitor failed dispatches, heartbeat timeouts, and result validation failures.
