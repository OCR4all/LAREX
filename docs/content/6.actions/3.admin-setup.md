# Admin Setup

Global administrators manage LAREX Actions from the admin area. The admin workflow has four parts:

1. Create or rotate endpoint secrets.
2. Register and validate the Action YAML definition.
3. Decide where the Action is available.
4. Monitor runs, failures, and audit history.

## Endpoint Secrets

Most processors should use HMAC dispatch authentication. Create an endpoint secret before saving a definition that references it.

1. Open **Admin -> Actions**.
2. Open **Endpoint Secrets**.
3. Create a secret with a stable `secretRef`, such as `kraken-segmentation-v1`.
4. Copy the one-time revealed value.
5. Set that value in the processor environment as `LAREX_DISPATCH_HMAC_SECRET`.

LAREX can resolve endpoint secrets from:

- the admin-managed database-backed secret store
- `larex.actions.endpoint-secrets.<secretRef>`
- `larex.actions.endpoint-secrets[<secretRef>]`
- `LAREX_ACTION_ENDPOINT_SECRET_<NORMALIZED_REF>`
- `LAREX_ACTIONS_ENDPOINT_SECRETS_<NORMALIZED_REF>`

Database-backed endpoint secrets require `LAREX_ACTION_ENDPOINT_SECRET_ENCRYPTION_KEY`.

## Register A Definition

Open **Admin -> Actions** and create a processor definition from YAML.

The editor validates:

- YAML syntax
- unknown fields
- required fields
- enum values
- endpoint URL policy
- secret availability
- input/output compatibility
- parameter defaults, numeric ranges, and static/dynamic allowed-value declarations
- concurrency limits
- duplicate processor IDs

The preview shows the parsed name, processor key, endpoint, timeout, role, lock mode, category, targets, inputs, outputs, and parameters.

See [YAML Reference](/actions/yaml-reference) for the complete schema.

## Test The Endpoint

Use the admin endpoint test before assigning a processor to users.

LAREX tests:

- `endpoint.preflightUrl` with a signed `POST` when `preflightUrl` is configured;
  the response must confirm the configured processor ID, Action protocol version,
  and required capabilities, including parameter-value discovery when used
- `endpoint.healthUrl` with `GET` when no preflight URL is configured
- `endpoint.url` with `HEAD` when neither test URL is configured

The preflight uses the same endpoint HMAC secret as real dispatches, so it detects
missing or mismatched secrets before users start a run. All variants use the same
endpoint origin policy as definition validation. The health/`HEAD` fallback checks
reachability only.

## Availability And Assignment

Definitions have two layers of availability:

| Layer | Meaning |
| --- | --- |
| Enabled | The definition can be used at all. Disabled definitions cannot run. |
| Global availability | The definition is generally available without a workspace-specific availability record. |

Workspace/project assignment decides where users see the Action. Availability can be global, workspace-specific, workspace-default, or project-specific depending on the admin and curator workflow.

If a user cannot see an Action, check:

- definition enabled state
- global or workspace availability
- project assignment
- user workspace role
- `access.execute`
- target support
- project lock state

## Execution Roles

| `access.execute` | Who can run |
| --- | --- |
| `EDITOR` | Any user with workspace access. |
| `CURATOR` | Users who can manage projects in the workspace. |

Default is `CURATOR`.

## Locking

| `locking.mode` | Behavior |
| --- | --- |
| `PAGES` | Locks affected pages while the run is active. |
| `PROJECT` | Locks the project while the run is active. |

Use `PAGES` for most processors. Use `PROJECT` only when the processor depends on or mutates project-wide state.

## Concurrency

Definitions can limit active runs:

```yaml
concurrency:
  maxActiveRuns: 1
  scope: PROJECT
```

| Scope | Counts active runs across |
| --- | --- |
| `PROJECT` | Same Action and project. |
| `WORKSPACE` | Same Action and workspace. |
| `GLOBAL` | Same Action across the instance. |

Default behavior is one active run per Action/project. When a limit is reached, users may be offered a queue option.

## Monitor Runs

Admin run views show recent runs, active runs, queue state, logs, result summaries, errors, cancellation, and duration. Use them to answer:

- Is the processor reachable?
- Are runs timing out before heartbeat?
- Are result uploads failing validation?
- Is one workspace filling the queue?
- Are users cancelling runs or retrying failures?

Terminal run history can be cleared from user-facing views, while admin history and audit records should be treated as operational evidence.

## Development Mock Processor

The local stack includes a mock processor service for testing the full Action path.

Default local values:

| Setting | Value |
| --- | --- |
| Processor ID | `mock-image-copy` |
| Endpoint URL | `http://mock-action-processor:9000/dispatch` |
| Health URL | `http://mock-action-processor:9000/health` |
| Browser health route | `http://mock-action-processor.localhost/health` |
| Secret ref | `mock-processor-v1` |
| Output image variant | `action-copy` |

The mock processor copies selected image/XML input back as results. It is useful for validating secrets, dispatch, callbacks, result import, cancellation, and UI refresh without a real OCR processor.

## Official Processors

Supported processor containers can be started with the optional
`compose.actions.yaml` fragment. Production definitions remain admin-managed;
register the shipped YAML from `deployment/actions/`, test its private endpoint,
and then configure availability. See [Official Action Services](/deployment/official-action-services).
