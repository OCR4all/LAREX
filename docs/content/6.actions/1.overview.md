# LAREX Actions Overview

LAREX Actions connect LAREX projects to external processors. A processor can receive selected page input, run outside the main application, and return PAGE XML or image files for LAREX to import.

Use Actions when processing needs to be configured, audited, scoped, and run from the LAREX UI instead of handled as an offline script.

## Who Does What

| Role | Work |
| --- | --- |
| User | Runs assigned Actions from a project or editor target, monitors status, cancels, and retries. |
| Curator | Decides which Actions are useful for a workspace or project and explains when to use them. |
| Global administrator | Registers Action definitions, manages endpoint secrets, tests endpoints, and controls availability. |
| Processor author | Builds and operates the external service that accepts dispatches and uploads results. |

## Lifecycle

```text
User starts an Action
  |
  v
LAREX validates permissions, scope, locks, and concurrency
  |
  v
LAREX dispatches a signed request to the processor endpoint
  |
  v
Processor pulls input files through callback URLs
  |
  v
Processor sends heartbeats and progress
  |
  v
Processor uploads result manifest and files
  |
  v
LAREX validates, imports, unlocks, indexes, and records history
```

The processor is not granted direct database or storage access. It talks to LAREX through per-run callback URLs and a per-run bearer secret.

## Supported Targets

| Target | Meaning |
| --- | --- |
| `PAGE` | Run on complete selected pages. |
| `REGION` | Run on selected PAGE XML region IDs. |
| `TEXT_LINE` | Run on selected PAGE XML textline IDs. |

Region and textline Actions still receive full page files according to the Action definition. The target metadata tells the processor which PAGE XML elements the user selected. LAREX imports only the selected scope from returned PAGE XML.

## Supported Categories

| Category | Typical use |
| --- | --- |
| `WORKFLOW` | General automation or processors that do not fit a narrow OCR/layout category. |
| `OCR_HTR` | OCR, HTR, recognition, or text-oriented processors. |
| `LAYOUT` | Layout segmentation and PAGE XML structure processors. |

Categories help users filter the run dialog. They do not change the protocol.

## Where Actions Appear

Actions can be started from:

- the project page for all pages or selected pages
- the editor wand for page, region, or textline targets
- context-menu Action entries in the editor where available

Runs are visible in:

- the project run dialog
- the workspace queue
- the global admin Action runs view
- Action-specific run panels in admin

## Important Guarantees

- Only enabled and assigned Actions can be executed.
- Permissions are checked before each run.
- Active runs can lock pages or whole projects.
- Concurrency can limit active runs per project, workspace, or globally.
- Cancellation is cooperative for processors that are already running.
- Result upload is validated before import.
- Terminal runs reject later heartbeat or result calls.
