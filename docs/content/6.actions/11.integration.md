# Integration Actions

Use `kind: INTEGRATION` when a processor receives LAREX files, performs external
work, and returns progress and a completion message. Examples include transforming
XML and saving it to an external server, or ingesting pages into another API.

Integration Actions run on project pages, editor page/region/text-line selections,
or dataset items. They receive frozen copies of saved inputs and create no page
locks, output drafts, annotation imports, or evaluation reports.

## Definition

```yaml
version: 1
id: external-export
name: Export to external service
kind: INTEGRATION
tags: [integration, export]
targets: [PAGE, REGION, TEXT_LINE]
endpoint:
  url: https://processor.example/dispatch
  auth:
    type: hmac
    secretRef: external-export-v1
locking:
  mode: NONE
inputs:
  images:
    level: optional
  xml:
    level: required
concurrency:
  maxActiveRuns: 2
  scope: WORKSPACE
```

Require `locking.mode: NONE` and omit `outputs`, `training`, and `evaluation`.
Existing image/XML declarations support image-only, XML-only, or combined input;
optional files are included when available. Every included page/item must provide
at least one accepted file. Region and text-line selections still receive full
page files with target element IDs.

Dataset execution requires the definition to support `PAGE` and be activated for
the entire workspace. Project activation alone permits only the assigned projects.
All dataset splits are accepted; split assignments are metadata, not requirements.
LINK inputs resolve the selected source files, and COPY inputs resolve the dataset's
copied files. Existing global image-variant and per-item image choices apply.

## Starting and monitoring

Use the project or editor's Run Action dialog, or **Run Action** on a dataset.
Select dataset items before opening Run Action to run on a subset. The dialog shows
input compatibility, image choices, parameters, and run history.

Snapshots are created before dispatch or queueing, reserve workspace quota, and
remain unchanged when source annotations or images change. Temporary snapshot
bytes are removed on completion, failure, cancellation, dispatch failure, or timeout;
file metadata and checksums remain in history. Callbacks and downloads use the
normal signed dispatch and per-run bearer authentication.

The dataset API is rooted at `/workspaces/{workspaceId}/actions/integration`:

| Endpoint | Method | Purpose |
| --- | --- | --- |
| `/processors` | GET | List executable, workspace-enabled Integration Actions. |
| `/processors/{definitionId}/parameter-values` | GET | Discover dynamic parameter choices. |
| `/datasets/{datasetId}/inputs` | GET | List available input files and dataset items. |
| `/datasets/{datasetId}/runs` | POST | Start a run using the existing dataset selection/image-choice request shape. |
| `/datasets/{datasetId}/runs` | GET | List Integration run history. |

Project integrations use the existing project discovery, input preview, and start
endpoints. Run details and cancellation use the existing workspace run endpoints.
Dispatch and input responses use protocol version 1, `kind: INTEGRATION`, and exactly
one of `projectId` or `datasetId`.

## Processor SDK

```python
from larex_actions import ActionContext

async def integrate(ctx: ActionContext) -> None:
    action_input = await ctx.pull_input()
    for index, page in enumerate(action_input.pages):
        await ctx.check_cancelled()
        xml_files = [await ctx.download_bytes(file) for file in page.xml]
        image_files = [await ctx.download_bytes(file) for file in page.images]
        # Transform or submit the bytes to your service here.
        # Use ctx.run_id as an idempotency key for external work.
        await ctx.heartbeat(
            int(90 * (index + 1) / len(action_input.pages)),
            f"Exported {page.name}",
            raise_on_cancel=True,
        )
    await ctx.complete(message=f"Exported {len(action_input.pages)} inputs")
```

Progress uses heartbeats. Completion accepts a final `completed` or `failed`
manifest with a message and no files. Use `ctx.fail(message)` for failure feedback;
the FastAPI adapter also reports unhandled handler exceptions. Incremental page
results, uploaded files, patches, and evaluation reports are rejected. Start a new
run to repeat external work; Integration runs do not expose Retry.

## Development mock

The development profile registers **Mock Integration** (`mock-integration`).
Activate it for your workspace to test project, editor, and dataset workflows.
It downloads inputs, emits cancellable progress, and returns input/file counts.
`delaySeconds` accepts 0–30; `simulateFailure` exercises failure feedback.
Endpoints are mounted at `/integration` on the existing mock processor service.

Set `LAREX_DEV_MOCK_INTEGRATION_ACTION_ENABLED=false` to disable bootstrap. Endpoint,
health, and preflight URLs have corresponding
`LAREX_DEV_MOCK_INTEGRATION_ACTION_*_URL` overrides.

The packaged mock requires the next SDK minor release (`>=0.16.0,<0.17`). Before
publication, build against a local SDK checkout:

```bash
export LAREX_ACTION_SDK_PATH=/absolute/path/to/larex-action-sdk
docker compose -f compose.yaml -f compose.sdk-dev.yaml build mock-action-processor
```

For tests without Docker, run from the LAREX repository:

```bash
uv run --project "$LAREX_ACTION_SDK_PATH" pytest scripts/mock-processor/test_main.py
```
