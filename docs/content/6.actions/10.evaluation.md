# Dataset Model Evaluation

Evaluation Actions receive a frozen image/PAGE XML pair for every selected
dataset item and return one structured report. They use the normal Action
dispatch, HMAC authentication, queue, heartbeat, cancellation, and realtime
status flow, but create no page locks and upload no files.

```yaml
version: 1
id: example-ocr-evaluation
name: OCR recognition evaluation
kind: EVALUATION
category: OCR_HTR
targets: [PAGE]
locking:
  mode: NONE
inputs:
  images:
    level: required
  xml:
    level: required
evaluation:
  profile: larex.ocr-recognition
  profileVersion: 1
  splits:
    TRAIN: none
    VAL: optional
    TEST: required
```

The profile and profile version define the comparable metric vocabulary. The
initial profiles are `larex.ocr-recognition` (CER/WER, scripts, confusions and
line samples) and `larex.layout-segmentation` (pixel accuracy/IoU, baseline
metrics, class diagnostics and page samples). Custom Actions may publish their
own namespaced profiles.

Completed callbacks must contain exactly one `evaluationReport` in the
multipart manifest. Reports contain finite summary metrics plus optional
searchable tables and samples. LAREX validates profile/version, unique keys and
sample IDs, input references, JSON values, and a 10 MiB serialized size limit
before storing the report with the run history.

Baselines are offered only when the run has completed against the same dataset
and frozen-input fingerprint and uses the same report schema/profile/version.
Matching summary metrics are compared using their declared direction; percent
deltas are shown as percentage points. Tables and samples remain side-by-side
data without cross-profile calculations.

The development mock service exposes `mock-ocr-evaluation` and
`mock-layout-evaluation` from the same container as processing and training.
Both validate frozen pairs, wait for `delaySeconds`, and return deterministic
reports whose values can be varied with the `quality` parameter.
