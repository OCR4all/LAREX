# Configuration

## Configuration Sources

- Frontend runtime: `frontend/nuxt.config.ts` and optional `frontend/.env`
- Backend runtime: `backend/src/main/resources/application.yaml` and `backend/src/main/resources/application-prod.yaml`
- Deployment env files: `deployment/env/.env.prod.example` and `deployment/env/.env.prod.local.example`

## Nuxt BFF Pattern

LAREX uses Nuxt server routes as a BFF layer:

- browsers talk to the frontend origin
- frontend server routes call the backend through `NUXT_API_BASE_INTERNAL`
- production can keep the backend internal-only

This is why the opinionated production setup does not publish the backend directly.

## Production Env Model

Production now centers on a small set of public inputs:

- frontend host
- Keycloak host
- Keycloak realm
- bind IP
- database credentials
- Keycloak secrets
- Nuxt session secret
- optional mail settings

The compose files derive the usual redirect, issuer, and CORS values from those inputs.

## Local Production-Like Env Model

`deployment/env/.env.prod.local.example` is intentionally smaller. It mainly captures the secrets needed to run production images locally while the compose overlay supplies `http://larex.localhost` and `http://keycloak.localhost` defaults.

## Validation

```bash
docker compose -f compose.yaml config

docker compose --env-file deployment/env/.env.prod.local.example \
  -f compose.prod.base.yaml \
  -f compose.prod.auth.bundled-keycloak.yaml \
  -f compose.prod.local.yaml \
  config

docker compose --env-file deployment/env/.env.prod.example \
  -f compose.prod.base.yaml \
  -f compose.prod.auth.bundled-keycloak.yaml \
  -f compose.prod.publish.localhost.yaml \
  config
```
