# LAREX Actions

LAREX Actions let administrators register pre-configured processors and let workspace owners or curators assign them to a workspace or a specific project.

Processors are defined with generic YAML version 1:

```yaml
version: 1
id: ocr-inference
name: OCR Inference
description: Run OCR on selected page images.

endpoint:
  url: https://ocr.example.org/dispatch
  timeoutSeconds: 30
  auth:
    type: hmac
    secretRef: ocr-processor-v1

access:
  execute: CURATOR

locking:
  mode: PAGES

inputs:
  images: true
  xml: true

outputs:
  xml:
    enabled: true
    mode: upsert
  images:
    enabled: false

runtime:
  model:
    name: default
    optional: true

parameters:
  threshold:
    type: number
    default: 0.5
    min: 0
    max: 1
```

## Endpoint Authentication

External dispatch endpoints should use HMAC authentication. The YAML stores only a `secretRef`; the actual secret value is configured in LAREX and in the processor deployment.

For the example above, set this in the LAREX backend environment:

```bash
LAREX_ACTION_ENDPOINT_SECRET_OCR_PROCESSOR_V1="long-random-shared-secret"
```

Set the same value in the processor service under any local name the processor expects:

```bash
LAREX_DISPATCH_HMAC_SECRET="long-random-shared-secret"
```

The secret value is not stored in the processor YAML, not stored in the database, and not sent in the dispatch request.

When LAREX dispatches a run with `endpoint.auth.type: hmac`, it adds these headers:

```http
X-LAREX-Action-Auth: hmac-sha256;v=1
X-LAREX-Action-Processor: ocr-inference
X-LAREX-Action-Run-Id: <run-id>
X-LAREX-Action-Timestamp: <UTC ISO timestamp>
X-LAREX-Action-Nonce: <random nonce>
X-LAREX-Action-Body-SHA256: <base64url sha256 body hash>
X-LAREX-Action-Signature: v1=<base64url hmac sha256 signature>
```

Processor authors should use the Python SDK where possible:

- GitHub: `https://github.com/OCR4all/larex-action-sdk`
- PyPI: `larex-action-sdk`
- Install: `uv add "larex-action-sdk[fastapi]"`

The SDK verifies dispatch headers, validates timestamp/nonce replay, exposes typed input models, sends heartbeat updates, downloads files, and uploads result manifests. Custom dispatch servers can use the framework-neutral `DispatchVerifier` and `ActionClient`; FastAPI processors can use the optional `larex_actions.fastapi` adapter.

Processors that do not use the SDK should verify:

- the timestamp is recent, usually within five minutes
- the nonce has not been used before within that timestamp window
- the request body hash matches `X-LAREX-Action-Body-SHA256`
- the processor id and run id headers match the JSON payload
- the HMAC signature matches the shared secret

The canonical signature string is:

```text
larex-action-dispatch-v1
POST
<path-and-query>
<run-id>
<processor-id>
<timestamp>
<nonce>
<body-sha256-base64url>
```

Use HMAC-SHA256 over that canonical string and compare the base64url result to `X-LAREX-Action-Signature` without the `v1=` prefix.

## Run Secret

The dispatch payload also contains a per-run secret. Processors use it as a bearer token when calling LAREX pull, heartbeat, file download, and result upload endpoints:

```http
Authorization: Bearer <run-secret>
```

This run secret is scoped to one Action run, expires, and is stored hash-only by LAREX. It is separate from the long-lived dispatch HMAC secret.

## Advanced Protocol Notes

Processor YAML `version: 1` is the administrator-facing definition schema version. Runtime payload versioning is handled by LAREX and the SDK. SDK-based processors do not need to configure it manually.

Raw HTTP processors may see `protocolVersion: 1` in dispatch and input payloads. SDK result manifests include the same field automatically. For compatibility with simple hand-written processors, LAREX treats a missing result manifest protocol version as v1 and rejects only unsupported explicit protocol versions.

Result upload is idempotent after a run reaches a terminal state; retrying after a completed or failed response returns the existing run instead of importing files again.

## Assignments

After a global admin saves a processor definition, assign it from the LAREX Actions admin page or from workspace settings.

Assignments can target:

- the workspace default, available to projects in that workspace
- one specific project

Workspace owners and curators can assign enabled processors. Editors can execute processors only when the processor YAML allows `access.execute: EDITOR`.

## Locking

`locking.mode: PAGES` locks the selected pages while the run is active. `locking.mode: PROJECT` locks the whole project. LAREX releases only locks owned by the Action run when the run completes, fails, or is cancelled.

## Development Mock Processor

The dev Docker Compose setup includes a small FastAPI mock processor built with `larex-action-sdk[fastapi]`:

- service: `mock-action-processor`
- internal dispatch URL: `http://mock-action-processor:9000/dispatch`
- browser health URL: `http://mock-action-processor.localhost/health`
- processor id: `mock-image-copy`
- secret ref: `mock-processor-v1`

The compose file injects the same dev secret into LAREX and the processor:

```yaml
app:
  environment:
    LAREX_ACTION_ENDPOINT_SECRET_MOCK_PROCESSOR_V1: dev-mock-action-secret-change-me

mock-action-processor:
  environment:
    LAREX_DISPATCH_HMAC_SECRET: dev-mock-action-secret-change-me
```

Use this YAML to test the full Action flow locally:

```yaml
version: 1
id: mock-image-copy
name: Mock Image Copy
description: Development processor that copies the first page image and XML back as Action outputs.

endpoint:
  url: http://mock-action-processor:9000/dispatch
  timeoutSeconds: 30
  auth:
    type: hmac
    secretRef: mock-processor-v1

access:
  execute: CURATOR

locking:
  mode: PAGES

inputs:
  images: true
  xml: true

outputs:
  xml:
    enabled: true
    mode: upsert
  images:
    enabled: true
    variant: action-copy
    mode: upsert

runtime:
  model:
    name: mock
    optional: true

parameters:
  threshold:
    type: number
    default: 0.5
    min: 0
    max: 1
```

The mock processor verifies the HMAC dispatch headers, pulls the selected input pages from LAREX, sends a few heartbeat updates, downloads the first input image and first XML file for each page, uploads image files back with variant `action-copy`, and imports XML files into the page's normal PAGE XML history.
