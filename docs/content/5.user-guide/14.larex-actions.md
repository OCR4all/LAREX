# Actions

Actions let administrators register pre-configured processors and let workspace owners or curators assign them to a workspace or a specific project.

Processors are defined with generic YAML version 1:

```yaml
version: 1
id: ocr-inference
name: OCR Inference
description: Run OCR on selected page images.
category: OCR_HTR
targets:
  - PAGE
  - REGION
  - TEXT_LINE

endpoint:
  url: https://ocr.example.org/dispatch
  healthUrl: https://ocr.example.org/health
  timeoutSeconds: 30
  auth:
    type: hmac
    secretRef: ocr-processor-v1

access:
  execute: CURATOR

locking:
  mode: PAGES

inputs:
  images: true
  xml: true

outputs:
  xml:
    enabled: true
    mode: upsert
  images:
    enabled: false

concurrency:
  maxActiveRuns: 1
  scope: PROJECT

runtime:
  model:
    name: default
    optional: true

parameters:
  threshold:
    type: number
    default: 0.5
    min: 0
    max: 1
```

## Endpoint Authentication

External dispatch endpoints should use HMAC authentication. The YAML stores only a `secretRef`; the actual secret value is generated in LAREX and copied into the processor deployment.

For the example above, create an endpoint secret in **Admin → Actions → Endpoint Secrets** with ref `ocr-processor-v1`. LAREX generates a strong secret server-side and shows the plaintext value once. Copy it immediately and set the same value in the processor service under any local name the processor expects:

```bash
LAREX_DISPATCH_HMAC_SECRET="generated-secret-from-larex"
```

LAREX stores the endpoint secret encrypted in the database. It is not stored in the processor YAML and is not sent in the dispatch request. The raw value is only returned on create or rotate.

Bundled processors that start with the LAREX compose stack should usually keep using env fallback, because the processor container needs the shared value before an admin can generate one in the UI. Set the same value in both the backend env and the bundled processor env. If no admin-managed secret exists for a ref, LAREX checks the backend environment:

```bash
LAREX_ACTION_ENDPOINT_SECRET_OCR_PROCESSOR_V1="long-random-shared-secret"
```

The admin secret list shows discoverable env-backed refs as `Env fallback` entries. These entries can be used by Action definitions, but they cannot be rotated or deleted from LAREX because the deployment environment is their source of truth.

Rotating an admin-managed secret generates a new value and reveals it once. Update the processor deployment with the new value before sending new jobs that use that `secretRef`.

When LAREX dispatches a run with `endpoint.auth.type: hmac`, it adds these headers:

```http
X-LAREX-Action-Auth: hmac-sha256;v=1
X-LAREX-Action-Processor: ocr-inference
X-LAREX-Action-Run-Id: <run-id>
X-LAREX-Action-Timestamp: <UTC ISO timestamp>
X-LAREX-Action-Nonce: <random nonce>
X-LAREX-Action-Body-SHA256: <base64url sha256 body hash>
X-LAREX-Action-Signature: v1=<base64url hmac sha256 signature>
```

Processor authors should use the Python SDK where possible:

- GitHub: `https://github.com/OCR4all/larex-action-sdk`
- PyPI: `larex-action-sdk`
- Install: `uv add "larex-action-sdk[fastapi]>=0.6,<0.7"`

The SDK verifies dispatch headers, validates timestamp/nonce replay, exposes typed input models, sends heartbeat updates, downloads files, and uploads result manifests. Custom dispatch servers can use the framework-neutral `DispatchVerifier` and `ActionClient`; FastAPI processors can use the optional `larex_actions.fastapi` adapter.

Processors that do not use the SDK should verify:

- the timestamp is recent, usually within five minutes
- the nonce has not been used before within that timestamp window
- the request body hash matches `X-LAREX-Action-Body-SHA256`
- the processor id and run id headers match the JSON payload
- the HMAC signature matches the shared secret

The canonical signature string is:

```text
larex-action-dispatch-v1
POST
<path-and-query>
<run-id>
<processor-id>
<timestamp>
<nonce>
<body-sha256-base64url>
```

Use HMAC-SHA256 over that canonical string and compare the base64url result to `X-LAREX-Action-Signature` without the `v1=` prefix.

## Run Secret

The dispatch payload also contains a per-run secret. Processors use it as a bearer token when calling LAREX pull, heartbeat, file download, and result upload endpoints:

```http
Authorization: Bearer <run-secret>
```

This run secret is scoped to one Action run, expires, is revoked when the run completes, fails, or is cancelled, and is stored hash-only by LAREX. It is separate from the long-lived dispatch HMAC secret.

LAREX only advertises callback URLs whose origin is allowlisted when it derives the URL from an incoming request. Configure allowed origins with `LAREX_ACTIONS_PUBLIC_BASE_URL_ALLOWED_ORIGINS`; it defaults to `cors.allowed-origin`. Non-local derived callback URLs must use HTTPS unless `LAREX_ACTIONS_PUBLIC_BASE_URL_REQUIRE_HTTPS=false`.

Processor dispatch and health-check URLs are also validated before LAREX calls them. Configure `LAREX_ACTIONS_ENDPOINT_ALLOWED_ORIGINS` to a comma-separated list such as `http://mock-action-processor:9000,https://kraken.kallimachos.de`. Public endpoints must use HTTPS; local service endpoints can use HTTP unless `LAREX_ACTIONS_ENDPOINT_ALLOW_INSECURE_LOCAL=false`.

The Python SDK also validates callback and download URLs by default: pull, heartbeat, and result URLs must share one origin, non-local origins must use HTTPS, and file download URLs must use the same trusted origin. Processors can pin expected LAREX origins with `LAREX_ALLOWED_CALLBACK_ORIGINS`.

## Cancellation Contract

Processors should call the heartbeat endpoint regularly and stop work when the heartbeat response contains `cancelRequested: true`. After cancellation is requested, processors should avoid uploading results and release their own temporary resources. LAREX rejects result uploads for runs in `CANCEL_REQUESTED` or `CANCELLED` and releases only locks owned by that run.

SDK-based processors should use the cooperative cancellation helpers:

- `await ctx.check_cancelled()` inside long-running loops and before expensive steps
- `raise_on_cancel=True` on heartbeat calls while work is still active
- the SDK subprocess helper for external commands so child processes receive a graceful terminate signal before escalation

When cancellation is detected, the SDK sends a final heartbeat with `status: "cancelled"` and then stops without uploading results. LAREX finalizes the run as `CANCELLED`, expires the run secret, releases locks, and promotes the next queued run.

## Advanced Protocol Notes

Processor YAML `version: 1` is the administrator-facing definition schema version. Runtime payload versioning is handled by LAREX and the SDK. SDK-based processors do not need to configure it manually.

Raw HTTP processors may see `protocolVersion: 1` in dispatch and input payloads. SDK result manifests include the same field automatically. For compatibility with simple hand-written processors, LAREX treats a missing result manifest protocol version as v1 and rejects only unsupported explicit protocol versions.

Once a run completes, fails, or is cancelled, LAREX rejects later pull, download, heartbeat, and result calls with the same run secret. Processors should treat a successful result upload response as final and avoid retrying after a terminal response.

## Assignments

After a global admin saves an Action definition, choose where it is available.

Global admins manage global and workspace availability from **Admin → Actions**:

- **Global** Actions are available in every workspace and project.
- **Workspace availability** makes a non-global Action available to one or more workspaces.

Workspace owners and curators manage project visibility from workspace settings:

- **Workspace default** makes the Action available to all projects in that workspace.
- **Project-specific** assignment makes the Action available only to selected projects.
- Global Actions are inherited and read-only in workspace settings.

The project **Run Action** dialog lists global Actions, workspace-default Actions, and project-specific Actions. Duplicate definitions are collapsed into one entry. Actions that are assigned but not executable for the current user are shown separately as unavailable instead of being mixed into the runnable selector.

Editors can execute Actions only when the YAML allows `access.execute: EDITOR`. `access.execute: CURATOR` requires a workspace curator, workspace owner, or global admin.

## Execution Scope

Users can run an Action for all project pages, selected pages, or from the editor wand on the current page, selected regions, or selected text lines. Actions declare where they are useful with:

```yaml
category: LAYOUT # WORKFLOW, OCR_HTR, or LAYOUT
targets:
  - PAGE
  - REGION
  - TEXT_LINE
```

If omitted, `category` defaults to `WORKFLOW` and `targets` defaults to `[PAGE]`.

LAREX still sends full page image/XML files according to the declared `inputs`; editor-targeted runs add target metadata with selected region and textline ids only. Processors should resolve geometry and current text from the PAGE XML they already receive, then decide whether to crop, mask, pad, deskew, or process the full image. Locks are still page-level, so a region or textline run locks the affected pages until the run reaches a terminal state.

A processor cannot read or write pages outside the run scope, and it can only access the input and output types declared in the Action YAML.

Declared `parameters` are fixed by the Action definition for now. Users can see the configured default values before starting a run, but they cannot edit them.

Processors return PAGE XML for page, region, and textline runs:

```yaml
outputs:
  xml:
    enabled: true
    mode: upsert
```

For page-targeted runs, the returned PAGE XML replaces the page annotation. For region-targeted runs, LAREX imports only the selected region content from the returned PAGE XML and preserves the rest of the current annotation. For textline-targeted runs, LAREX imports only the selected textlines. This keeps the processor protocol simple: a processor always returns PAGE XML, while LAREX owns the scoped merge.

The run history in the project **Run Action** dialog can expand individual runs to show status timestamps, result summaries, and processor logs. Failed and cancelled runs can be retried from that history; retry creates a new run with the same Action, page scope, and stored parameters, then applies the normal permission, assignment, concurrency, and lock checks again.

## Production Controls

LAREX applies these runtime safeguards around every Action run:

- Dispatch is retried with backoff before a run is marked failed.
- A watchdog fails stale dispatches and runs without heartbeats, then releases Action-owned locks.
- Completed, failed, and cancelled run records are pruned after the configured retention period.
- Result uploads are checked against file count, per-file size, total size, declared output type, MIME/decoding, XML validity, page scope, storage quota, and output variant rules.
- Run logs are stored as structured timestamped events while preserving the legacy log text summary.
- Action definition changes, assignment changes, run start/cancel/complete/failure, watchdog failures, and dispatch failures are written to the Action audit log.

Use `concurrency` to limit active runs:

```yaml
concurrency:
  maxActiveRuns: 1
  scope: PROJECT
```

`scope` can be `PROJECT`, `WORKSPACE`, or `GLOBAL`. If omitted, LAREX defaults to one active run per Action and project.

Admins can also test an endpoint from **Admin → Actions**. If `endpoint.healthUrl` is set, LAREX sends a short GET request to that URL. Otherwise it sends a HEAD request to `endpoint.url`.

## Locking

`locking.mode: PAGES` locks the selected pages while the run is active. `locking.mode: PROJECT` locks the whole project. LAREX releases only locks owned by the Action run when the run completes, fails, or is cancelled.

## Development Mock Processor

The dev Docker Compose setup includes a small FastAPI mock processor built with `larex-action-sdk[fastapi]`:

- service: `mock-action-processor`
- internal dispatch URL: `http://mock-action-processor:9000/dispatch`
- browser health URL: `http://mock-action-processor.localhost/health`
- processor id: `mock-image-copy`
- secret ref: `mock-processor-v1`

The compose file injects the same dev secret into LAREX and the processor:

```yaml
app:
  environment:
    LAREX_ACTION_ENDPOINT_SECRET_MOCK_PROCESSOR_V1: dev-mock-action-secret-change-me

mock-action-processor:
  environment:
    LAREX_DISPATCH_HMAC_SECRET: dev-mock-action-secret-change-me
```

For bundled local processors, keep this env fallback setup. For a remote mock processor that is deployed separately, create `mock-processor-v1` in **Admin → Actions → Endpoint Secrets** and copy the revealed value into that remote processor's `LAREX_DISPATCH_HMAC_SECRET`.

Use this YAML to test the full Action flow locally:

```yaml
version: 1
id: mock-image-copy
name: Mock Image Copy
description: Development processor that copies the first page image and XML back as Action outputs.
category: WORKFLOW
targets:
  - PAGE
  - REGION
  - TEXT_LINE

endpoint:
  url: http://mock-action-processor:9000/dispatch
  healthUrl: http://mock-action-processor:9000/health
  timeoutSeconds: 30
  auth:
    type: hmac
    secretRef: mock-processor-v1

access:
  execute: CURATOR

locking:
  mode: PAGES

inputs:
  images: true
  xml: true

outputs:
  xml:
    enabled: true
    mode: upsert
  images:
    enabled: true
    variant: action-copy
    mode: upsert

concurrency:
  maxActiveRuns: 1
  scope: PROJECT

runtime:
  model:
    name: mock
    optional: true

parameters:
  threshold:
    type: number
    default: 0.5
    min: 0
    max: 1
```

The mock processor verifies the HMAC dispatch headers, pulls the selected input pages from LAREX, sends a few heartbeat updates, downloads the first input image and first XML file for each page, uploads image files back with variant `action-copy`, and uploads PAGE XML files for page or editor-targeted runs.

## Development Kraken Segmentation Processor

The dev Docker Compose setup also includes an internal Kraken OCR segmentation processor:

- service: `kraken-segmentation-processor`
- internal dispatch URL: `http://kraken-segmentation-processor:9000/dispatch`
- processor id: `kraken-segmentation`
- secret ref: `kraken-segmentation-v1`
- Kraken version: `7.0.2`

When the backend runs with the `dev` Spring profile, LAREX automatically creates a global **Kraken Segmentation** Action for this processor. The Action is available in every workspace/project for curators and global administrators. Disable this bootstrap with:

```bash
LAREX_DEV_KRAKEN_SEGMENTATION_ACTION_ENABLED=false
```

The processor downloads the first selected page image, runs Kraken baseline segmentation, serializes the result as PAGE XML, and imports it back through the normal Action result path. For region-targeted runs, it also downloads the current PAGE XML, crops the selected region for Kraken, and returns a PAGE XML container with the selected region updated.

```bash
kraken -x -i page-image output.xml --device cpu --precision 32-true segment -bl
```

The container is CPU-first by default. These environment variables can be used to adjust runtime behavior:

```yaml
kraken-segmentation-processor:
  environment:
    KRAKEN_DEVICE: cpu
    KRAKEN_PRECISION: 32-true
    KRAKEN_TEXT_DIRECTION: horizontal-lr
    KRAKEN_SEGMENTATION_MODEL: ""
    KRAKEN_MAX_PROCESS_SECONDS: 900
```

Outside local dev, you can host the same processor in the production compose stack by adding `-f compose.prod.kraken.yaml`. The overlay wires the backend to the internal processor URL. You can either create `kraken-segmentation-v1` in **Admin → Actions → Endpoint Secrets** and copy the revealed value into the processor env, or keep using `LAREX_ACTION_ENDPOINT_SECRET_KRAKEN_SEGMENTATION_V1` as the backend fallback secret.

Use this YAML if you need to recreate the dev Action manually:
