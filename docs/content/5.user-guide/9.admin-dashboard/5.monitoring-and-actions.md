# Monitoring and Actions

The admin monitoring pages help diagnose operational issues across the whole instance. They cover search indexes, captured API errors, application health, and LAREX Action runs.

## Search Index

Open **Admin -> Search Index** to manage the global index used for page filtering and workspace text search.

The index powers:

| Capability | Description |
| --- | --- |
| Text content | Find pages containing specific transcription text. |
| Workspace search | Rank text hits across projects. |
| Labels | Filter pages by region or textline labels. |
| Tags | Filter pages by assigned tags. |

The index updates automatically when annotations are saved. Use **Rebuild Index** only when:

- pages were imported from external sources that bypassed the normal save flow
- search or label filters appear out of sync
- an upgrade introduced new indexing behavior
- an administrator suspects index corruption

Rebuilding processes all XML files in all projects and can take several minutes on large installations.

## Error Events

Open **Admin -> Errors** to inspect captured API errors. The page shows 24-hour and 7-day summaries, including total events, server errors, actionable client errors, distinct users, and distinct workspaces.

Use filters to narrow the table by:

- time window: 1, 7, or 30 days
- status code: 403, 409, 500, or 507
- user
- workspace
- message, code, or path search

Open **Details** for an event when investigating a support report. Error events are useful for correlating quota errors, permission failures, server errors, and workspace-specific problems.

## Application Health

Open **Admin -> Actuator** to check backend health. The page shows overall status, component counts, last refresh time, and component details returned by the health endpoint.

Use this page for a quick operational check before deeper log investigation. Refresh the page after deployment, database maintenance, or service restarts.

## Action Runs

Open **Admin -> Action Runs** to inspect queued, active, and finished LAREX Action runs across all workspaces.

The table shows:

- Action name and processor key
- workspace, workspace ID, and project
- status and status message
- page count
- last activity
- cancellation when the run can be cancelled
- link back to the Action definition

Use filters for status, Action, workspace, or search text. Queued runs show queue position. Active runs can be cancelled when the processor/run state allows it; running processors stop cooperatively after LAREX records the cancellation request.

## Action Definition Administration

Open **Admin -> Actions** to manage processor definitions and dispatch metadata. This area covers:

- creating Action definitions from YAML
- validating YAML
- saving and deleting definitions
- endpoint health testing
- endpoint secrets
- workspace/project availability
- Action-specific runs and audit events

For the full setup workflow, see [Actions Admin Setup](/actions/admin-setup). For YAML fields and behavior, see [YAML Reference](/actions/yaml-reference).

## Troubleshooting Examples

| Symptom | Admin page |
| --- | --- |
| Search results miss recently imported text. | Rebuild from **Search Index** after confirming imports bypassed normal save/index flow. |
| Users report quota failures. | Filter **Errors** for status `507`, then inspect **Quotas** for the affected workspace. |
| A processor appears stuck. | Check **Action Runs**, review status message and last activity, then cancel if appropriate. |
| A page or project appears locked. | Check active Action runs and import jobs before assuming a manual lock problem. |
| A service looks unavailable. | Refresh **Actuator** and then inspect deployment logs if a component is down. |
