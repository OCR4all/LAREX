The test suites should stay small enough that one person can read all of them. Each test
should state a behaviour that a user, an API client or a PAGE XML consumer relies on. A test
that only repeats how the code is currently written makes refactoring harder and catches
little, so it does not belong in the suite.

## Running Tests

| Command | What it runs |
| --- | --- |
| `task backend:test` | JUnit tests, including Testcontainers integration tests (needs Docker) |
| `task backend:test:coverage` | The same, with a JaCoCo report in `backend/build/reports/jacoco/` |
| `task frontend:test` | ESLint, `nuxt typecheck` and all Vitest projects |
| `task frontend:test:coverage` | Vitest with a coverage report in `frontend/coverage/` |
| `task frontend:test:e2e` | Playwright journeys against a running stack |
| `task test` | Backend, docs and frontend checks |

## Test Layers

### Backend

| Layer | Use it for | Tools |
| --- | --- | --- |
| Unit | Pure domain logic: geometry, validation, dataset splits, PAGE mapping | JUnit, AssertJ |
| Integration | Services together with the database, transactions and security; HTTP endpoints | `@SpringBootTest`, Testcontainers, MockMvc |
| Architecture | Package and layering rules | ArchUnit |

Prefer integration tests over Mockito for service behaviour. When a service mostly
coordinates repositories, locks and permissions, a test that mocks all of those can only
check call order. Stub only what leaves the process, such as Keycloak admin calls or Action
service HTTP requests.

### Frontend

Vitest runs three projects:

| Project | Files | Environment | Use it for |
| --- | --- | --- | --- |
| `unit` | `*.test.ts` | Node | Utilities, commands, stores and composables with no Nuxt runtime |
| `client` | `*.client.test.ts` | Node, `import.meta.client = true` | Code that branches on the client build |
| `nuxt` | `*.nuxt.test.ts` | Nuxt app in happy-dom | Rendered components through `mountSuspended` |

Move logic out of components into composables or utilities, and test it there. Mount a
component only for behaviour that lives in its template, such as which fields a role can
see or what a form submits. Use `mockNuxtImport` for auto-imported composables and
`registerEndpoint` for API calls. `workspace/slideover/__tests__/create.nuxt.test.ts` is a
complete example.

Never read or compile `.vue` or `.ts` source text in a test. If a component's behaviour
is hard to reach from a test, extract it or test it through a mounted component.

### End-to-End

Playwright journeys in `frontend/e2e/` cover what only a browser can show: sign-in,
focus and keyboard handling, loaders, uploads, and several users working together. Keep
them few and long: each journey follows one realistic task from start to finish.

The journeys run against an already running stack. By default they sign in at
`http://larex.localhost` as `katarn` from the development realm. Set `E2E_BASE_URL`,
`E2E_USERNAME` and `E2E_PASSWORD` to use another stack or account.

## PAGE XML Fidelity

Losing or changing annotation data on load and save is the most expensive bug LAREX can
have, so three checks guard the PAGE XML pipeline.

**Corpus.** `PageCorpusTest` runs every file in `backend/src/test/resources/page-corpus/`
through upload canonicalisation, editor load and editor save without edits. It checks two
things:

- The output matches the golden files in `page-corpus-goldens/<document>/`: the stored file,
  the conversion messages, the `PageDto` JSON and the saved file. Timestamps written during
  the run show as `[now]`.
- Every difference between the uploaded, stored and saved file is listed in
  `page-corpus/known-differences.txt`. This list is a ratchet: an unlisted difference fails
  the test, and so does a listed one that no longer occurs.

To record an intended change, run the test with `LAREX_UPDATE_GOLDENS=true`. Then review
every changed golden file and every changed line in `known-differences.txt` in the diff. A
new PAGE feature or a fidelity fix comes with a corpus file that shows it.

**Editor model.** `page-conversion.identity.test.ts` sends a `PageDto` that fills every
field to the editor model and back, and then does the same with each backend golden
`dto.json`. It also sends each one through the collaboration snapshot. Differences are
listed in `fixtures/page-conversion-known-differences.ts`. A field added to `PageDto` fails
the typecheck until the fixture's field table names it.

**Stored data.** `./gradlew pageAudit -Pdir=<directory> [-Preport=<file>] [-Pbaseline=<file>]`
reads every PAGE file under a directory without changing it. It reports which files LAREX can
load and save, which files the strict page4j reader rejects and why, and what a load and save
without edits would change. Run it on a copy of production data before changing the PAGE
library, the mappers or the stored version.

`-Pbaseline` makes the audit a ratchet across builds. If the file doesn't exist, the audit
records each file's outcome and differences in it. If it does exist, the report lists the
differences that are new in this build, the ones that went away, and the files whose outcome
changed. A change to the PAGE pipeline is ready when the report has no new differences and no
file got worse. Record the baseline with the build before the change.

## What a Test Must Be

Keep a test only if all of these hold:

1. **It states a behaviour.** Its name reads like a sentence from the documentation, not a
   description of a past bug.
2. **It goes through a stable seam:** a public function, an HTTP endpoint, a command's
   `execute` and `undo`, a store action, the rendered DOM, or a PAGE file in and out.
3. **It survives refactoring.** Changing the code without changing the behaviour leaves it
   green.
4. **It can be read in under a minute.** A setup much longer than the assertions means the
   test is at the wrong seam.

Do not add tests that:

- parse or compile production source code;
- reflect on annotations or assert on framework configuration binding;
- assert mainly with `verify(...)` chains or the order of mocked calls;
- live in a separate file named after one bug or one hardening step.

## Fixing a Bug

A bug fix does not add a new test file or a test named after the bug. Use the first option
that fits:

1. **Add a case to an existing table:** a row in an `it.each` or `@ParameterizedTest`, or
   another fixture file.
2. **Tighten the existing test** whose name already describes the behaviour that broke.
3. **Write the missing behaviour test** in the module's existing test file, named after the
   behaviour, if the bug shows that a behaviour was never specified.
4. **Add a step to an end-to-end journey** if the bug only shows up in a real browser,
   or explain in the pull request why no automated test fits.

A pull request that adds a new test file explains in its description why the test could
not go into an existing one.
