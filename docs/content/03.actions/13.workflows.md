Workflows combine page-processing Actions into a saved, ordered sequence. A workflow runs on project pages and starts each step only after the previous step has completed successfully and its results have been imported.

## Build a workflow

Open **Admin → Actions → Build workflow**. A draft with a temporary name appears in the Actions sidebar, just like a new processor Action. The editor opens directly on the Actions page. Give the workflow a name, then find processors in the filterable library. Drag a processor onto the canvas to insert it at that position, or click its **+** button to append it. Drag a node by its header to reorder steps; the arrows offer the same controls without dragging.

Edit default parameters, required image types, and image variants inside each node. The same processor can appear multiple times with independent parameters. A new step stores the Action's defaults. Parameters whose choices come from the processor stay unset until a value is picked, so the processor's current default applies each time the workflow starts. Selecting a node or editing parameters preserves the canvas pan and zoom. Use **Fit workflow** to see the complete sequence. Undo and redo restore step changes, including removed nodes and their parameters. Use **Save** in the Actions toolbar or **Ctrl/⌘ S**. The same toolbar provides availability, enable/disable, and delete controls for saved workflows. Selecting a saved workflow opens this same editor directly.

Steps run from left to right. Connections are automatic: workflows have one path, with no branches or cycles. A workflow can contain up to 30 steps. Training, evaluation, integration, and processors that only target regions or text lines cannot be included.

After saving, the workflow appears alongside individual processors in Admin Actions. Use the same **Availability** controls to make it global or available to selected workspaces. Every constituent processor must be available in that scope; a globally available workflow requires globally available processors.

A curator then adds the workflow in **Workspace settings → Actions**, where it can be activated for the entire workspace or selected projects, just like any other Action. Individual processors do not need separate activation to run as part of an activated workflow. Each step still checks the processor’s availability, enabled state, and the initiating user’s execution permissions.

### Who can run a workflow

Every step runs as the user who started the workflow. A workflow therefore needs the strictest execute role among its steps: if any step's processor requires curator access, only curators can run the whole workflow. LAREX derives this from the current steps every time, not from a value stored on save. Each step node, the processor library, the workflow list, and the runner show a role badge, and the runner names the steps that require curator access.

LAREX checks the starter's role again before each step. If it no longer suffices, the run stops with a message naming that step.

Workflow creation and editing take place in **Admin → Actions**. Workspace settings provides activation and project assignment for workflows that an administrator has made available.

## Test a workflow

Use **Test workflow** in the Admin Actions toolbar to check the current steps, including unsaved edits. Results appear in a popover card with an overall status, progress bar and a row for every step. Checks run in sequence, with a spinner on the active step and a short minimum display time before moving on. Reopen the popover to review the results or use **Run again** to repeat the check. Authenticated preflight verifies processor identity and capabilities when supported; otherwise the Action’s normal reachability check is used. Each step is checked using its own parameter configuration. Editing a step clears the previous results.

Testing does not save the workflow or start page processing. Project permissions, availability and actual page inputs are checked when running.

## Run a workflow

Open the project’s **Run Action** panel for all pages or the current selection. Workflows appear alongside individual Actions in the same table. Use the **Type** filter to show workflows, or combine it with tags and search. Select a workflow to open its graph, then adjust parameters directly inside each step node. The step dropdown and previous/next buttons navigate and center the selected node. These adjustments apply only to this run. Use **Back to Actions** to choose a different Action or workflow.

The info button beside **Back to Actions** explains execution and page locking in a popover.

Review the affected pages before starting. A popover summarizes eligibility and annotation replacements across all steps. Search the page and skipped-page lists, and exclude any pages you want to keep. Exclusions apply to the entire workflow. Use **Review again** to refresh eligibility after page inputs change or a start attempt is rejected; deliberate exclusions are retained for pages that remain eligible.

Each step reads the project’s current PAGE XML and selected image variants. **Required image types** inherits the processor’s accepted types when empty. Choosing types narrows that set and requires a matching image on every workflow page, even if the processor normally accepts images optionally. For example, require `COLOR` for a first step and `BINARY` for a later step. Leave image variants empty to select compatible images automatically; a variant constraint and a type constraint must both match. A later step can select an image variant produced by an earlier step. Generic output files are retained as ordinary Action outputs; they are not passed directly between steps. Page locks apply separately to each processor run, so the project is not locked for the entire workflow.

## Progress and cancellation

Workflow runs are persisted by the backend and continue after closing the panel or restarting the backend. Editing a saved workflow does not change an existing run’s sequence or parameter snapshot. Disabling a workflow or revoking its activation/availability prevents later steps from starting. Workflows with active runs cannot be deleted.

The workflow stops if a step fails, is cancelled, or completes with issues. It also stops if a later step loses execution permission, activation, or required inputs. It never silently drops pages between steps. Results already imported by completed steps remain in the project.

Starting a workflow closes the Run Action panel. The Job panel shows one workflow job with overall progress, an ordered step list, per-step logs, and workflow cancellation. Individual processor runs continue to handle page locks and result imports internally. In a project, open the **Run Action** panel's history and choose the **Workflows** tab for workflow runs; the **Actions** tab keeps individual step reports and outputs. Administrators can also open the workflow runs sidebar beside **Audit** in **Admin → Actions**. Cancelling the workflow requests cancellation of the active step and prevents later steps from starting.

Active workflow jobs remain visible regardless of the number of newer completed runs. If workflow metadata is temporarily unavailable, its individual steps remain grouped internally and do not appear as separate jobs. Clearing Action history retains completed steps that an active workflow still needs. Once a workflow finishes, its child reports can be removed; the workflow remains dismissible independently, and dismissal affects only your Job panel. Removed reports and logs are no longer available.

Processors use the existing LAREX Action protocol; no workflow-specific SDK interface is needed. Typed image inputs add optional `image_types` requirements and per-file `image_type` metadata, which processors may ignore.

## Try the development processors

With the development mock processor enabled, Admin Actions includes four processors that form a working example:

1. **Mock Binarization** requires `COLOR` or `GRAYSCALE` input, thresholds the page image and writes the `binarized` image variant. Adjust `threshold` from 0 to 255.
2. **Mock Whole-page Region** creates PAGE XML if needed and replaces the layout with one full-page text region. It requires `BINARY` image input. Leave variants empty to automatically consume the preceding binary output, or select `binarized` explicitly. A differently named color image cannot satisfy this requirement.
3. **Mock Single Text Line** adds one text line and baseline inside the first text region. It requires a `BINARY` image and an existing text region.
4. **Mock Random OCR** adds sample text to existing text lines. Adjust `wordCount` and `seed` to vary the output. Choose one or more `vocabularies` to draw the words from; the choices come from the processor, which marks its default. It requires a `BINARY` image and at least one text line.

These processors use the normal signed dispatch, result upload, and import paths. The region and line steps replace existing layout; review affected pages before running them. All four are globally available in development and can be used in a workflow without separately activating each processor.

To test the type transitions, start with a page containing only a color or grayscale image and add the four steps in this order. Leave image variants empty: the first step selects the source image and the later steps select the detected binary output. To test a color-only first step, choose `COLOR` under its **Required image types**. Run a binary-only step directly on the original page to check the missing-input warning; after binarization, its dropdown should show and preselect only binary variants. Each mock step reports the consumed variant and detected type in its page result message.

## Development mock SDK version

The packaged mock pins its SDK range in `scripts/mock-processor/requirements.txt`. A mock feature that depends on a new SDK release needs that release published before the mock image is built or distributed; changing the LAREX dependency does not publish the SDK.

To verify against an unreleased SDK, use `compose.sdk-dev.yaml` with `LAREX_ACTION_SDK_PATH` pointing to the SDK checkout, as described in [Development mock](/actions/integration#development-mock). Workflow orchestration itself remains in LAREX and does not require a new SDK endpoint.
