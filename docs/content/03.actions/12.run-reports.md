# Outcomes and Run Reports

A processing run can finish with **Completed with issues**. For example, a run
with 998 successful pages and two failed pages retains the successful imports and
downloadable outputs. Its report lists the counts, page names, and failure reasons.
The run details provide a searchable page table and a JSON download. Reports are
also available from the workspace queue and admin run monitoring.

| Final state | Meaning |
| --- | --- |
| `COMPLETED` | Processing finished without failures or warnings. Ordinary skips are allowed. |
| `COMPLETED_WITH_ISSUES` | Processing finished with recoverable failures or explicit warnings. |
| `FAILED` | A fatal error stopped processing, or every page failed without any successful or deliberately skipped pages. |
| `CANCELLED` | Cancellation stopped the run. |

All these states release locks and concurrency slots and expire the callback
secret. Both completed states finalize downloadable outputs. Fatal and cancelled
runs retain the existing output-cleanup behavior; previously committed annotation
imports remain imported. Their reports show recorded outcomes and unfinished work.

## Page Outcomes

Protocol version remains `1`. LAREX advertises `capabilities.runReports: true` in
dispatch and input payloads. Reporting APIs require `larex-action-sdk>=0.19.0`
and refuse to send report data to servers that do not advertise this capability.
The simplified incremental Python interface shown below requires SDK 0.20.

An incremental result can include `pageOutcome`:

```json
{
  "protocolVersion": 1,
  "status": "running",
  "pageId": "page-42",
  "pageOutcome": {
    "pageId": "page-42",
    "status": "FAILED",
    "message": "Invalid PAGE XML: missing Page element",
    "warnings": []
  },
  "files": []
}
```

Accepted outcomes are `SUCCEEDED`, `FAILED`, and `SKIPPED`. Failed and skipped
pages require a reason and cannot submit files. Successful pages may include
warnings. Omitting `pageOutcome` preserves the existing successful-acknowledgement
behavior, including submissions with no output files.

Every outcome counts toward progress and releases its page lock. A deliberate
skip such as “No eligible content” does not mark the run as having issues.
Invalid input and processing errors are failures. Every selected page must be
acknowledged before an incremental run can complete.

```python
from larex_actions import PageResultRejected

for page in action_input.pages:
    await ctx.check_cancelled()
    try:
        results = await process_page(page)  # Your page-processing function.
    except InvalidPageInput as error:  # Your explicitly recoverable exception.
        await ctx.submit_page_results(
            page.id,
            page_status="FAILED",
            reason=str(error),
        )
        continue
    try:
        await ctx.submit_page_results(page.id, results)
    except PageResultRejected:
        # LAREX has already recorded and settled this failed page.
        continue

await ctx.complete(message="Finished processing selected pages")
```

Supply the page ID only once. `message` remains run progress text; `reason` is
the page-specific diagnostic stored in the report. `warnings=["Low confidence"]`
adds nonfatal concerns to a page, including one that succeeded. Warnings mark
the run as having issues but do not make a successful page retryable. Omitting
`page_status` means success; use `page_status="SKIPPED", reason="No eligible content"`
for a deliberate skip. The SDK constructs the protocol's `pageOutcome` internally.
The SDK 0.19 `outcome=PageOutcome(...)` incremental argument is removed in 0.20;
bulk report entries retain `PageOutcome`.

LAREX validates every output belonging to a page before importing any of them.
Invalid XML, undecodable images, and missing selected targets in scoped XML cause
a durable page failure. The callback returns HTTP 422 with
`code: ACTION_PAGE_RESULT_REJECTED`, which the SDK exposes as `PageResultRejected`.
Replaying that page submission returns the same rejection without importing files.
Authentication, protocol, quota, storage, database, and transport errors remain
fatal. Bulk uploads likewise omit an invalid page's outputs while importing valid
pages; their final response contains the derived overall state.

## Run Reports

Bulk processors pass a typed `RunReport` with one outcome for every selected page:

```python
from larex_actions import PageOutcome, RunIssue, RunReport

report = RunReport(
    pageOutcomes=[
        PageOutcome(pageId="page-1"),
        PageOutcome(pageId="page-2", status="FAILED", message="Invalid XML"),
    ],
    issues=[RunIssue(severity="WARNING", message="Some inputs could not be exported")],
)
await ctx.complete(results, "Export complete", run_report=report)
```

Incremental completion can provide run-level issues; its page outcomes come from
the earlier submissions. Training, evaluation, and integration Actions can also
submit run-level issues, without page outcomes. Evaluation metrics remain in their
separate evaluation report. `ctx.heartbeat()` and `ctx.fail()` accept a report
containing run-level issues, including on fatal termination.

The report schema version is `1`. Issue severities are `WARNING` and `ERROR`.
Report submissions are limited to 10 MiB, messages are bounded and secrets are
redacted. LAREX calculates `total`, `succeeded`, `failed`, `skipped`, `unfinished`,
and `unknown` counts; processors do not supply authoritative counts. Run lists
contain counts, while authenticated details contain the full report.

Historical states are preserved. Acknowledgements without explicit outcomes are
shown as `UNKNOWN`; unaccounted pages in completed legacy bulk runs are also
unknown. LAREX does not infer failures from old log messages.

## Retrying and Official Actions

Retry selects failed and unfinished pages. It excludes successful pages and
deliberate skips, and uses that same selection for the overwrite review and locks.
Runs containing only warnings have nothing to retry. Historical acknowledgements
remain settled; historical bulk runs without page accounting retry their original
selection. Integration work still starts a fresh run and snapshot.

Kraken continues after identifiable page-processing failures and server page
rejections. Missing or invalid shared models and unavailable runtime devices fail
before the page loop. PAGE XML NER continues after invalid XML by default; setting
`continueOnInvalidXml: false` restores stop-on-error behavior.

The development mock Action accepts `failEveryNthPage`: `0` disables simulated
failures, `500` produces two failures in a 1,000-page selection.

## Upgrade Compatibility

Deploy LAREX reporting support and its migrations before adopting reporting
processors. Bulk reporting requires SDK 0.19 or later; the simplified incremental
interface on this page requires 0.20. The packaged development mock uses
`>=0.21.0,<0.22`. Keep service dependency ranges, lockfiles, and installed Action
YAML compatible with the deployed server's capabilities.

When upgrading a processor, test one successful page, one deliberately skipped
page, one recoverable failure, cancellation, and retry. Confirm that successful
pages remain imported and retry selects only failed/unfinished pages before
increasing workload size.
