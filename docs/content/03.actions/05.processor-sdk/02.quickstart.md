## FastAPI processor

```python
import os

from larex_actions import ActionContext
from larex_actions.fastapi import create_larex_action_app


async def process(ctx: ActionContext) -> None:
    action_input = await ctx.pull_input()
    total = len(action_input.pages)
    for index, page in enumerate(action_input.pages, start=1):
        await ctx.heartbeat(
            status_message=f"Processing page {index}/{total}: {page.name}",
            raise_on_cancel=True,
        )
        results = ctx.result_builder()
        if page.xml:
            xml_bytes = await ctx.download_bytes(page.xml[0])
            results.add_xml_bytes(
                page_id=page.id,
                content=xml_bytes,
                file_name=f"{page.name}-processed.xml",
            )
        await ctx.submit_page_results(page.id, results, f"Imported {page.name}")

    await ctx.complete(message="Done")


app = create_larex_action_app(
    processor_id="my-processor",
    dispatch_secret=os.environ["LAREX_DISPATCH_HMAC_SECRET"],
    handler=process,
    max_concurrent_runs=1,
)
```

Each accepted page submission updates progress automatically, so this example
does not pass a percentage to `ctx.heartbeat()`. See
[Progress Reporting](/actions/processor-sdk/progress-and-cancellation#progress-reporting)
for manual updates. Processors that upload everything at the end can call
`await ctx.complete(results, "Done")` once with a bulk result instead.

## Run it

Create a uv project, save the example as `processor.py` inside it, install
the FastAPI extra and an ASGI server, then run it. `uv add` fails with
"No pyproject.toml found" outside a project; skip `uv init` if you are adding
the processor to an existing one.

```bash
uv init --bare --python 3.11 my-processor
cd my-processor
# save the example here as processor.py
uv add "larex-action-sdk[fastapi]" uvicorn
export LAREX_DISPATCH_HMAC_SECRET='replace-with-the-LAREX-endpoint-secret'
export LAREX_ALLOWED_CALLBACK_ORIGINS='https://your-larex-host'
uv run uvicorn processor:app --host 0.0.0.0 --port 9000
```

Register a matching definition through [Admin Setup](/actions/admin-setup): its
`id` must equal `processor_id`, its endpoint must reach `/dispatch`, its
`preflightUrl` must reach `/preflight`, and its `secretRef` must resolve to the
same secret. The example copies XML and therefore needs XML input and enabled
XML output. It demonstrates the transport; replace the copy with your processing.
Explicitly activate the definition for a workspace before running it on a test page.

## Adapter routes

The FastAPI adapter exposes:

- `/dispatch`
- `/preflight`
- `/health` for liveness
- `/parameter-values` for [dynamic parameter values](/actions/processor-sdk/parameter-values)

`/preflight` accepts only a signed LAREX request and returns the processor identity,
Action protocol version, and processor capabilities. Add it as
`endpoint.preflightUrl` so the admin endpoint test verifies authentication and
compatibility rather than only checking liveness.

Set `LAREX_ACTION_ROUTE_PREFIXES` when a reverse proxy preserves a path prefix:

```bash
LAREX_ACTION_ROUTE_PREFIXES=/kraken,/ocr
```

With that setting, the processor also exposes `/kraken/dispatch`,
`/kraken/preflight`, `/kraken/health`, and equivalent `/ocr/*` routes. Do not
strip the prefix before the request reaches the processor, because the signature
includes the path.

## Concurrency and durability

The adapter runs handlers as background work **inside the web process**. A process
restart loses that work; it is not a durable job queue. `max_concurrent_runs`
bounds simultaneous handlers for CPU- or GPU-heavy processors; additional signed
dispatches are still accepted and wait for a slot. Align the Action's
[concurrency limits](/actions/yaml-reference#concurrency) with processor capacity.
For crash-durable queuing, verify dispatches yourself and hand them to a worker
system; see [Framework-Neutral Processors](/actions/processor-sdk/framework-neutral).

Long computations must keep sending heartbeats and checking cancellation; the SDK
does not heartbeat in the background. See
[Progress and Cancellation](/actions/processor-sdk/progress-and-cancellation).

## Processor capabilities

Without `processor_capabilities`, the adapter advertises `incrementalPageResults`,
`customFileResults`, and `runReports`. An explicit mapping replaces these
defaults, so list every feature the handler supports:

```python
app = create_larex_action_app(
    processor_id="my-processor",
    dispatch_secret=secret,
    handler=process,
    processor_capabilities={
        "incrementalPageResults": True,
        "customFileResults": False,
        "runReports": True,
    },
)
```

`parameterValueDiscovery` is added automatically when providers are registered.
Report-mode evaluation processors must advertise `evaluationReports: true`, which
is never a default.

## Environment variables

| Variable | Use |
| --- | --- |
| `LAREX_DISPATCH_HMAC_SECRET` | Shared HMAC secret copied from LAREX endpoint secret creation/rotation. Used when `dispatch_secret` is not passed. |
| `LAREX_ALLOWED_CALLBACK_ORIGINS` | Comma-separated callback origins accepted by the SDK. |
| `LAREX_ACTION_ROUTE_PREFIXES` | Additional route prefixes for the adapter routes. |

Processor-specific implementations may add their own variables, for example a
processor ID, model paths, devices, precision, timeouts, or output variants.
