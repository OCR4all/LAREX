The result builder, page submissions, and output types below apply to
**processing** Actions. Other kinds finish differently:

| Kind | How the run finishes |
| --- | --- |
| `INTEGRATION` | `await ctx.complete(message=...)` without files. Page results, uploaded files, and evaluation reports are rejected by the SDK before sending. See [Integration Actions](/actions/integration#processor-sdk). |
| `TRAINING` | Publish the model to processor-managed storage, then `await ctx.complete(message=...)` without files. See [Dataset Model Training](/actions/training). |
| `EVALUATION` | Submit one report with `ctx.complete_evaluation()`, or run-level result files in `FILES` mode. See [Dataset Model Evaluation](/actions/evaluation#submit-with-the-sdk). |

## Result builder

Use the result builder for files LAREX should import:

```python
results = ctx.result_builder()
results.add_xml_bytes(
    page_id=page.id,
    content=xml_bytes,
    file_name=f"{page.name}-processed.xml",
)
results.add_image_bytes(
    page_id=page.id,
    content=image_bytes,
    variant="processed",
    file_name=f"{page.name}-processed.png",
)
await ctx.complete(results, "Processed pages")
```

`add_xml_path(...)` and `add_image_path(...)` upload files from disk instead.
The Action's YAML must allow every uploaded output type: image results are
rejected unless image output is declared, and XML results unless XML output is
declared. See [Result Import](/actions/result-import) for how LAREX applies them.

## Image variants

A page can receive several images in one submission, for example a binarizer that
writes both a binary and a normalized grayscale image. Give every image of a page
its own variant:

```python
results = ctx.result_builder()
results.add_image_path(page.id, out_dir / "page.bin.png", variant="binary", mime_type="image/png")
results.add_image_path(page.id, out_dir / "page.nrm.png", variant="grayscale", mime_type="image/png")
await ctx.submit_page_results(page.id, results)
```

Each variant replaces the page's existing image with the same name. The SDK
rejects a second image with the same page and variant before uploading. List
every variant the processor may return in the Action YAML; LAREX rejects
undeclared variants:

```yaml
outputs:
  images:
    enabled: true
    variants: [binary, grayscale]
```

## Incremental page results

The example above is the bulk API. For reactive processors, create a fresh
builder per page and submit it as soon as that page succeeds:

```python
for page in action_input.pages:
    await ctx.check_cancelled()
    results = ctx.result_builder()
    # Add this page's XML and/or images when the processor produced output.
    await ctx.submit_page_results(page.id, results, f"Imported {page.name}")

# Final acknowledgement contains no files.
await ctx.complete(message="Processed pages")
```

The SDK refuses `submit_page_results` if the dispatch did not advertise
`capabilities.incrementalPageResults`, so an incremental processor cannot silently
run against an older LAREX. Do not reuse one result builder across pages. Every
file in an incremental submission, including custom files, must carry the
submission's page ID.

### Pages without a result

Sometimes processing succeeds but produces no output. The page must still be
acknowledged; `await ctx.submit_page_results(page.id)` records success without
files. For a deliberate skip, record the reason explicitly:

```python
await ctx.submit_page_results(
    page.id,
    page_status="SKIPPED",
    reason="No eligible content",
)
```

A skipped page counts toward run progress and, for Actions using
`locking.mode: PAGES`, releases that page's lock. It does not create or modify
XML, images, or custom files, and does not make the run have issues.

Do not simply `continue` without calling `submit_page_results`. An incremental
run can only be completed after every page in `action_input.pages` has been
submitted.

## Custom files

LAREX servers that advertise `capabilities.customFileResults` accept arbitrary
durable files. Check the capability before doing expensive postprocessing:

```python
if not ctx.capabilities.custom_file_results:
    raise RuntimeError("This LAREX server does not support custom file results")

results = ctx.result_builder()
results.add_file_bytes(
    content=ner_jsonl,
    file_name="named-entities.jsonl",
    mime_type="application/x-ndjson",
)
results.add_file_path(
    report_path,
    file_name="report.txt",
    mime_type="text/plain",
)
await ctx.complete(results, "Postprocessing complete")
```

Omit `page_id` for project-level files in a bulk or final builder; pass
`page_id=page.id` to associate a file with a page. The client raises
`CustomFileResultsUnsupported` before uploading if the server did not advertise
support.

## Run outcomes

With `capabilities.runReports`, a processor can record recoverable page failures,
deliberate skips, and warnings without stopping the run:

```python
from larex_actions import PageResultRejected, RunIssue, RunReport

# Recoverable failure: acknowledge the page and continue with later pages.
await ctx.submit_page_results(page.id, page_status="FAILED", reason="Invalid input")

# Successful output can still have nonfatal concerns.
await ctx.submit_page_results(page.id, results, warnings=["Low recognition confidence"])

# LAREX already settled this page as failed; continue with the next one.
try:
    await ctx.submit_page_results(page.id, results)
except PageResultRejected:
    pass

await ctx.complete(run_report=RunReport(issues=[RunIssue(message="Some pages had low confidence")]))
```

Each snippet is a separate page submission; a page is acknowledged only once and
duplicate submissions replay the stored outcome. `message` is run progress text,
while `reason` is stored in the page's report. Omitting `page_status` means
success. Failed and skipped pages require a reason and cannot contain files. Do
not catch transport, authentication, or arbitrary runtime errors as recoverable
page failures.

`complete`, `complete_evaluation`, and `upload_results` accept a keyword-only
`run_report`; `heartbeat` and `fail` accept reports with run-level issues. Bulk
processors pass `RunReport(pageOutcomes=[...])` with an outcome for every selected
page. The reporting APIs raise `RunReportsUnsupported` on servers that do not
advertise the capability. Send `completed` normally: LAREX derives
`COMPLETED_WITH_ISSUES` or `FAILED` from the recorded outcomes. See
[Outcomes and Run Reports](/actions/run-reports) for final states, validation,
and retry behavior.

## Rejected results

When LAREX rejects a result callback, the SDK raises `ResultSubmissionError`, an
`httpx.HTTPStatusError` subtype whose message includes a bounded and sanitized
backend response detail. Let the FastAPI adapter log it, or include it in your
own worker logs, to surface the actual manifest, quota, or import validation
failure. The SDK also raises it when LAREX answers an upload with a run that has
already failed, for example after a timeout while LAREX was unreachable, instead
of treating the upload as delivered.

Once cancellation has been requested, the SDK refuses result uploads and
acknowledges the cancellation instead.
