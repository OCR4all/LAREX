## Dispatch Verification

Use `DispatchVerifier` when the processor is not a FastAPI app:

```python
from larex_actions import DispatchVerifier

payload = DispatchVerifier(
    processor_id="my-processor",
    dispatch_secret=secret,
).verify(
    method=request_method,
    path_and_query=request_path_and_query,
    headers=request_headers,
    body=request_body,
)
```

Pass `payload.model_dump(mode="json", by_alias=True)` to your queue or worker
system, then use `ActionClient.from_dispatch(payload)` in async workers. The
client offers the same input, heartbeat, cancellation, and result methods as
`ActionContext`, including `complete_evaluation()`.

This is useful when:

- dispatch should enqueue work and return quickly
- runs must survive a restart of the web process
- the actual processor runs in a worker pool
- the HTTP framework is not FastAPI
- GPU work is scheduled by another runtime

## Security

- Dispatch requests are verified with the `X-LAREX-Action-*` HMAC headers.
- Timestamps and nonces are checked to reduce replay risk.
- The FastAPI adapter rejects dispatch bodies larger than
  `max_dispatch_body_bytes` (1 MiB by default).
- Callback URLs must share one origin and use HTTPS, except for local hosts.
  When `LAREX_ALLOWED_CALLBACK_ORIGINS` is set, that origin must be listed.
- Per-run bearer secrets and dispatch HMAC secrets are never included in model
  representations.
- The Action YAML must still declare the inputs and outputs LAREX should expose
  or accept.

See [Security and Deployment](/actions/security-deployment) for network
placement, secret rotation, and processor hardening.
