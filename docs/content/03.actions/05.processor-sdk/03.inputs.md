## Input Pull

After dispatch, processors pull input from the callback URL in the dispatch payload:

```python
action_input = await ctx.pull_input()
```

The input contains:

- `protocolVersion`
- `runId`
- `processorKey`
- `projectId`, or `datasetId` for dataset Actions
- resolved processor parameters
- pages in processor scope
- page image file descriptors
- page XML file descriptors
- target selection
- resolved input requirements
- image variant selection
- cancellation state
- negotiated capabilities

Files are not embedded in the input response. Download each file descriptor with
`ctx.download_bytes(file)`; the SDK fetches it through its `downloadUrl`.

A parameter declared with `multiple: true` arrives in `action_input.parameters`
as a list of the selected values, which may be empty.

## Target-Aware Runs

LAREX can dispatch `PAGE`, `REGION`, and `TEXT_LINE` targets. The SDK exposes the
requested target on both the dispatch and the pulled input:

```python
payload_target = ctx.payload.target
action_input = await ctx.pull_input()
input_target = action_input.target
```

Processors receive full page images and XML according to the Action definition,
never crops. Target metadata contains the selected region or textline IDs. The
processor resolves geometry from PAGE XML when it wants to crop, mask, pad,
deskew, or process a subset.

Return normal PAGE XML with `add_xml_bytes(...)` or `add_xml_path(...)`. For
region and textline targets, LAREX imports only the selected scope.

## Input Requirements

Input definitions declare whether each file type is unavailable, optional, or
required, including target-specific requirements:

```yaml
inputs:
  images:
    level: required
  xml:
    level: optional
    requiredForTargets:
      - REGION
```

LAREX resolves that contract for the selected target and exposes the resulting
`NONE`, `OPTIONAL`, or `REQUIRED` levels as `ctx.payload.input_requirements` and
`action_input.input_requirements` (serialized as `inputRequirements`). Pages
missing a required input are excluded before dispatch. See
[Inputs](/actions/yaml-reference#inputs) for all options.

## Image Types

A definition may restrict accepted images with `inputs.images.imageTypes`, for
example `[BINARY]`. The effective set is exposed as
`action_input.input_requirements.images.image_types`, and each image `ActionFile`
carries `image_type`: `COLOR`, `GRAYSCALE`, `BINARY`, or `UNKNOWN`. `image.variant`
remains the variant name.

LAREX detects types from file bytes, independently of variant names, and never
converts files. When constraints are present, the SDK rejects supplied images
with missing, unknown, or incompatible types. Older payloads without these fields
default to unrestricted requirements. See
[Image types](/actions/yaml-reference#image-types) for the detection rules.

## Dataset Items

Training and evaluation Actions receive a dataset instead of a project. Their
payloads expose `dataset_id` instead of `project_id`, and dispatches include
`dataset_item_ids`. Each pulled input page represents one dataset item:

| Field | Meaning |
| --- | --- |
| `page.id` | Dataset item ID. Use it for evaluation sample references. |
| `page.source_page_id` | Source page of the item. |
| `page.split` | `TRAIN`, `VAL`, or `TEST`. |

Each item contains exactly one PAGE XML file. Training items contain one frozen
image by default; evaluation items contain images according to
`inputRequirements.images.level`, which can be `NONE` for XML-only evaluation.
Definitions with `inputs.images.multiple: true` can receive several frozen images
per item. See [Dataset Model Training](/actions/training) and
[Dataset Model Evaluation](/actions/evaluation).
