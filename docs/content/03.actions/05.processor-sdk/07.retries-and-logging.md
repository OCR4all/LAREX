## Retry Policy

The SDK retries connection failures and transient HTTP responses (`408`, `429`,
`502`, `503`, and `504`) with exponential backoff and jitter. Pass a
`RetryPolicy` as `retry=` to `ActionClient` or `ActionClient.from_dispatch(...)`
to change the defaults:

```python
from larex_actions import ActionClient, RetryPolicy

client = ActionClient.from_dispatch(
    payload,
    retry=RetryPolicy(result_window=1800, heartbeat_failure_grace=600),
)
```

With the FastAPI adapter, pass the policy to the app:

```python
app = create_larex_action_app(
    processor_id="my-processor",
    handler=process,
    retry=RetryPolicy(heartbeat_failure_grace=600),
)
```

A `client_factory` builds its own client, so it cannot be combined with `retry=`;
pass the policy inside the factory instead.

| Field | Default | Meaning |
| --- | --- | --- |
| `backoff` | `0.5` | First wait in seconds; it doubles per attempt. |
| `max_backoff` | `30` | Longest wait between two attempts. |
| `read_attempts` | `3` | Attempts for `pull_input()` and file downloads. |
| `heartbeat_attempts` | `3` | Attempts per heartbeat. |
| `heartbeat_request_timeout` | `15` | Timeout of one heartbeat request, with at most 5 seconds to connect. |
| `heartbeat_failure_grace` | LAREX's `heartbeatTimeoutSeconds` | How long heartbeats may fail before the SDK raises. `client.heartbeat_failure_grace` shows the value in use. |
| `result_window` | `900` | Seconds that result uploads keep retrying. |
| `result_max_attempts` | `None` | Optional cap on result upload attempts. |

## Retry Behavior

- **Result uploads** keep retrying for up to 15 minutes, so a LAREX restart at the
  end of a long run does not lose its results. Path-based files are reopened for
  every attempt, and LAREX accepts a repeated upload of the same page or of the
  final result without importing it twice. While an upload retries, the SDK logs
  a warning on the `larex_actions.client` logger at most once a minute.
- **Input pulls and downloads** retry three times. A download that breaks off
  midway starts over and overwrites the partial file.
- **Heartbeats** retry three times with a short timeout so a cancellation check
  never blocks for long. A retried heartbeat whose first attempt reached LAREX
  may append its `log` line twice. See
  [Outages](/actions/processor-sdk/progress-and-cancellation#outages) for how
  failing heartbeats are tolerated.

The client arguments `result_max_attempts`, `result_retry_backoff`, and
`result_retry_max_backoff` are deprecated; they still work and override the
matching `RetryPolicy` fields.

## Transport Logging

The SDK uses Python's standard `logging` module for optional transport
diagnostics. Records are emitted at `DEBUG` on the `larex_actions.transport`
logger, so normal processor output remains unchanged until the application
enables that logger. The library does not configure the root logger or install
handlers.

When the processor already configures a root handler, enabling the named logger
is enough:

```python
import logging

logging.getLogger("larex_actions.transport").setLevel(logging.DEBUG)
```

For a Uvicorn or Docker process where the root logger has no handler, attach a
stream handler in the processor's startup code. `StreamHandler` writes to stderr,
which Docker and process supervisors collect alongside stdout:

```python
import logging

sdk_transport_logger = logging.getLogger("larex_actions.transport")
sdk_transport_logger.setLevel(logging.DEBUG)
sdk_transport_logger.addHandler(logging.StreamHandler())
sdk_transport_logger.propagate = False
```

Transport records identify operations such as input pulls, heartbeats, downloads,
page-result submissions, completion uploads, retries, and failures. They include
safe metadata when available, such as run and page IDs, result status and file
type counts, HTTP status, duration, and retry attempt. They never include
authorization headers, request or response bodies, file contents, or callback or
download URLs.

Transport logging is local only: it does not send extra heartbeats or other
requests to LAREX. It shows when an SDK call succeeds, fails, or is retried, but
not what the processor does between calls. Use application logging for that, or
`ctx.heartbeat(...)`/`ctx.log(...)` when the progress should also appear in LAREX.
