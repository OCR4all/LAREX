## Progress Reporting

`progress_percent` on `ctx.heartbeat()` and `ctx.log()` is an optional, absolute
percentage of the entire Action run. `25` means 25% overall, not an increase of
25% or progress within the current page. Omitting it leaves the stored percentage
unchanged; you can still send status text. LAREX ignores decreases, clamps running
progress to 0–99%, and sets 100% on completion.

Each `ctx.heartbeat()` call sends one update; the SDK does not heartbeat in the
background. Long operations need their own periodic heartbeats and cancellation
checks. Uncaught exceptions are reported as a failed run by the runtime, so there
is no need to send a separate failure update.

`ctx.submit_page_results()` automatically advances progress from the fraction of
settled pages, including failed and skipped pages, up to 99%. Manual updates and
automatic page progress share the same overall percentage; the higher value wins.
There is currently no way to reserve part of the range for preparation or
postprocessing.

Manual percentages are useful when uploading all results at the end, or for
training and other Actions whose progress cannot be inferred from page results.
For example, a training processor can use 0–10% for preparation, 10–90% for
epochs, and 90–99% for validation and publication. The functions below represent
application-specific work:

```python
await ctx.heartbeat(0, "Preparing training data", raise_on_cancel=True)
await prepare_training_data()

await ctx.heartbeat(10, "Training", raise_on_cancel=True)
for epoch in range(total_epochs):
    await train_epoch(epoch)
    await ctx.heartbeat(
        progress_percent=10 + ((epoch + 1) * 80) // total_epochs,
        status_message=f"Epoch {epoch + 1}/{total_epochs}",
        raise_on_cancel=True,
    )

await ctx.heartbeat(90, "Validating and publishing model", raise_on_cancel=True)
await validate_and_publish_model()

await ctx.complete(message="Model published")
```

Choose a positive `total_epochs`. These percentages are estimates of overall work,
not elapsed time; omit them if no useful estimate is available.

## Cancellation

Cancellation is cooperative. LAREX marks a run as cancellation requested, and the
processor observes that state through heartbeat responses
(`cancelRequested: true`).

```python
await ctx.check_cancelled()
```

or:

```python
await ctx.heartbeat(progress_percent=50, status_message="Halfway", raise_on_cancel=True)
```

Both raise `ActionCancelled` when a cancellation is pending.

- Check cancellation at safe interruption points.
- `ctx.check_cancelled()` sends a heartbeat only when the last successful one is
  older than `cancel_check_interval` (one second by default) and otherwise returns
  immediately, so it is cheap in a polling loop. Keep the interval at a second or
  more, because every recorded heartbeat is a database write in LAREX.
- On cancellation, stop work. The SDK refuses result uploads and acknowledges the
  cancellation instead.

### External Commands

`ctx.run_subprocess(command, timeout=..., cancel_poll_seconds=5)` polls for
cancellation while a child process runs. On cancellation it sends a final
`status="cancelled"` heartbeat and terminates the child gracefully before
escalating to `kill`. CPU-heavy in-process work needs its own execution and
heartbeat design.

## Heartbeat Timing

The dispatch payload advertises `heartbeatTimeoutSeconds`: how long LAREX waits
without a heartbeat before its watchdog fails the run (default 1800, set by
`larex.actions.timeout.heartbeat-minutes`). Protocol version 1 processors must
treat the field as optional and fall back to 1800 seconds when it is absent.
Keep heartbeats well inside that window.

A heartbeat without progress, status message, log, or run report is a liveness
check. When it arrives within 5 seconds of the last recorded heartbeat, LAREX
answers with the current cancellation state without updating the run, so frequent
`check_cancelled()` calls are cheap. Such checks therefore do not reset the
watchdog more than once per 5 seconds, which is far below the timeout. LAREX only
pushes run updates to browsers when status, progress, status message, logs, or the
run report change.

Each recorded heartbeat also extends the run secret by 24 hours, so runs may last
longer than a day as long as they keep heartbeating. Result uploads do not extend
the secret.

## Outages

A cancellation check or a running `ctx.heartbeat()`/`ctx.log()` that cannot reach
LAREX, or gets a `5xx`, `408`, or `429` response, logs a warning and returns
instead of raising, so a short outage or a LAREX restart does not end a long run.
That update's progress, status message, and log line are lost; the next heartbeat
carries the current state again. Heartbeats with a `run_report`, `ctx.fail()`, and
the cancellation acknowledgement still raise.

The SDK raises once no heartbeat has succeeded for `heartbeatTimeoutSeconds`,
because LAREX has failed the run by then, and right away when LAREX rejects the
run itself, for example with `401` or `403`. Without the field, the SDK waits 30
minutes. See [Retries and Logging](/actions/processor-sdk/retries-and-logging) to
override this grace period.

To react to an outage yourself, for example to save a checkpoint before giving
up, read `ctx.seconds_since_last_heartbeat`. It counts from the last successful
heartbeat, or from the start of the run if none has succeeded yet:

```python
await ctx.check_cancelled()
if ctx.seconds_since_last_heartbeat > 300:
    save_checkpoint()
    raise RuntimeError("LAREX has been unreachable for 5 minutes")
```

To have the SDK raise sooner instead, set a shorter `heartbeat_failure_grace`;
`0` raises as soon as a heartbeat's retries fail.
