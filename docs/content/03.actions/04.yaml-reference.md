# YAML Reference

Action definitions are strict YAML documents. Unknown fields are rejected. The only supported definition version is `1`.

One schema covers all four [Action kinds](#action-kind): `PROCESSING`, `INTEGRATION`, `TRAINING`, and `EVALUATION`. Most fields mean the same in every kind, but `kind` changes which blocks are required, allowed, or rejected. Check [Fields by kind](#fields-by-kind) before writing a non-processing definition. The complete example below is a processing Action; [minimal definitions](#minimal-definitions) for every kind are at the end of this page.

## Complete Example (processing)

```yaml
version: 1
id: ocr-inference
name: OCR Inference
kind: PROCESSING
description: Run OCR on selected page images.
info: Only use binarized and grayscale images.
tags: [ocr, htr]
targets:
  - PAGE
  - REGION
  - TEXT_LINE

endpoint:
  url: https://ocr.example.org/dispatch
  healthUrl: https://ocr.example.org/health
  preflightUrl: https://ocr.example.org/preflight
  timeoutSeconds: 30
  auth:
    type: hmac
    secretRef: ocr-processor-v1

access:
  execute: CURATOR

locking:
  mode: PAGES

inputs:
  images:
    level: required
  xml:
    level: optional
    requiredForTargets:
      - REGION

outputs:
  xml:
    enabled: true
  images:
    enabled: false
  files:
    enabled: false

concurrency:
  maxActiveRuns: 1
  scope: PROJECT

runtime:
  model:
    name: default
    optional: true

parameters:
  threshold:
    type: number
    default: 0.5
    min: 0
    max: 1
    description: Minimum recognition confidence.
```

Replace `secretRef` with a configured endpoint secret before saving the definition.

## Top-Level Fields

| Field | Required | Default | Validation |
| --- | --- | --- | --- |
| `version` | Yes | none | Must be `1`. |
| `id` | Yes | none | `[a-zA-Z0-9][a-zA-Z0-9._-]{1,126}` and unique. |
| `name` | Yes | none | Non-blank text. |
| `description` | No | none | Text shown in the UI. |
| `info` | No | none | Plain-text message shown in an info alert after selecting the Action, above its configuration. Multiline YAML strings preserve line breaks; blank messages are hidden. |
| `kind` | No | `PROCESSING` | One of `PROCESSING`, `TRAINING`, `EVALUATION`, `INTEGRATION`. See [Action Kind](#action-kind). |
| `tags` | No | `[]` | Free-form array of non-blank strings, used to filter Actions. Labels are trimmed and duplicates removed. |
| `targets` | No | `[PAGE]` | One or more of `PAGE`, `REGION`, `TEXT_LINE`. Duplicate values are ignored. Training and evaluation run on dataset items, which are whole pages, and resolve inputs at `PAGE` level, so declare `[PAGE]`. Integration Actions need `PAGE` to run on datasets. |
| `endpoint` | Yes | none | Endpoint object. |
| `access` | No | `CURATOR` | Execution role object. |
| `locking` | Depends on kind | `PAGES` | Locking object. Integration, training, and evaluation must set `mode: NONE` explicitly. |
| `inputs` | Yes | none | At least one input type must be enabled, in every kind. Evaluation requires both images and XML. |
| `outputs` | Processing only | none | Processing requires at least one enabled output type. Integration rejects the block entirely. Training and evaluation reject any enabled output; omit the block. |
| `training` | Training only | none | Training split requirements. Required for `TRAINING`, rejected for every other kind. |
| `evaluation` | Evaluation only | none | Output mode (`REPORT` by default or `FILES`), report profile/version, and split requirements. Required for `EVALUATION`, rejected for every other kind. |
| `concurrency` | No | one active run per project | Concurrency object. |
| `runtime` | No | none | Metadata currently parsed and stored. |
| `parameters` | No | `{}` | Parameter definitions. |

## Action Kind

```yaml
kind: PROCESSING
```

`kind` defaults to `PROCESSING` when omitted. It controls the run resource, locking rules, and result contract; tags do not affect these behaviors.

| Kind | Definition requirements | Result contract |
| --- | --- | --- |
| `PROCESSING` | Use `locking.mode: PAGES` (the default) or `PROJECT`. Enable at least one of `outputs.xml`, `outputs.images`, or `outputs.files`. | Returns declared XML, images, or files for import into the project. |
| `INTEGRATION` | Set `locking.mode: NONE`, omit `outputs`, `training`, and `evaluation`, and enable image and/or XML inputs. | Performs external work on frozen project/editor or dataset inputs and returns status feedback. See [Integration Actions](/actions/integration). |
| `TRAINING` | Set `locking.mode: NONE`, omit `outputs`, and declare `training.splits` with `TRAIN: required`. | Publishes the model to processor-managed storage and completes without uploaded files. |
| `EVALUATION` | Set `locking.mode: NONE`, omit `outputs`, require both image and XML inputs for `PAGE`, and declare `evaluation` with at least one accepted split and a profile for report mode. | Returns one structured `evaluationReport` (default), or one or more downloadable files with `evaluation.outputMode: FILES`. |

### Fields by kind

| Field | `PROCESSING` | `INTEGRATION` | `TRAINING` | `EVALUATION` |
| --- | --- | --- | --- | --- |
| `locking.mode` | `PAGES` (default) or `PROJECT` | `NONE`, set explicitly | `NONE`, set explicitly | `NONE`, set explicitly |
| `outputs` | Required, at least one type enabled | Not allowed, not even with every type disabled | Omit; enabled types are rejected | Omit; enabled types are rejected |
| `outputs.xml.overwrites` | Optional, needs XML output | Not allowed | Not allowed | Not allowed |
| `inputs` | At least one type | At least one type | At least one type | Images **and** XML required for `PAGE` |
| `training` | Not allowed | Not allowed | Required, `TRAIN: required` | Not allowed |
| `evaluation` | Not allowed | Not allowed | Not allowed | Required |
| `targets` | Any | Any; must include `PAGE` for datasets | `[PAGE]` (inputs resolve at page level) | `[PAGE]` (inputs resolve at page level) |
| Runs on | Project/editor selection | Project/editor selection or dataset | Dataset | Dataset |
| Activation | Workspace or single project | Workspace or single project; datasets need workspace-wide activation | Workspace-wide only | Workspace-wide only |

`endpoint`, `access`, `concurrency`, `parameters`, `runtime`, `tags`, `info`, and the input options (`level`, `requiredForTargets`, `multiple`, `imageTypes`) work the same in every kind. `inputs.images.multiple` applies to every kind; training and evaluation still receive exactly one PAGE XML file per item.

Training and evaluation use dataset items as inputs instead of project page selections. Their input files are frozen for the run. The `training` and `evaluation` blocks are valid only for their corresponding kinds.

For complete definitions, split options, and processor examples, see [Dataset Model Training](/actions/training) and [Dataset Model Evaluation](/actions/evaluation).

## Endpoint

```yaml
endpoint:
  url: https://processor.example.org/dispatch
  healthUrl: https://processor.example.org/health
  preflightUrl: https://processor.example.org/preflight
  parameterValuesUrl: https://processor.example.org/parameter-values
  timeoutSeconds: 30
  auth:
    type: hmac
    secretRef: processor-v1
```

| Field | Required | Default | Validation |
| --- | --- | --- | --- |
| `endpoint.url` | Yes | none | HTTP/HTTPS URL, host required, no credentials, no fragment. |
| `endpoint.healthUrl` | No | none | Same URL validation as `endpoint.url`. |
| `endpoint.preflightUrl` | No | none | Signed `POST` endpoint used by **Test endpoint** to verify HMAC auth, processor identity, protocol version, and required capabilities. |
| `endpoint.parameterValuesUrl` | For dynamic allowed values | none | Signed `POST` endpoint used to discover authoritative parameter choices. |
| `endpoint.timeoutSeconds` | No | `30` | Integer `1..300`. |
| `endpoint.auth.type` | No | `none` | `none` or `hmac`. External endpoints must use `hmac`. |
| `endpoint.auth.secretRef` | For HMAC | none | Must match the endpoint-secret reference pattern and resolve to a configured secret. |

Endpoint policy:

- Configure `preflightUrl` for SDK-based processors. LAREX signs the preflight
  exactly like a dispatch and validates the structured response. When it is
  omitted, **Test endpoint** falls back to the unauthenticated `healthUrl` (or a
  `HEAD` request to `url`), which proves reachability only.

- External endpoints must use HTTPS.
- Local/private endpoints may use HTTP when insecure local endpoints are allowed.
- If `LAREX_ACTIONS_ENDPOINT_ALLOWED_ORIGINS` is configured, the endpoint origin must be listed.
- URLs must not contain username/password credentials or fragments.

## Access

```yaml
access:
  execute: CURATOR
```

| Value | Meaning |
| --- | --- |
| `EDITOR` | Any workspace member can run the Action. |
| `CURATOR` | Only users who can manage projects in the workspace can run it. |

Default is `CURATOR`.

## Locking

```yaml
locking:
  mode: PAGES
```

| Value | Meaning |
| --- | --- |
| `PAGES` | Lock only affected pages. |
| `PROJECT` | Lock the entire project. |
| `NONE` | No page or project locks; required for integration, training, and evaluation. |

Default is `PAGES`, which is valid only for processing. Processing Actions must use `PAGES` or `PROJECT`. Integration, training, and evaluation Actions must set `NONE` explicitly; omitting `locking` gives them `PAGES` and fails validation.

## Inputs

```yaml
inputs:
  images:
    level: required
  xml:
    level: optional
    requiredForTargets:
      - REGION
```

At least one input type must be enabled, in every kind. Evaluation Actions must require both images and XML for `PAGE`.

| Level | Meaning |
| --- | --- |
| `none` | Do not expose this input for the selected target. |
| `optional` | Expose the input when available; missing data does not exclude a page or dataset item. |
| `required` | Exclude pages or dataset items that do not provide this input. |

`requiredForTargets` overrides the base level to `required` for the listed targets. Each target must also appear in the top-level `targets` list. This supports processors that can create PAGE XML for a full page but need existing XML geometry for region-scoped processing.

Legacy booleans remain supported: `true` maps to `optional`, while `false` maps to `none`. New definitions should use explicit levels so the run dialog can show accurate compatibility messages.

When image input is active for the selected target, users can choose image variants globally or per page (per dataset item for dataset Actions). By default, each page or item receives at most one image. To accept multiple image variants, opt in explicitly:

```yaml
inputs:
  images:
    level: required
    multiple: true
  xml:
    level: optional
```

`inputs.images.multiple` is a boolean and defaults to `false`, including for legacy boolean and level-only input declarations. It applies to processing, integration, training, and evaluation Actions. The frontend enables multi-selection only for Actions declaring `true`; the backend rejects multiple selections for single-image Actions. `multiple` is not supported on XML inputs.

LAREX sends the resolved levels and image multiplicity in dispatch and pull-input payloads as `inputRequirements`. The Python SDK validates `inputRequirements.images.multiple`; `page.images` remains a list in either mode. Actions opting in must handle every supplied image. Training and evaluation still receive exactly one PAGE XML file per item. When several selected variants are available on a page, they are all sent; fallback applies only when none match.

### Image types

Variants identify images by name; `imageTypes` independently restricts their detected processing type:

```yaml
inputs:
  images:
    level: required
    imageTypes: [BINARY]
```

`imageTypes` is an optional, nonempty list of `COLOR`, `GRAYSCALE`, or `BINARY`. Values are case-insensitive and duplicates are removed. Omission accepts all encodings, including unknown types. Type matching is exact: use `[GRAYSCALE, BINARY]` to accept both. The field is invalid on XML or disabled image inputs.

LAREX inspects color models, sample depth, and palettes. Grayscale images containing only exact black and white samples are `BINARY`, including the eight-bit 0/255 output commonly written by binarizers. Grayscale images with any intermediate intensity remain `GRAYSCALE`; the check examines every pixel without subsampling. One-bit grayscale and black/white palettes can be recognized directly. Colored palettes are color even at one bit. Alpha does not count as a color channel. RGB images remain `COLOR`, including those whose pixels appear grayscale. Unrecognized or unreadable images are `UNKNOWN`, which cannot satisfy a type constraint. Files are never converted automatically.

Type filtering happens before variant matching and fallback. Without an explicit variant selection, a constrained Action automatically receives the first compatible image in stable variant/filename/ID order, or all compatible images when `multiple: true`. Fallback cannot bypass the type constraint. Required-image pages without compatible inputs are listed as skipped; optional image inputs may be empty. Dataset selections with incompatible explicit image IDs fail validation.

Dispatch and pull-input `inputRequirements.images.imageTypes` contain the effective accepted types. Each image file in pull inputs additionally exposes `imageType`. Copied datasets and frozen inputs preserve this metadata independently of their source. These fields are additive to protocol version 1; definitions without them retain their existing behavior.

Existing files are inspected in the background, up to 25 rows per image table per batch, and immediately when needed for selection or image metadata. Bulk page and dataset listings return cached types, with `imageType: null` while inspection is pending. Opening an individual image listing or validating an Action resolves pending types immediately. Read-only validation uses the detected result without writing; the background worker persists it later. Pending records remain eligible for server review; required-type dropdowns offer only confirmed matches. The server enforces the actual type before execution. Metadata inspection does not change content timestamps. Server configuration can disable background inspection with `larex.images.backfill-enabled: false`, or change its default ten-second delay with `larex.images.backfill-delay-ms`.

## Outputs

```yaml
outputs:
  xml:
    enabled: true
  images:
    enabled: true
    variant: action-copy
  files:
    enabled: true
```

`outputs` applies to processing Actions only. A processing Action must enable at least one output type. Other kinds return results through their own contracts:

- **Integration:** status and a completion message only. Any `outputs` block is rejected, including one with every type disabled or with `overwrites`.
- **Training:** the processor publishes the model to its own storage. Enabled outputs are rejected; omit the block.
- **Evaluation:** a report or files, controlled by `evaluation.outputMode`. Enabled outputs are rejected; omit the block.

Output import behavior for processing Actions is fixed: PAGE-targeted XML replaces the existing page XML after creating a version snapshot; REGION and TEXT_LINE results replace their selected annotation scope. Images replace existing images with the same result variant. Use `overwrites` to describe potential annotation replacement or deletion.

| Field | Required when enabled | Default | Validation |
| --- | --- | --- | --- |
| `outputs.xml.enabled` | No | `false` | Boolean. |
| `outputs.images.enabled` | No | `false` | Boolean. |
| `outputs.images.variant` | Yes for image output | none | `[a-zA-Z0-9][a-zA-Z0-9._-]{0,63}`. |
| `outputs.files.enabled` | No | `false` | Boolean. Enables arbitrary durable files in the project Outputs panel. |

Result uploads are still validated against the processor declaration. A processor cannot upload XML, images, or custom files unless the corresponding output is enabled. Custom outputs are a flat file collection in version 1; archive directory-shaped results before returning them.

### Annotation overwrite declarations

XML-producing processing Actions can optionally declare annotation levels they may replace or delete, per supported target:

```yaml
outputs:
  xml:
    enabled: true
    overwrites:
      PAGE: [REGIONS, READING_ORDER]
      REGION: [TEXT_LINES]
      TEXT_LINE: [TEXT]
```

Supported levels are `REGIONS`, `TEXT_LINES`, `BASELINES`, `TEXT`, `WORDS`, `GLYPHS`, and `READING_ORDER`. `TEXT` includes nonempty text alternatives at region, line, word, and glyph levels. `READING_ORDER` means explicit PAGE reading-order structures containing region references, including references in nested groups. Empty groups do not trigger an overwrite warning. Metadata and custom attributes are not modeled.

Replacing structural levels includes descendants: regions include textlines, baselines, words, glyphs, and text; textlines include baselines, words, glyphs, and text; words include glyphs and text; glyphs include text. LAREX warns only about affected levels actually present in the import scope. REGION imports preserve the selected region itself and replace its textlines and nested regions; TEXT_LINE imports replace only selected lines.

Each target key must appear in `targets`, and XML output must be enabled. Unknown targets/levels and null lists are rejected. Duplicate levels are normalized. An explicit empty list (`PAGE: []`) declares no overwrite risk. A missing target declaration produces a generic warning when XML already exists. These declarations are advisory, not import restrictions; declare the union of potential effects across parameters.

Before starting or retrying, the UI previews eligible pages and lets users exclude affected pages. Failed annotation inspection falls back to a generic warning. Existing API clients can continue to start runs directly; the preview is informational and reflects annotations at preview time.

This extension keeps definition version `1` and does not change the processor wire protocol. Deploy LAREX schema support before installing YAML that uses `overwrites`.

### Upgrading existing definitions

Before deploying a version with this schema, manually remove `outputs.xml.mode` and `outputs.images.mode` from each existing Action's YAML and save it through the current admin UI. Verify that the stored `yaml_source` and `parsed_json` omit both fields. The old serializer may retain JSON keys with null values; remove those keys from stored parsed JSON as well before upgrading. Keep other mode settings, such as `locking.mode`, intact.

There is no automatic migration or legacy compatibility path. Definitions containing the removed fields are rejected by the new parser, including stored parsed JSON.

### Replacing categories with tags

Flyway migration V35 removes the former top-level `category` field from stored YAML and parsed JSON, sets tags to `[]`, and removes the database category column. Existing categories are discarded. YAML may be reformatted, but other fields retain their meaning. New or edited definitions must use `tags` instead of `category`; category is rejected by the parser. Tags are independent of Action kind and do not change the processor protocol.

| Field | Default | Validation |
| --- | --- | --- |
| `maxActiveRuns` | `1` | Integer `1..100`. |
| `scope` | `PROJECT` | `PROJECT`, `WORKSPACE`, or `GLOBAL`. |

## Runtime Metadata

```yaml
runtime:
  model:
    name: default
    optional: true
```

`runtime.model.name` and `runtime.model.optional` are parsed and stored as metadata. They can document the expected model or tell admins that model configuration is optional, but current run parameter resolution is based on `parameters`.

## Parameters

```yaml
parameters:
  threshold:
    type: number
    default: 0.5
    min: 0
    max: 1
    description: Minimum confidence.
    required: false
  model:
    type: string
    default: model-a
    allowedValues:
      provider: models
```

| Field | Default | Validation |
| --- | --- | --- |
| Parameter name | none | `[a-zA-Z0-9][a-zA-Z0-9._-]{0,63}`. |
| `type` | `string` | `string`, `number`, `integer`, or `boolean`. |
| `default` | Type default | Must match type and numeric range. |
| `min` | none | Numeric lower bound. |
| `max` | none | Numeric upper bound; must be >= `min`. |
| `description` | none | Help text. |
| `required` | none | Parsed as metadata. |
| `allowedValues.values` | none | A non-empty list of up to 1,000 choices. Each choice contains a unique `value` matching the parameter type and a display `label` (1–256 characters). The effective default must be one of the listed values. |
| `allowedValues.provider` | none | Identifier of a provider exposed by `endpoint.parameterValuesUrl`; mutually exclusive with `values`. |

### Fixed allowed values

For a hardcoded set of choices, use `allowedValues.values` instead of
`allowedValues.provider`:

```yaml
parameters:
  ocrModel:
    type: string
    default: "Processor default"
    description: "Calamari OCR model; the processor default uses its pre-configured model."
    allowedValues:
      values:
        - value: "Processor default"
          label: "Processor default"
        - value: "model-a"
          label: "Model A"
        - value: "model-b"
          label: "Model B"
```

Replace `model-a` and `model-b` with identifiers your processor accepts. The UI
displays `label` and sends `value` to the processor. Each `value` must match the
parameter's `type`; `label` is always a non-blank string. For example, an integer
choice uses `value: 1`, not `value: "1"`.

YAML's abbreviated syntax (flow collections) is also supported. This is equivalent
to the `allowedValues` block above:

```yaml
allowedValues:
  values:
    - { value: "Processor default", label: "Processor default" }
    - { value: "model-a", label: "Model A" }
    - { value: "model-b", label: "Model B" }
```

Each choice needs both the `value:` and `label:` keys, including in abbreviated
syntax. A list of plain strings such as `values: ["model-a", "model-b"]` does not
match the required structure.

Configure exactly one of `values` or `provider`. For fixed choices, `default` must
match a listed `value`, not its label. If `default` is omitted, the type default
listed below must be present among the choices.

### Default runtime values

| Type | Default when `default` is omitted |
| --- | --- |
| `string` | empty string |
| `number` | `0.0` |
| `integer` | `0` |
| `boolean` | `false` |

The run dialog initializes parameters from these defaults. Static and dynamic
allowed values render as searchable selects while preserving their primitive
types. Dynamic values are fetched when the Action is selected, can be refreshed,
and are fetched again before run creation. A processor outage, empty provider, or
stale selection blocks the run rather than falling back to free text.

## Validation Messages

Common validation failures:

| Path | Cause |
| --- | --- |
| `version` | Missing or not `1`. |
| `id` | Invalid format or duplicate processor ID. |
| `endpoint.url` | Missing, invalid, non-HTTP(S), contains credentials/fragment, or violates origin/HTTPS policy. |
| `endpoint.auth` | External endpoint configured without HMAC. |
| `endpoint.auth.secretRef` | Missing, invalid, or no matching secret is configured. |
| `kind` | Not one of `PROCESSING`, `TRAINING`, `EVALUATION`, `INTEGRATION`. |
| `locking.mode` | Processing uses `NONE`; integration, training, or evaluation uses anything else, including the `PAGES` default when `locking` is omitted. |
| `inputs` | Neither images nor XML enabled; for evaluation, images or XML not required for `PAGE`. |
| `outputs` | Processing has no enabled XML, image, or file output; integration declares an `outputs` block at all; training or evaluation enables an output type. |
| `outputs.xml.overwrites` | XML output not enabled, target not declared in `targets`, or unknown level. |
| `training`, `evaluation` | Block used with the wrong kind, or missing for its own kind. |
| `training.splits.TRAIN` | Not `required`. |
| `evaluation.splits` | Missing, or every split is `none`. |
| `evaluation.profile` | Missing in `REPORT` mode. |
| `endpoint.parameterValuesUrl` | Missing although a parameter uses `allowedValues.provider`. |
| `concurrency.maxActiveRuns` | Outside `1..100`. |
| `parameters.*.default` | Does not match type or numeric range. |
| `parameters.*.allowedValues` | Both/neither source configured, invalid/duplicate choices, type mismatch, or static default not present. |
