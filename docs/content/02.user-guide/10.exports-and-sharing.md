# Exports, releases, and sharing

Save annotation changes before exporting. An export reads persisted project data; it does not capture unsaved editor changes.

## Choose by purpose

| You need | Choose | What to expect |
| --- | --- | --- |
| Current images and XML as ordinary files | Basic project export | Flat ZIP using original filenames. |
| A document for reading, analysis, or another tool | Converted output | Text, PDF, ALTO, TEI, DOCX, CSV, or XLSX, with options appropriate to that format. |
| An editable project for re-import | LAREX project package | Structured ZIP with project/page descriptors and optional assigned resources/history. |
| A stable project delivery | Project release | Frozen package with version metadata and sharing controls. |
| Curated pages with train/validation/test splits | Dataset package or dataset release | Dataset manifest, selected files, and split lists. |
| A working project in another workspace | Project transfer | A move/copy request approved in the receiving workspace. |

A package export is not a complete server backup. Use the [administrator backup workflow](/user-guide/admin-dashboard/workspaces-import-backup) for instance recovery.

## Export a project or page

1. Open the project export menu, or the page's export action.
2. Choose the output type and scope the dialog offers.
3. Review format options and image variants.
4. Start the export and follow its progress in **Jobs**.
5. Open the downloaded artifact and check representative pages before handing it off.

For text-based outputs, choose the text level and any offered variant/index options deliberately. Reading order, available transcription, and layout affect the result. A conversion cannot preserve every PAGE XML construct in every target format.

For PDFs, the dialog offers **Searchable**, **Images only**, **Text pages**, and **PDF/A searchable** profiles. Select an image variant globally or per page. With **Fallback image** enabled, a missing selected variant uses the page's first available image; without it the affected page is omitted. Confirm the page count in the result.

TEI offers standard and layout-aware profiles. Spreadsheet exports offer page metadata, tags, or regions. Choose an output that matches the recipient's need; keep PAGE XML or a package when layout fidelity and future editing matter.

## Preserve an editable project

Choose a **LAREX package** for structured re-import. It contains readable page folders, `manifest.json`, `page.json` descriptors, and declared assets. Assigned resources can travel with the package. Optional converted outputs go in `exports/` and are not imported as project content.

Enable **Include PAGE XML version history (archival)** if you need older saved annotations. It is off by default for regular and batch package exports. Project releases include history by default.

When editing an extracted package, update JSON descriptors for every added, removed, or renamed file before re-zipping it. LAREX rejects inconsistent, duplicate, missing, undeclared, or unsafe paths. See the [package and import reference](/user-guide/projects#export-or-transfer-a-project) for conflict and resource-reuse choices.

## Create and share a project release

Curators can create a versioned project release from the project's release controls. Releases always include the full project; the current page selection is ignored. Add a useful version tag and notes, wait for a ready artifact, and verify the downloaded package.

A release records a stable delivery. Correcting the working project afterward requires a new release when you want to distribute the correction.

Release sharing uses an expiring secret. Keep the supplied URL and secret together only for intended recipients. The public share flow asks for the secret before downloading. Curators can rotate, extend, or revoke the share. Revocation stops future access through that credential; it cannot retract files already downloaded.

For dataset release procedures and their separate annotation copies, see [Datasets and releases](/user-guide/datasets).

## Transfer work between workspaces

A curator can request **copy** or **move** from project sharing controls. The receiving workspace reviews the request in **Workspace Settings → Requests**. The sender can track outgoing requests and cancel a pending request.

Use copy when both workspaces need independent working versions. Use move when the receiving workspace should own the working project. A workspace transfer is different from sharing a frozen release with an external recipient.

Resolve destination naming conflicts in the transfer review rather than deleting the existing project first. For invitations and your own transfer requests, see [Account settings](/user-guide/account-and-notifications).
