Save annotation changes before exporting. An export reads persisted project data; it does not capture unsaved editor changes.

## Choose by purpose

| You need | Choose | What to expect |
| --- | --- | --- |
| Current images and XML as ordinary files | Basic project export | Flat ZIP using original filenames. |
| A document for reading, analysis, or another tool | Converted output | Text, PDF, ALTO, FineReader XML, hOCR, TEI, DOCX, CSV, or XLSX, with options appropriate to that format. |
| An editable project for re-import | LAREX project package | Structured ZIP with project/page descriptors and optional assigned resources/history. |
| A stable project delivery | Project release | Frozen package with version metadata and sharing controls. |
| Curated pages with train/validation/test splits | Dataset package or dataset release | Dataset manifest, selected files, and split lists. |
| A working project in another workspace | Project transfer | A move/copy request approved in the receiving workspace. |

A package export is not a complete server backup. Use the [administrator backup workflow](/user-guide/admin-dashboard/workspaces-import-backup) for instance recovery.

## Export a project or page

1. Open the project export menu, or the page's export action.
2. Choose the output type and scope the dialog offers.
3. Review format options and image variants.
4. Start the export and follow its progress in **Jobs**.
5. Open the downloaded artifact and check representative pages before handing it off.

For text-based outputs, choose the text level and any offered variant/index options deliberately. Reading order, available transcription, and layout affect the result. A conversion cannot preserve every PAGE XML construct in every target format.

### Which transcription a converted export uses

| Output | Index used |
| --- | --- |
| Text (`.txt`), direct or embedded in a package | The dialog's **Text index**. It defaults to `0`, not to the project's GT index. |
| PDF, ALTO, FineReader XML, hOCR, TEI, DOCX, CSV, XLSX | The project's effective **Default GT Index**. An undefined GT index selects text without an index. |

Each line then falls back when its selected index has no text: first to index `0`, then to the lowest-indexed non-empty variant. A line without GT can therefore export recognition text. If your project's GT index is not `0`, set **Text index** explicitly for TXT. Filter the editor list to **Without GT** before exporting when the output must contain reviewed text only.

### Legacy PAGE XML versions

LAREX stores every page as PAGE `2024-07-15`, and PAGE XML and package exports use that version by default. They can also target an older schema, from `2010-03-19` to `2019-07-15`. Keep the default unless the receiving tool requires an older version.

An older schema can't hold everything PAGE 2024 can. On export, LAREX replaces what the target lacks with the closest equivalent, for example a form region with a custom region of type `form` in PAGE 2018 and 2019, and drops what has no equivalent. The dialog warns **Legacy export can lose data** and asks for confirmation first.

LAREX lists every change it makes, so you can check what the recipient gets:

| Export | Where the changes are listed |
| --- | --- |
| PAGE XML of one page | A notice that stays open until you close it. It shows the first ten lines and counts the rest. |
| PAGE XML of a project | `_export-warnings.txt` in the archive |
| Package or release | `warnings` in `manifest.json` |

Each line names the change and the elements it affects. The same change on many elements is one line that names the first three and counts the rest. Your project keeps its PAGE 2024 data; only the exported file changes.

### ALTO, FineReader XML and hOCR

ALTO holds less than PAGE XML. An ALTO export keeps regions, lines, words and glyphs with
their outlines and text, alternative word readings, languages, text styles, labels and
region types as tags, the reading order, processing steps, and the page size. Relations,
table rows and columns, and the other PAGE details are left out; a table becomes one block
with a text block per cell. The export dialog says so below the format when you choose
ALTO.

FineReader XML (`.finereader.xml`) holds less still. Each region becomes a block with its
bounding box: text regions as `Text`, tables as `Table`, separators as `Separator`,
barcodes as `Barcode`, and every other region as `Picture`. Lines keep their text,
baseline and language, with one character box per character. LAREX takes character boxes
from glyphs when a word has one glyph per character, and otherwise divides the word's box
evenly; character confidences come from the glyph or word confidence, and words survive as
word starts in the character list. Outlines are reduced to boxes, and relations, table rows
and columns, and the other PAGE details are left out.

hOCR (`.hocr`) writes one XHTML file per page. Text regions become `ocr_carea` and
`ocr_par` elements with their lines and words; lines keep their boxes, baselines and text
angle, and words keep their boxes and confidences as `x_wconf`. Languages and reading
direction carry over. Other regions are written as empty areas with a box, such as
`ocr_photo`, `ocr_separator` or `ocr_table`. Outlines are reduced to boxes, and glyphs,
relations, table rows and columns, and the other PAGE details are left out.

For a project, each of these formats downloads as a zip with one file per page:
`.alto.zip`, `.finereader.zip` or `.hocr.zip`.

Pages that were [uploaded as ALTO, FineReader XML or hOCR](/user-guide/projects#upload-files) were
converted to PAGE XML on import, so exporting them in that format again gives a new file,
not the original.

For PDFs, the dialog offers **Searchable**, **Images only**, **Text pages**, and **PDF/A searchable** profiles. Select an image variant globally or per page. With **Fallback image** enabled, a missing selected variant uses the page's first available image; without it the affected page is omitted. Confirm the page count in the result.

TEI offers standard and layout-aware profiles. Spreadsheet exports offer page metadata, tags, regions, or tables. The **Tables** profile writes one row per table cell in CSV, and one sheet per table in XLSX; see [Export tables](/user-guide/tables#export-tables). Choose an output that matches the recipient's need; keep PAGE XML or a package when layout fidelity and future editing matter.

## Preserve an editable project

Choose a **LAREX package** for structured re-import. It contains readable page folders, `manifest.json`, `page.json` descriptors, and declared assets. Assigned resources can travel with the package. Optional converted outputs go in `exports/` and are not imported as project content.

Enable **Include PAGE XML version history (archival)** if you need older saved annotations. It is off by default for regular and batch package exports. Project releases include history by default.

When editing an extracted package, update JSON descriptors for every added, removed, or renamed file before re-zipping it. LAREX rejects inconsistent, duplicate, missing, undeclared, or unsafe paths. See the [package and import reference](/user-guide/projects#export-or-transfer-a-project) for conflict and resource-reuse choices.

## Create and share a project release

Curators can create a versioned project release from the project's release controls. Releases always include the full project; the current page selection is ignored. Add a useful version tag and notes, wait for a ready artifact, and verify the downloaded package.

A release records a stable delivery. Correcting the working project afterward requires a new release when you want to distribute the correction.

Release sharing uses an expiring secret. Keep the supplied URL and secret together only for intended recipients. The public share flow asks for the secret before downloading. Curators can rotate, extend, or revoke the share. Revocation stops future access through that credential; it cannot retract files already downloaded.

For dataset release procedures and their separate annotation copies, see [Datasets and releases](/user-guide/datasets).

## Transfer work between workspaces

A curator can request **copy** or **move** from project sharing controls. The receiving workspace reviews the request in **Workspace Settings → Requests**. The sender can track outgoing requests and cancel a pending request.

Use copy when both workspaces need independent working versions. Use move when the receiving workspace should own the working project. A workspace transfer is different from sharing a frozen release with an external recipient.

Resolve destination naming conflicts in the transfer review rather than deleting the existing project first. For invitations and your own transfer requests, see [Account settings](/user-guide/account-and-notifications).
