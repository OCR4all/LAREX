# Collaboration and version history

LAREX separates the live editing session from saved XML and its retained versions. Save at a meaningful checkpoint before handing work over or starting a processor.

## Share page edit access

Only one user holds edit access to a page at a time. Other people can view the page and request access from its current editor.

1. Check the collaborator strip and edit-access status.
2. Request access if someone else is editing.
3. Let the current editor grant the request, or use takeover if your permissions allow it.
4. Confirm you hold edit access before making changes.

A forced takeover offers two choices:

| Choice | Effect |
| --- | --- |
| Save and take over | Saves the synchronized live annotations before transferring access. If the save fails, access stays with the current editor. |
| Discard and take over | Reloads the last saved annotation and discards the live changes being taken over. |

Use discard only when the team intends to lose those unsaved edits. Saving before takeover requires synchronized live annotations.

The editor renews access while the page stays open and renewal requests reach the server. Changing view or reloading annotations does not itself release the lease. Leaving the page, granting a request, takeover, or expiry after renewal stops can release it. A temporary interruption in collaboration updates alone does not prove that access has transferred.

## Save and undo

Undo and redo operate on live editing history. They do not replace a successful save. Save before leaving the page and confirm the result, especially before an Action processes saved XML.

Use version history when you need a saved checkpoint from an earlier session. Versions apply to a particular XML annotation; with multiple XML variants, check which one you are viewing.

## Compare and restore a version

1. Open **Version History** from the page/editor controls.
2. Identify the checkpoint by version number, timestamp, author, and comment.
3. Choose **Compare** to inspect it against the current annotation.
4. Filter changes by geometry, text, or metadata. Use the region, line, and baseline views as needed. Linked canvas navigation helps compare the same area.
5. Choose **Restore** only after checking the differences and the confirmation message.

Restoring preserves the currently saved XML as a new version first, then makes the chosen checkpoint current. Unsaved changes in the editor are discarded. If those edits matter, save them before restoring.

After restoration, reopen or inspect the page and confirm that the intended text and geometry are current. Allow indexing to catch up before relying on search results.

## Know the recovery boundary

Version history concerns annotation XML, not a full project backup. It does not restore deleted images, workspace membership, all project settings, or an entire deployment. Retention is configured by the operator, so old checkpoints can be pruned.

For an archival project package, explicitly enable **Include PAGE XML version history (archival)**. Regular package exports leave history off by default; project releases include it by default. See [Exports and sharing](/user-guide/exports-and-sharing) and [project package details](/user-guide/projects#export-or-transfer-a-project).

If a page remains read-only, check [Troubleshooting your work](/user-guide/troubleshooting) for page state, project lock, Action scope lock, and permission causes.
