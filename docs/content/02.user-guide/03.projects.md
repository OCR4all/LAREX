A project is the working container for a document or collection segment. It holds pages, images, PAGE XML files, tags, task state, resource assignments, and processing history.

The page table stays visible while updates arrive from uploads, Actions, state changes, or a manual refresh. You can continue reading the current rows until the updated data arrives.

## Create a project

From the library, choose **New Project** and enter the required project name. Curators can also add:

- description
- project tags
- tag set
- codec
- dictionary
- label set
- normalization profile
- validation ruleset
- default ground-truth index
- default recognition indices

The assigned resources shape editor behavior, validation, search, and review workflows. They can be changed later from project settings.

## Configure project defaults and editor overrides

Open project settings to review **Project Defaults**, **Text Variants**, **Editor Tool Overrides**, and **Action Outputs**.

- Assign toolkit resources for this project, including its virtual keyboard.
- Set the ground-truth index and recognition indices used by text review. These are transcription alternatives, not image variant names. Check **Undefined** to use text without an index; see [text alternatives](/user-guide/text-review#understand-text-alternatives).
- Decide which of the seven toolkit resources editors may override in their editor session. A project default and permission to choose another resource are separate settings.
- Set retention for outputs of newly started Actions. Changing this setting does not retroactively change a run's captured retention policy.

Workspace defaults are copied at creation; later propagation can fill missing values or replace explicit choices. See [workspace defaults](/user-guide/workspace-library#workspace-presets). An editor's temporary tool override is not a rewrite of the project's shared resource definition.

## Move pages between projects

Select pages in the project view and choose **More → Manage pages → Move pages** from the selection toolbar. Project managers can choose another unlocked project in the same workspace.

The slideover previews each page and offers one policy for name clashes:

- **Skip** leaves clashing pages in the source project.
- **Overwrite** permanently removes the matching destination pages, including their images, XML, and version history, then moves the source pages into their place.
- **Rename** adds a shared prefix and/or suffix to clashing page names only. Adjust the affixes until all resulting names are unique.

Moved pages keep their identity, assets, XML history, metadata, and page task links. They are appended in source project order and use the destination project's settings. Renaming does not change asset filenames or XML contents.

Locked projects, locked selected pages, and pages with active annotation editors block the move. Overwriting also requires the destination pages to be unlocked and free of active editors. If the preview changes before submission, review the refreshed preview before trying again.

## Copy pages between projects

Select pages and choose **More → Manage pages → Copy pages** from the selection toolbar. Project managers can copy pages to another unlocked project in the same workspace. The preview offers the same **Skip**, **Overwrite**, and **Rename** policies as moving pages. Overwrite permanently removes the matching destination pages and their assets and history.

Copies receive new identities and independent images, thumbnails, and current XML. They retain descriptions, tags, and external source metadata, and are appended in source project order using the destination project's settings. Copies start as **Open** pages; review state, task and dataset links, and XML version history remain with the originals. Asset filenames and XML contents stay the same, including when page names are renamed.

Locked source projects and pages can be copied. Active annotation editors block copying, and overwrite targets must be unlocked and free of active editors. Copies count toward the workspace storage quota. If a preview becomes outdated, review the refreshed preview before submitting again.

## Add material

Projects can receive material through uploads or IIIF import.

### Track jobs

The **Jobs** panel opens automatically when a job you schedule becomes active. Jobs scheduled by other users still contribute to the active-job badge without opening the panel.

Use **My jobs** to see your uploads, imports, Action runs, and local background tasks. Switch to **All visible jobs** to see all jobs available to you, including jobs you can manage as a curator. **Clear completed** clears completed jobs from the selected tab.

### Upload a directory as a new project

In the library's project menu, choose **Upload directory as project**, or drop a folder onto the library when the browser supports folder drops. LAREX uses the folder name as the initial project name and includes supported images and XML files. If the name is invalid or already taken, the naming dialog lets you choose another before creating the project.

Watch **Jobs** for file processing and conflicts after creation. The directory flow creates a project; use **Upload Files** inside an existing project when adding more material to it. PDFs use the project upload flow rather than this image/XML directory shortcut. **Import Package** and **Import OCR4all project** are separate library import choices for those structured inputs.

### Upload files

Use **Upload Files** for local files.

Accepted inputs:

- images
- PAGE XML files, including PAGE XML exported from Transkribus
- ALTO XML files
- ABBYY FineReader XML files
- hOCR files (`.hocr`, `.html` or `.xhtml`)
- PDFs

LAREX converts ALTO to PAGE XML when it imports the file and keeps only the PAGE XML.
Regions, lines, words, glyphs, reading order, styles and tags carry over; ALTO details
that have no PAGE equivalent are dropped.

ALTO with coordinates in `mm10` or `inch1200` needs the page image, because LAREX scales
the coordinates to the image's pixels. Upload the image together with the ALTO file, or
upload the ALTO to a page that already has its image. If the ALTO page size differs from
the image size, LAREX scales by the ratio of the two sizes; otherwise it uses the image
resolution. An ALTO file without a usable image is rejected.

FineReader XML and hOCR are converted to PAGE XML the same way. From FineReader XML,
blocks become regions of the matching type, and lines keep their text, baseline and
language; LAREX builds words from the character boxes and takes each word's confidence
from its characters. From hOCR, text areas become text regions, and lines and words keep
their boxes, baselines, languages, reading direction and word confidences; photos become
image regions and separators become separator regions. Both formats use pixel
coordinates, so they need no page image.

The converted PAGE XML records the import as a processing step named `LAREX ALTO import`,
`LAREX FineReader XML import` or `LAREX hOCR import`, with a label for each detail the
conversion could not keep. You can read it in the document metadata in the editor, and it
stays in the file when you export the page. The stored file is named after the upload with
an `.xml` extension, so `0001.hocr` becomes `0001.xml`.

Every export starts from the converted PAGE XML, so exporting the page in its original
format does not reproduce the uploaded file. See
[ALTO, FineReader XML and hOCR](/user-guide/exports-and-sharing#alto-finereader-xml-and-hocr).

Local upload names determine page grouping. The text before the **first dot** is the page name, and the remaining suffix identifies the variant:

| Filename | Page | Variant |
| --- | --- | --- |
| `0001.png` | `0001` | `png` |
| `0001.bin.png` | `0001` | `bin.png` |
| `0001.xml` | `0001` | `xml` |

Use matching page basenames for the image and XML. Avoid dots inside a page identifier unless you intend the remaining text to become a variant. Inspect conflicts when different inputs share a basename and variant.

LAREX stores PAGE XML as PAGE `2024-07-15`. A file in an older version, back to `2009-03-16`, is upgraded on upload. The upgrade carries all annotation data over and writes it the way PAGE 2024 does, for example script names as `Arab - Arabic` instead of `Arabic`. The uploaded file stays in the page's version history as the first version, so you can compare it with the upgrade or export it again.

For PDFs, LAREX asks for a page prefix before processing. Upload progress is tracked, and unresolved conflicts appear as a project warning.

Conflict choices:

| Choice | Result |
| --- | --- |
| Keep existing | Ignore the incoming conflicting file. |
| Replace existing | Replace the current project file. |
| Rename upload | Keep both by storing the new file under a different name. |

#### PAGE XML from Transkribus

Transkribus writes PAGE XML that the PAGE schema rejects. LAREX recognises a Transkribus
export by its `TranskribusMetadata`, its table cells or a Transkribus `Creator`, and
repairs it before validating it. This applies to uploads, server import jobs and project
packages alike:

- `TranskribusMetadata` is removed. The Transkribus document ID, page ID, page number,
  transcript ID, image ID and status move to a metadata item named `Transkribus`; the file
  URLs and the Transkribus user ID are not kept.
- Table cells become text regions inside the table, each with a table cell role for its
  row, column and span, and the table gets its row and column count. Cell border flags and
  corner points are dropped. The table has no grid afterwards; use **Create Grid from
  Cells** in the [table editor](/user-guide/tables) to add one.
- Points outside the page image, including negative coordinates, move onto the edge of the
  image, and fractional coordinates are rounded to whole pixels.
- Tags, properties and links that Transkribus stores as elements, the image rotation,
  translation and scaling attributes on the page, and attributes the schema does not allow
  on table regions are removed. Tags and structure types in the `custom` attribute stay.

Regions, lines, words, text, baselines, confidences and reading order carry over. The
repaired file is stored as PAGE XML 2024-07-15 with a processing step named
`LAREX Transkribus import` that lists each change. Unlike an older PAGE version, the
original export is not kept in the version history. A Transkribus export that is already
valid is imported like any other PAGE XML. Anything else in the file that the schema rejects still fails
the import with the validation message.

### Import IIIF

Use **Import IIIF** for public IIIF Presentation manifests or collections.

Manifest and image URLs must use HTTP or HTTPS and point to public hosts. By default, LAREX rejects URLs that resolve to `localhost` or a private network address, including after redirects. Ask your administrator if your IIIF server is only reachable internally ([`LAREX_IIIF_ALLOW_PRIVATE_NETWORK_HOSTS`](/deployment/environment-vars#iiif-request-scheduling)).

Supported sources:

- manifest URL
- uploaded manifest JSON file
- IIIF Presentation API v2
- IIIF Presentation API v3
- IIIF collections with manifest expansion

The preview step shows metadata, canvases, thumbnails, warnings, and estimated storage. To keep previews responsive and avoid contacting every image endpoint, LAREX approximates image sizes from manifest dimensions and image formats with a safety margin. Images without usable dimensions use a 10 MB fallback during quota preflight. You can import all importable canvases, manually choose canvases, or select a start/end range.

Each imported canvas becomes one LAREX page with a local `iiif` image variant. IIIF import does not create PAGE XML automatically.

IIIF download jobs from different projects share a durable instance-wide queue. They appear in the global **Jobs** panel with their queue position, progress, cancel action, and completed history, including after a page reload. Pending jobs are recovered after a backend restart. To prevent stale previews from creating duplicate pages, only one active or queued IIIF import is allowed per project.

If an imported canvas collides with an existing page, choose:

| Choice | Result |
| --- | --- |
| Skip | Keep the existing page and do not import that canvas. |
| Rename | Create a new page with a different name. |
| Replace IIIF Image | Reuse the existing page and replace its `iiif` image variant. |

After a partial failure, **Retry Failed** creates a new import job for failed canvases only.

## Work with pages

The page table is the project control surface. It shows page order, name, description, tags, page state, annotation state, image count, your Tasks, update time, and row actions.

Common page tasks:

- edit page metadata
- inspect images
- view or edit raw PAGE XML
- export XML
- open version history
- delete pages
- select pages for batch actions
- open selected pages in the editor
- run LAREX Actions on selected pages

## Inspect page images

The image count opens a carousel of this page's image variants. The carousel uses presentation images with a maximum edge of 1,600 pixels. Opening a card or comparing variants uses a presentation image with a maximum edge of 3,200 pixels. These JPEG previews are for display; the type labels and file sizes describe the original files.

In the detail view, the toolbar uses an **SD** icon for Preview and an **HD** icon for Full Resolution. The tooltip identifies the active mode and the mode clicking will switch to. Use this control to load the full-size image explicitly, including large scans, or return to the smaller preview. Downloads and LAREX Actions continue to use originals.

The first request for a large scan can take longer while its preview is generated. Generated previews are cached across backend restarts. Failed loads, including either side of a comparison, show an error and a retry control; they never silently download the original. The editor also uses presentation images by default, with a resolution toggle in the toolbar for the active canvas.

## Edit PAGE XML directly

Use **View/Edit XML** when you need raw PAGE XML access.

The XML editor:

- loads the first PAGE XML file for the page
- validates against the bundled PAGE schema of the file's version
- checks that the visual editor can open the page, for example that every ID is unique and every reference points to an existing element
- lists each error with its line and column
- blocks saving XML with errors
- pretty-prints compact XML with two-space indentation
- supports find and replace with `Ctrl/Cmd+F` and `Ctrl/Cmd+H`
- keeps version history separate from the editing surface

Supported PAGE schema versions are `2010-03-19`, `2013-07-15`, `2016-07-15`, `2017-07-15`, `2018-07-15`, `2019-07-15`, and `2024-07-15`. Saving keeps the version you wrote. The visual editor opens a page in an older version as its PAGE 2024 upgrade.

## Open pages in the editor

Use **Open in Editor** from the project header.

- If pages are selected, LAREX opens the selected pages.
- If no pages are selected, LAREX opens the project page set.
- Hovering or focusing the editor action starts prefetching for faster navigation.

Workspace search results can also open a page directly in text mode with the search term already applied.

## Run project-level Actions

The project Action dialog can run assigned processors on:

- all pages
- selected pages

If the processor accepts images, choose the image variant globally or per page. Missing selected variants can either fall back to the first available image or skip affected pages.

See [Running LAREX Actions](/user-guide/larex-actions).

## Export or transfer a project

The project export menu offers three distinct outputs:

| Export | Purpose |
| --- | --- |
| Basic project export | A flat ZIP of current images and XML using their original filenames. |
| Converted output | PDF, text, TEI, ALTO, FineReader XML, hOCR, DOCX, CSV, or XLSX derived from the current project. |
| LAREX package | A readable, structured ZIP that can be edited and uploaded as a new project. |

For PDF output, choose one image variant for all pages or select a variant page by page. If the chosen variant is missing, enable **Fallback image** to use that page's first available image; otherwise the page is omitted from the PDF. The same options are available when a PDF is included as an optional output in a basic export or LAREX package.

A LAREX package stores each page in a directory derived from its page name. Filesystem-name collisions receive a readable suffix such as `-2`; authoritative page order comes from `manifest.json`. Each `page.json` descriptor declares the current files and metadata, while `manifest.json` also declares project settings and assigned toolkit resources. Internal database IDs, thumbnails, and METS are not included.

Enable **Include PAGE XML version history (archival)** when earlier XML versions must travel with the package. Regular and batch package exports leave this off by default, so re-uploaded XML starts with an empty version history. Project releases include history by default. Optional converted outputs are stored under `exports/` and are ignored during re-upload.

Package descriptors are strict: after adding, removing, or renaming a file in the extracted archive, update the corresponding JSON path before re-zipping it. Invalid, missing, duplicate, undeclared, or unsafe paths are rejected before the project is created.

When you upload a package, LAREX validates it first and opens a review step showing the project, its pages, file counts, XML history, and assigned resources. Nothing is imported until you confirm the review.

If a project with the same name already exists, choose whether to replace it, import the package under a custom new name, or skip it. The rename choice is prefilled with a collision-safe suggestion that you can edit. Replacement is staged first: the existing project and its files are removed only after the incoming project has imported successfully.

Resource import can be disabled for the whole package or configured per assigned resource:

| Choice | Result |
| --- | --- |
| Reuse existing | Assign the existing same-name resource without changing it. This is the default when its content is identical. |
| Replace existing | Update the same-name resource in place. Other projects using it immediately see the imported definition. |
| Upload as renamed copy | Create a separate resource with a collision-safe name. |
| Skip resource | Do not import or assign that resource. |

New resources are uploaded by default. Protected system resources cannot be replaced. Re-upload supports the current package schema 1.0.
