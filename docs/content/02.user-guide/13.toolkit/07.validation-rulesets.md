# Validation rulesets

A validation ruleset finds regex matches in selected transcription text. Matches are findings to inspect. This text-validation feature does not validate XML structure, enforce required regions, or inspect arbitrary metadata. Raw PAGE XML schema validation and dataset file validation are separate checks.

## Create a ruleset

Open **Validation Rulesets**, create a resource, and give each rule a name, pattern, severity, and useful message.

| Field | Meaning |
| --- | --- |
| Name / Description | What the rule checks and why. |
| Pattern | Regular expression that matches a potential problem. |
| Flags | Server supports `i` (case-insensitive), `m` (multiline), `s` (dotall), `u` (Unicode case), and `x` (comments). |
| Severity | Info, Warning, or Error for prioritizing findings. |
| Message | Actionable guidance shown with a match. |

Patterns match problems rather than describe a whole text that must pass. A match is reported even at Info severity; the source-validation result is valid only when there are no occurrences.

## Try a concrete rule

For repeated punctuation, enter:

```text
Name: Repeated punctuation
Pattern: [!?.,;:]{2,}
Severity: Warning
Message: Check repeated punctuation against the image.
```

In **Preview**, try `What??` and `A normal sentence.`. The first should report `??`; the second should have no match. A match can be intentional, so a reviewer still needs to inspect the source.

The browser preview supports `i`, `m`, `s`, and `u`; server validation uses Java regular expressions and also supports `x`. Browser and server regex behavior can differ. Confirm the result on actual selected sources before depending on an advanced expression.

## Validate project text

Save the ruleset and assign it in project settings or workspace defaults. For batch validation, select projects in the library and choose **Validate with Ruleset**, pick the ruleset, and run the check. This library flow covers every page and text variant in those selected projects. Other scoped review/API operations can select narrower sources or indices; follow the scope shown by the operation you actually use.

Server validation reads saved, indexed text and applies the project's effective normalization profile before matching. This can change the text your expression sees. Blank text rows are skipped, so a successful result is not evidence that every page has transcription.

Results include rule names, severity, messages, occurrence counts, matched samples, and affected page references. Inspect the analyzed page/project counts as well as the result status.

1. Open affected pages and compare the matches with their images.
2. Correct genuine errors and save.
3. Wait for indexing to refresh, then validate the same scope again.
4. Adjust a noisy rule when it flags valid source conventions too often.

See [Normalization](/user-guide/toolkit/normalization), [Codecs](/user-guide/toolkit/codecs), and [Dictionaries](/user-guide/toolkit/dictionaries) for other kinds of review.
