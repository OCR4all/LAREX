# Normalization

A normalization profile defines repeatable text transformations. Some review operations use a project's effective profile for comparison. Explicit **Apply** operations can also rewrite saved transcription. Assigning a profile alone is different from applying it to source text.

## Configure a profile

Curators can open **Normalization Profiles**, create a profile, and choose:

| Control | Effect |
| --- | --- |
| Unicode normalization | None, NFC, NFD, NFKC, or NFKD. Compatibility forms can change distinctions your project wants to preserve. |
| Dehyphenate line breaks | Joins supported word fragments separated by a hyphen and line break in the input text. |
| Expand common ligatures | Expands supported typographic ligatures such as `ﬁ` to `fi`. |
| Map long s to s | Replaces supported long-s forms with `s`. |
| Normalize quotes, dashes, ellipsis | Maps the supported variants to standardized punctuation. |
| Manual replacement rules | Plain-text or regular-expression search and replacement, in listed order. |
| Collapse whitespace / Trim text | Collapses whitespace runs and/or removes surrounding whitespace. |

Use the **Preview** tab on representative text before saving. For example, enable **Map long s to s** and **Expand common ligatures**: `ſchrift ﬁnden` becomes `schrift finden`. Leave other transformations off while testing that pair so you can identify their effect.

The preview applies dehyphenation, Unicode normalization, preset character/punctuation transformations, manual replacements, then whitespace cleanup. Manual rules run in their saved order. A line-break rule only sees line breaks present in the input being normalized; it does not reconstruct page reading order across separately stored lines.

For regex replacements, test both matches and intended non-matches. The browser preview and server execution use different regex engines, so use simple portable patterns and verify the source preview before a large apply.

## Assign a profile

Save and assign the profile in project settings or workspace defaults. Review tools can use the effective profile when comparing indexed text, including dictionary and regex validation workflows. This does not mean every search or export automatically uses normalized text.

Document the editorial purpose of the profile: comparison tolerance, historical-character normalization, or an intentional transcription rewrite.

## Preview and apply to projects

From the library, select projects and choose **Normalize Text**.

1. Select a normalization profile.
2. Run the preview and inspect original text, normalized text, matched rules, and changed row/page counts.
3. Confirm the scope. The library batch flow covers every page and text variant in the selected projects.
4. Apply only when that full scope and the preview are intended.
5. Inspect representative pages, confirm the saved result, and allow indexes to refresh.

Other review surfaces may offer narrower page, element, or variant targets. Check the scope shown in that dialog; do not assume a line selection limits a library batch operation.

Applying changes is a mutation of saved XML. Save live edits first, avoid concurrent review of the same material, and use [version comparison/recovery](/user-guide/history-and-collaboration) when checking a result. For a durable archival checkpoint, keep a package or release as well.

## If the result looks wrong

Check Unicode form, preset toggles, manual rule order, variant scope, and whether normalization already removed a distinction before a later rule runs. Correct the profile and preview again instead of repeatedly applying an uncertain transformation.
