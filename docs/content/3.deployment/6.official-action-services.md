# Official Action Services

`compose.actions.yaml` is the supported optional deployment fragment for processors
maintained as part of the LAREX ecosystem. Processors remain isolated HTTP services:
they receive signed dispatch requests and communicate with LAREX only through the
Action callback API. They do not receive database or storage credentials.

The fragment works with all three supported base modes:

- local development (`compose.yaml`)
- local production-like deployment
- opinionated production deployment

The `actions` profile starts the complete official catalog. Each processor also has
an individual profile so operators can choose only the workloads they need.

## Included Processors

| Processor | Service | Individual profile | Default image                               |
| --- | --- | --- |---------------------------------------------|
| Kraken Segmentation | `action-kraken-segmentation` | `action-kraken` | `ghcr.io/ocr4all/larex-action-kraken:0.3.0` |

Image tags are pinned in `.env.actions`. Update them deliberately after reviewing
processor release notes; do not rely on `latest` in production.

## Environment Setup

Create the independent processor environment file:

```bash
task docker:actions:init-env
```

This copies `deployment/env/.env.actions.example` to `.env.actions` and generates
the Kraken dispatch HMAC secret. Keep `.env.actions` private and back it up through
the same secret-management process as `.env.prod`.

Important shared settings:

| Variable | Purpose |
| --- | --- |
| `LAREX_ACTIONS_PUBLIC_BASE_URL` | Callback API base reachable by the processors |
| `LAREX_ACTIONS_CALLBACK_ALLOWED_ORIGINS` | Callback origins accepted by processor SDK clients |
| `LAREX_ACTIONS_ENDPOINT_ALLOWED_ORIGINS` | Processor origins the LAREX backend may dispatch to |
| `LAREX_ACTION_ENDPOINT_SECRET_KRAKEN_SEGMENTATION_V1` | Shared dispatch HMAC secret |

When official and external processors coexist, include every permitted processor
origin in `LAREX_ACTIONS_ENDPOINT_ALLOWED_ORIGINS`. If an external processor cannot
reach `http://app:8080`, set `LAREX_ACTIONS_PUBLIC_BASE_URL` to the HTTPS callback
base reachable by both internal and external processors and update the callback
allowlist accordingly. The example endpoint allowlist includes the development mock
processor; remove that origin from production when the mock service is not deployed.

## Local Production-Like Deployment

Initialize both env files, then start the combined stack:

```bash
task docker:prod:local:init-env
task docker:actions:init-env
task docker:prod:local:actions:up
```

Direct Compose equivalent:

```bash
docker compose \
  --env-file .env.prod.local \
  --env-file .env.actions \
  -f compose.prod.base.yaml \
  -f compose.prod.auth.bundled-keycloak.yaml \
  -f compose.prod.local.yaml \
  -f compose.actions.yaml \
  --profile actions \
  up -d --wait --wait-timeout 300
```

## Production Deployment

```bash
task docker:prod:init-env
task docker:actions:init-env
task docker:prod:actions:up
```

Direct Compose equivalent:

```bash
docker compose \
  --env-file .env.prod \
  --env-file .env.actions \
  -f compose.prod.base.yaml \
  -f compose.prod.auth.bundled-keycloak.yaml \
  -f compose.prod.publish.localhost.yaml \
  -f compose.actions.yaml \
  --profile actions \
  up -d --wait --wait-timeout 300
```

Use `--profile action-kraken` instead of `--profile actions` to start Kraken alone.

## Register Kraken

Development mode bootstraps Kraken for convenience. Production deliberately keeps
Action definitions admin-managed, so adding or removing a container never silently
changes application availability.

After the first production deployment:

1. Open **Admin → Actions**.
2. Register `deployment/actions/kraken-segmentation.yaml`.
3. Run the endpoint health test.
4. Enable the definition and configure global or workspace availability.

The shipped definition references `kraken-segmentation-v1`. The backend and
processor receive the matching secret from `.env.actions`; it appears in the admin
secret list as an environment fallback.

## Security And Isolation

The official service fragment:

- publishes no processor ports to the host
- uses only the private `backend` network
- uses a read-only root filesystem and a temporary `/tmp`
- drops Linux capabilities and enables `no-new-privileges`
- rotates container logs
- persists only processor cache/data required across restarts
- configures health checks and resource limits

If a processor must run on a GPU host, deploy the processor separately and register
its HTTPS endpoint instead. Do not expose the internal Compose endpoint publicly.

## Models And Resources

Kraken defaults to CPU execution. Configure device, precision, model, timeouts, and
container limits in `.env.actions`. A custom local model must be made available to
the container through an operator-owned Compose override and referenced by its
container path in `KRAKEN_SEGMENTATION_MODEL`.

`KRAKEN_MAX_CONCURRENT_RUNS` defaults to `1` and should remain conservative for
GPU or memory-heavy models. Increase it only after measuring peak memory with
representative pages. `/health` reports liveness; `/ready` returns `503` while all
run slots are occupied.

Resource limits are operational guardrails, not sizing guarantees. Benchmark with
representative page sizes and models before production rollout.

## Operations

```bash
task docker:prod:actions:ps
task docker:prod:actions:logs
```

Before upgrading, pin the new image tag and test it in the production-like stack.
Then pull and apply the complete configured stack with health waiting:

```bash
task docker:prod:actions:upgrade
```

Previously imported incremental page results remain stored in LAREX if a later page
or processor instance fails.
