# CI/CD

LAREX uses GitHub Actions workflows in `.github/workflows/`.

## Workflows

| Workflow | File | Purpose |
|----------|------|---------|
| CI | `.github/workflows/ci.yml` | Backend, frontend, docs, theme, Docker image, and Compose validation checks |
| Branch Container Images | `.github/workflows/branch-images.yml` | Deployable branch images for non-production environments |
| Release | `.github/workflows/release.yml` | Versioned release, image publishing, and version sync |

## CI Workflow (`ci.yml`)

### Triggers

- Push to `main`
- Pull requests targeting `main`
- Reusable workflow calls from release and branch-image workflows

### Jobs

1. `backend` (Backend Tests)
- Uses PostgreSQL `17-alpine` service
- Runs with JDK 25 (Temurin)
- Executes `./gradlew test`
- Builds JAR via `./gradlew build -x test`
- Uploads backend test reports as artifact

2. `frontend` (Frontend Checks)
- Uses Node 20 + pnpm 11.1.2
- Installs dependencies in `frontend/`
- Runs `pnpm build`
- Note: lint/typecheck steps are currently present but commented out in workflow

3. `keycloak-theme` (Keycloak Theme Build)
- Uses Node 20 + pnpm 11.1.2
- Installs dependencies in `keycloak-theme/`
- Runs `pnpm run build-keycloak-theme`
- Uploads generated theme artifact (`dist_keycloak/`)

4. `docs` (Docs Build)
- Uses Node 20 + pnpm 11.1.2
- Installs dependencies in `docs/` with `--frozen-lockfile`
- Runs `pnpm build`

5. `compose-validation` (Compose Validation)
- Validates local dev, production-like, bundled Keycloak, external Keycloak, and bundled Nginx Compose configurations
- Checks for stale deployment references in `README.md`, `docs`, and `Taskfile.yml`

6. `docker-build` (PR-only build test)
- Runs only on pull requests
- Builds backend and frontend production Docker images with Buildx
- Does not push images

## Branch Container Images Workflow (`branch-images.yml`)

### Triggers

- Push to `dev`, `staging`, or `next`
- Manual dispatch (`workflow_dispatch`) when run from `dev`, `staging`, or `next`

### Pipeline

1. `test`
- Reuses `ci.yml`
- Must pass before images are published

2. `build-and-push`
- Builds backend and frontend with `Dockerfile.prod`
- Pushes mutable branch tags for deployable non-production environments
- Does not create GitHub releases

## Release Workflow (`release.yml`)

### Triggers

- Push to `main` when `VERSION` changes
- Manual dispatch (`workflow_dispatch`) with optional `skip_tests`

### Pipeline

1. `version`
- Reads and normalizes `VERSION`
- Exposes it as workflow output

2. `test`
- Reuses `ci.yml`
- Skipped when `skip_tests=true`

3. `build-and-push`
- Builds and pushes backend/frontend production images to `ghcr.io`
- Runs after successful tests (or when tests are skipped manually)
- Adds Docker metadata tags

4. `create-release`
- Creates GitHub release `v<version>`
- Uses generated release notes

5. `sync-versions`
- Runs `scripts/version-sync.sh`
- Commits and pushes version-sync changes if needed

## Image Tags

Release images are tagged with Docker metadata rules, including:

- `<version>`
- `<version>-<sha>`
- `latest` (default branch only)
- `sha-<sha>`

Branch images are tagged with:

- `<branch>` such as `dev`, `staging`, or `next`
- `<branch>-<sha>`
- `sha-<sha>`

Set `LAREX_IMAGE_TAG` to the branch tag for non-production deployments, for example `LAREX_IMAGE_TAG=staging`.

## Registry and Auth

- Registry: `ghcr.io`
- Backend image: `ghcr.io/ocr4all/larex/backend`
- Frontend image: `ghcr.io/ocr4all/larex/frontend`
- Authentication: `GITHUB_TOKEN` via `docker/login-action`

## Local Validation

Useful local commands before pushing:

```bash
task test
task build
cd docs && pnpm build
```
