# Production Deployment

Production deployment is Docker-based. The production compose files do not require Node.js, pnpm, Java, or Gradle on the server; those tools are used inside image builds.

LAREX production is assembled from a base compose file plus small overlays. The base file defines the application services. Overlays choose the authentication mode, publishing strategy, docs service, optional processors, and optional Nginx reverse proxy.

## Which Setup Should I Use?

| Setup | Command | Use it for | Public surface |
| --- | --- | --- | --- |
| Local production-like | `task docker:prod:local:up` | Testing production images and auth locally | `*.localhost` through Traefik |
| Opinionated production | `task docker:prod:up` | Real deployment behind your own reverse proxy | frontend and Keycloak loopback ports |
| External Keycloak | `task docker:prod:external-keycloak:up` | Real deployment with an existing Keycloak | frontend loopback port, no bundled Keycloak |
| Bundled Nginx | `task docker:prod:nginx:up` | Simple host-managed TLS with provided certs | host ports `80` and `443` |

For most deployments, use `task docker:prod:up` and put your existing reverse proxy in front of the loopback-bound frontend and Keycloak ports.

## Compose Files

| File | What it does |
| --- | --- |
| `compose.prod.base.yaml` | Core production services: application database, backend, frontend |
| `compose.prod.auth.bundled-keycloak.yaml` | Adds bundled Keycloak and Keycloak database |
| `compose.prod.auth.external-keycloak.yaml` | Configures backend/frontend for an external Keycloak |
| `compose.prod.publish.localhost.yaml` | Publishes selected production services to loopback ports |
| `compose.prod.local.yaml` | Adds local Traefik, Mailpit, and `*.localhost` routes for rehearsals |
| `compose.prod.docs.yaml` | Adds docs to opinionated production |
| `compose.prod.local.docs.yaml` | Adds docs to local production-like setup |
| `compose.prod.kraken.yaml` | Adds the bundled Kraken segmentation processor |
| `compose.prod.nginx.yaml` | Adds optional bundled Nginx |

## One-Time Environment Setup

Create a production env file:

```bash
task docker:prod:init-env
```

This uses `scripts/bootstrap-env-secrets.sh prod` to create `.env.prod` from `deployment/env/.env.prod.example` and seed required secrets.

For local production-like rehearsals:

```bash
task docker:prod:local:init-env
```

This creates `.env.prod.local` from `deployment/env/.env.prod.local.example`.

You can also copy the examples manually, but then you must provide strong secret values yourself:

```bash
cp deployment/env/.env.prod.example .env.prod
cp deployment/env/.env.prod.local.example .env.prod.local
```

Never commit populated `.env.prod` or `.env.prod.local` files.

## Local Production-Like

Use this before changing a real deployment. It runs production-style images while keeping local routes and Mailpit.

```bash
task docker:prod:local:up
```

Open:

- `http://larex.localhost`
- `http://keycloak.localhost`
- `http://mail.localhost`

With docs:

```bash
task docker:prod:local:up:docs
```

With the bundled Kraken segmentation processor:

```bash
task docker:prod:local:up:kraken
```

Stop:

```bash
task docker:prod:local:down
```

## Opinionated Production

Use this when a host-level reverse proxy, load balancer, or ingress controller handles TLS and public routing.

```bash
task docker:prod:up
```

This starts:

- frontend on `127.0.0.1:3000`
- bundled Keycloak on `127.0.0.1:8090`
- backend on the internal compose network only
- PostgreSQL and Keycloak PostgreSQL on internal volumes

The backend is intentionally not published to the host. Browser traffic should enter through the frontend BFF routes, not directly through the backend API.

With docs:

```bash
task docker:prod:up:docs
```

This publishes docs on `127.0.0.1:3001`.

With the bundled Kraken segmentation processor:

```bash
task docker:prod:up:kraken
```

Stop:

```bash
task docker:prod:down
```

## Production With External Keycloak

Use this when your organization already operates Keycloak.

```bash
task docker:prod:external-keycloak:up
```

You still use `.env.prod`, but the external Keycloak values become the important ones:

- `KEYCLOAK_PUBLIC_HOST`
- `KEYCLOAK_REALM`
- `KEYCLOAK_ADMIN_CLIENT_SECRET`
- `NUXT_OAUTH_KEYCLOAK_CLIENT_SECRET`

The external realm must contain equivalent frontend and backend clients, roles, redirect URIs, and web origins. See [Keycloak Setup](/deployment/keycloak-setup).

## Production With Bundled Nginx

Use this only if you want LAREX to start an Nginx container as part of the compose stack.

```bash
task docker:prod:nginx:up
```

`compose.prod.nginx.yaml` expects operator-provided certificate files. It does not request or renew LetsEncrypt certificates.

Required certificate names:

- `${LAREX_PUBLIC_HOST}.crt`
- `${LAREX_PUBLIC_HOST}.key`
- `${KEYCLOAK_PUBLIC_HOST}.crt`
- `${KEYCLOAK_PUBLIC_HOST}.key`

## Reverse Proxy Expectations

For the default production setup, configure your external reverse proxy roughly as follows:

| Public host | Upstream |
| --- | --- |
| `LAREX_PUBLIC_HOST` | `http://127.0.0.1:3000` |
| `KEYCLOAK_PUBLIC_HOST` | `http://127.0.0.1:8090` |
| docs host, if self-hosted | `http://127.0.0.1:3001` |

Do not expose the backend container directly unless you have a specific internal integration requirement and understand the security consequences.

## Image Version Pinning

Production Compose pulls backend and frontend images from GHCR by default. Set `LAREX_IMAGE_TAG` in `.env.prod` to a released version instead of `latest` when you want reproducible deployments and predictable rollbacks.

## Verification

Check containers:

```bash
task docker:prod:logs
```

or:

```bash
docker compose --env-file .env.prod \
  -f compose.prod.base.yaml \
  -f compose.prod.auth.bundled-keycloak.yaml \
  -f compose.prod.publish.localhost.yaml \
  ps
```

Verify:

- frontend is reachable through your public host
- Keycloak issuer and redirect URLs match the public Keycloak host
- backend health is reachable from the frontend container
- the backend is not directly exposed publicly
- email settings work for invitations and password/setup flows
- Action processor URLs are allowed and reachable if you use LAREX Actions

After the first successful login, rotate bootstrap passwords and remove or replace temporary admin credentials.
