# Production Deployment

Production deployment is Docker-based. The officially supported administrator artifact is the versioned bundle created by the [installation wizard](/getting-started/installation); cloning the repository is not required. The bundle contains the selected Compose fragments, runtime assets, environment templates, backup utilities, and exact commands for its topology.

LAREX production is assembled from a base compose file plus small overlays. The base file defines the application services. Overlays choose the authentication mode, publishing strategy, docs service, optional official Action processors, and optional Nginx reverse proxy.

The `task docker:prod:*` commands on this page are equivalent repository-maintainer shortcuts. Administrators using a downloaded bundle should use the direct `docker compose` commands in its generated `README.md` so every selected overlay is included consistently.

## Which Setup Should I Use?

| Setup | Command | Use it for | Public surface |
| --- | --- | --- | --- |
| Local production-like | `task docker:prod:local:up` | Testing production images and auth locally | `*.localhost` through Nginx |
| Opinionated production | `task docker:prod:up` | Real deployment behind your own reverse proxy | frontend and Keycloak loopback ports |
| External Keycloak | `task docker:prod:external-keycloak:up` | Real deployment with an existing Keycloak | frontend loopback port, no bundled Keycloak |
| Bundled Nginx | `task docker:prod:nginx:up` | Simple host-managed TLS with provided certs | host ports `80` and `443` |

For most deployments, use `task docker:prod:up` and put your existing reverse proxy in front of the loopback-bound frontend and Keycloak ports.

## Compose Files

| File | What it does |
| --- | --- |
| `compose.prod.base.yaml` | Core production services: application database, backend, frontend |
| `compose.prod.auth.bundled-keycloak.yaml` | Adds bundled Keycloak and Keycloak database |
| `compose.prod.auth.external-keycloak.yaml` | Configures backend/frontend for an external Keycloak |
| `compose.prod.publish.localhost.yaml` | Publishes selected production services to loopback ports |
| `compose.prod.local.yaml` | Adds local Nginx, Mailpit, and `*.localhost` routes for rehearsals |
| `compose.prod.docs.yaml` | Adds the pre-built docs image to opinionated production |
| `compose.prod.local.docs.yaml` | Adds docs to local production-like setup |
| `compose.prod.nginx.yaml` | Adds optional bundled Nginx |
| `compose.actions.yaml` | Adds opt-in official Action processor services through profiles |

OCR and layout processors remain separate Action endpoints. Supported processors such as Kraken can either run independently or through the optional official services fragment. See [Official Action Services](/deployment/official-action-services), [Actions Overview](/actions/overview), and [Security and Deployment](/actions/security-deployment).

## One-Time Environment Setup

Create a production env file explicitly when you want to review it before startup:

```bash
task docker:prod:init-env
```

This uses `scripts/bootstrap-env-secrets.sh prod` to create `.env.prod` from
`deployment/env/.env.prod.example` and seed required secrets. All production `up`
tasks run this idempotent initialization automatically, so a missing env file or a
known placeholder secret cannot accidentally reach container startup. Existing
non-placeholder values are preserved.

For local production-like rehearsals:

```bash
task docker:prod:local:init-env
```

This creates `.env.prod.local` from `deployment/env/.env.prod.local.example`.

You can also copy the examples manually, but then you must provide strong secret values yourself:

```bash
cp deployment/env/.env.prod.example .env.prod
cp deployment/env/.env.prod.local.example .env.prod.local
```

Never commit populated `.env.prod` or `.env.prod.local` files.

Official Action services use a separate `.env.actions` so processor images, secrets,
models, and resource settings can be managed independently:

```bash
task docker:actions:init-env
```

## Local Production-Like

Use this before changing a real deployment. It runs production-style images behind a basic local Nginx proxy while keeping local routes and Mailpit.

```bash
task docker:prod:local:up
```

Open:

- `http://larex.localhost`
- `http://keycloak.localhost`
- `http://mail.localhost`

With docs:

```bash
task docker:prod:local:up:docs
```

Stop:

```bash
task docker:prod:local:down
```

## Opinionated Production

Use this when a host-level reverse proxy, load balancer, or ingress controller handles TLS and public routing.

```bash
task docker:prod:up
```

The task waits for service health before returning. The default timeout is 300
seconds; override it for slower hosts with, for example,
`LAREX_COMPOSE_WAIT_TIMEOUT=600 task docker:prod:up`.

This starts:

- frontend on `127.0.0.1:3000`
- bundled Keycloak on `127.0.0.1:8090`
- backend on the internal compose network only
- PostgreSQL and Keycloak PostgreSQL on internal volumes

The backend is intentionally not published to the host. Browser traffic should enter through the frontend BFF routes, not directly through the backend API.

With docs:

```bash
task docker:prod:up:docs
```

This publishes docs on `127.0.0.1:3001`.

Stop:

```bash
task docker:prod:down
```

## Production With External Keycloak

Use this when your organization already operates Keycloak.

```bash
task docker:prod:external-keycloak:up
```

You still use `.env.prod`, but the external Keycloak values become the important ones:

- `KEYCLOAK_PUBLIC_HOST`
- `KEYCLOAK_REALM`
- `KEYCLOAK_ADMIN_CLIENT_SECRET`
- `NUXT_OAUTH_KEYCLOAK_CLIENT_SECRET`

The external realm must contain equivalent frontend and backend clients, roles, redirect URIs, and web origins. See [Keycloak Setup](/deployment/keycloak-setup).

## Production With Bundled Nginx

Use this only if you want LAREX to start an Nginx container as part of the compose stack.

```bash
task docker:prod:nginx:up
```

`compose.prod.nginx.yaml` expects operator-provided certificate files. It does not request or renew LetsEncrypt certificates.

With bundled Keycloak, the default template requires:

- `${LAREX_PUBLIC_HOST}.crt`
- `${LAREX_PUBLIC_HOST}.key`
- `${KEYCLOAK_PUBLIC_HOST}.crt`
- `${KEYCLOAK_PUBLIC_HOST}.key`

With external Keycloak, set `NGINX_TEMPLATE_FILE=./deployment/nginx/templates/larex-proxy.external-keycloak.conf.template`. That template proxies only LAREX and requires only the `${LAREX_PUBLIC_HOST}` certificate pair; the external identity provider remains at its existing public URL.

## Reverse Proxy Expectations

For the default production setup, configure your external reverse proxy roughly as follows:

| Public host | Upstream |
| --- | --- |
| `LAREX_PUBLIC_HOST` | `http://127.0.0.1:3000` |
| `KEYCLOAK_PUBLIC_HOST` | `http://127.0.0.1:8090` |
| docs host, if self-hosted | `http://127.0.0.1:3001` |

Do not expose the backend container directly unless you have a specific internal integration requirement and understand the security consequences.

## Image Version Pinning

Production Compose pulls backend, frontend, and optional docs images from GHCR by default. Set `LAREX_IMAGE_TAG` in `.env.prod` to a released version instead of `latest` when you want reproducible deployments and predictable rollbacks.

Official processor images are pinned separately in `.env.actions`. Rehearse upgrades
with `task docker:prod:local:actions:up` before changing production.

## Routine Operations

Validate the resolved Compose model before a deployment and inspect the running
services without repeating the full list of Compose fragments:

```bash
task docker:prod:config
task docker:prod:ps
task docker:prod:logs
```

For a normal upgrade, pin the desired release in `.env.prod`, validate the model,
then pull and apply only changed images:

```bash
task docker:prod:config
task docker:prod:upgrade
```

When official processors are enabled, use the matching commands so their pinned
images and health checks are included:

```bash
task docker:prod:actions:ps
task docker:prod:actions:upgrade
```

The upgrade tasks wait for the resulting stack to become healthy. They do not
remove volumes or unrelated containers. To roll back application images, restore
the previous `LAREX_IMAGE_TAG` and run the same upgrade task. Database migrations
may not be reversible, so take a backup and review release notes before upgrading.

## Persistent Data And Backups

A recoverable production backup needs more than the portable dump in the Admin
Dashboard. LAREX provides a host-side snapshot command that coordinates all
required state:

```bash
task docker:prod:backup
```

The host needs Docker with Compose v2, `jq`, `tar`, and either `sha256sum` or
`shasum`.

The command briefly stops the frontend, backend, and bundled Keycloak so database
dumps and file volumes describe one consistent point in time. PostgreSQL remains
running for `pg_dump`. The resulting `larex-instance-*.tar.gz` contains:

- a custom-format PostgreSQL dump and the complete `app_data` volume
- the LAREX version, backend image, Flyway schema version, PostgreSQL version, and
  SHA-256 checksums
- with bundled Keycloak, its PostgreSQL dump and `keycloak_data` volume

Creation verifies the completed archive before restarting the paused services.
Environment files and secrets are excluded by default. Continue preserving
`.env.prod`, `.env.actions`, reverse-proxy configuration, certificates, and the
Action endpoint-secret encryption key in secure secret storage. You can use
`--include-config` only if the snapshot destination has secret-grade access
controls.

Checksums detect corruption; they do not authenticate who created an archive.
Sign snapshots with your normal operator signing tooling when authenticity is
part of the recovery policy.

### Verify And Restore

Verification is offline and does not require a running LAREX stack:

```bash
task docker:prod:backup:verify -- backups/larex-instance-20260719-120000.tar.gz
```

Run preflight against the target deployment before restoring:

```bash
task docker:prod:restore:preflight -- backups/larex-instance-20260719-120000.tar.gz
```

Preflight checks the archive format and every checksum, validates the auth mode,
rejects an older target PostgreSQL major version, and guards against a LAREX major
version mismatch. It makes no changes.

Restore replaces the target LAREX database and `app_data`. With bundled Keycloak,
it also replaces the Keycloak database and data volume:

```bash
task docker:prod:restore -- backups/larex-instance-20260719-120000.tar.gz --yes
```

The explicit `--yes` is required. If restore fails, LAREX services remain stopped
so a partially restored instance is not exposed. Inspect the error, repeat
preflight, and restore again. After success, check health and sign-in before
accepting traffic.

For external Keycloak deployments, use the script's `external-keycloak` profile
and back up the external identity provider independently:

```bash
./scripts/larex-instance-backup.sh create --profile external-keycloak
```

The Action processor `action_kraken_state` volume is a cache/data volume and can
usually be rebuilt, but preserve it if you install local models there. The Admin
Dashboard portable dump remains useful for moving workspaces and projects between
instances, but it is not an instance snapshot. See
[Workspaces, Import, and Backup](/user-guide/admin-dashboard/workspaces-import-backup).
Portable dumps are written to `/mnt/data/backups` in the backend container. The
production Compose stack mounts the dedicated `backup_data` volume there. Set
`LAREX_BACKUP_MOUNT_SOURCE` to a host directory when operators need the archives
to appear directly on the host.

`task docker:prod:down` removes containers and networks but preserves named volumes.
There is intentionally no production equivalent of the destructive local
`docker:down:clean` task.

## Verification

Check container health and then inspect logs:

```bash
task docker:prod:ps
task docker:prod:logs
```

or:

```bash
docker compose --env-file .env.prod \
  -f compose.prod.base.yaml \
  -f compose.prod.auth.bundled-keycloak.yaml \
  -f compose.prod.publish.localhost.yaml \
  ps
```

Verify:

- frontend is reachable through your public host
- Keycloak issuer and redirect URLs match the public Keycloak host
- backend health is reachable from the frontend container
- the backend is not directly exposed publicly
- email settings work for invitations and password/setup flows
- Action processor URLs are allowed and reachable if you use LAREX Actions

After the first successful login, rotate bootstrap passwords and remove or replace temporary admin credentials.
